# 规格 · F 域写接口补 version/CAS(并发防护)

状态:**待主人签字**(签字前不动码)· 分支 pkg/idem-hardening · 出处:idem-hardening 包第 6 项
依赖:**后端先补契约字段**,前端随后织入。范本 = 同树 G4 `expectedTiersVersion`(`lib/admin/g4-client.ts:599/608/617`)。

## ①用户故事

- **作为**佣金审计运营,**我想**在提交处置前确认这笔佣金没被别人改过,**以便**不会把一条基于过时状态的决定当成生效了。
- **作为**参数运营,**我想**在别人先我一步改了同一组参数时被明确拦下,**以便**不会静默覆盖同事的调整。
- **作为**风控负责人,**我想**每条 F 域写操作都能追溯它基于哪一版快照,**以便**事后对账时分得清「重复提交」和「基于旧数据的并发操作」。

## Why —— 幂等键防不了这一类

铁律:**并发 ≠ 重复。要 CAS 不是幂等键。**

- 幂等键(Idempotency-Key)回答的是「这条命令我是不是**已经发过一次**」。
- CAS(version / expectedVersion)回答的是「我这条命令**基于的那份快照,现在还成立吗**」。

F 域当前只有前者(`f1-client.ts` 全文 0 处 version,大小写不敏感回源确认)。于是两个失效场景无解:

| 场景 | 现在会怎样 | 该怎样 |
|---|---|---|
| A 冻结佣金事件 → B 复核后解冻 → A 未刷新页面,基于旧快照再点一次「冻结」并写同样理由 | 指纹(值 + 理由)与 24h 内那次完全一致 → 客户端复用同一命令号 → 后端幂等回放,直接返回第一次的结果。**A 以为冻结成功了,实际当前状态是解冻**;审计轨也不会有第二条 | 服务端比对 expectedVersion 与当前版本 → 不一致返 409,前端提示「数据已被他人改动,请刷新后重看当前状态」 |
| 两名运营同时基于同一份 V 级阈值表提交不同的调参 | 后提交的覆盖先提交的,先提交者无感知(lost update) | 后提交者拿 409,看到最新值后重新决策 |

第二个场景与 G4 阶梯档位当初的处境**完全同型**(区间耦合结构,任一行增删改都影响邻行),G4 已按 `expectedTiersVersion` 整表 CAS 解决,F 域照抄即可。

## 契约(需后端实现)

### 数据字典

| 字段 | 位置 | 类型 | 生成规则 |
|---|---|---|---|
| `version` | 各 F 读接口返回体 | 整数,≥0 | 服务端持有;**该聚合根内任一可写字段变更即 +1**;不下发 = 后端未升级 |
| `expectedVersion` | 各 F 写接口请求体 | 整数 | 前端把读接口拿到的 `version` 原样回传 |

**版本粒度 = 聚合根,不是单字段**(与 G4 `tiersVersion` 同口径:整表一个版本号)。F 域四个聚合根:

| 聚合根 | 覆盖的写动作 | 为什么是一个整体 |
|---|---|---|
| `f1.vrank`(V 级体系) | 阈值调整 · 奖励项增删改 · 晋降级 | 阈值与奖励项互相约束,单字段版本挡不住「改阈值 + 别人同时删奖励项」 |
| `f3.binary`(双轨制) | 双轨参数调参 · F3 结算 | 结算读的就是那组参数 |
| `f4.pool`(领导池) | 池参数调参 · 池结算 | 同上 |
| `f5.commission`(佣金审计) | 冻结 / 解冻 / 解锁 · 冲正 · 重发 · 暂停某用户 · 异常配置 | 同一笔佣金上的处置互斥,状态机必须序列化 |

### 端点与语义

- 所有 F 写端点(`lib/admin/f1-client.ts` 的 `updateF*TeamConfig` / `updateF1VRankThreshold` / `*F1VRankReward` / `executeF3Settlement` / `reverseF5Commission` / `reissueF5Commissions` / `suspendF5UserCommissions` / `updateF5AnomalyConfig`,以及 A2 提案通道上的 F 调参)请求体加 `expectedVersion`。
- 版本不匹配:**HTTP 409** + `message = F_VERSION_CONFLICT` + 返回体带当前 `version` 与最新快照。
- 409 是确定性拒绝(4xx),按统一 5xx 口径**弃命令号**,不进「结果未知」通道 —— 这次提交确定没生效。
- `expectedVersion` 缺失或非整数:400,不做「缺失即放行」的兼容(放行等于这道防护可被静默绕过)。
- 幂等键与 CAS **并存不互斥**:幂等键先判(同键重放直接回原结果,不再比版本),版本后判。

## GWT 验收

**G** 运营 A 打开 F5 佣金审计,读到 `version=7`
**W** 运营 B 在别处把同一笔佣金解冻(服务端 `version` 变 8)
**T** A 基于旧快照提交「冻结 + 同一理由」→ 服务端返 409 `F_VERSION_CONFLICT`,携当前快照;A 的页面提示「这笔佣金已被他人改动(当前:已解冻),请确认后重新操作」,并刷新为最新状态;**该命令号被丢弃,不留在待重试队列**

异常路径 1:**同一命令号重放**(A 网络抖动后原样重试)→ 幂等键先命中 → 返回第一次的结果,**不因为期间版本变了而报 409**(重放的是同一次意图,不是新意图)。
异常路径 2:**后端未升级**(读接口不下发 `version`)→ 前端不发 `expectedVersion`,行为与今天一致(退化但不报错);前端在 F 域面板顶部显示一次「并发保护未启用」提示,不静默。

## 前端侧改动(签字后另开实现任务)

1. `f1-client.ts` 读接口 normalize 出 `version`(缺席记 `null`,不要默认 0 —— 0 是合法版本号,拿 0 当「没有」会把首版当成缺席)。
2. 写接口签名加 `expectedVersion`,由调用方从当前 overview 取。
3. **版本织入命令号槽位/指纹**:槽位形如 `f-config:{key}@v{version}`。换版本 = 换槽位 = 铸新命令号,天然避免「旧快照同输入被当重试」。
4. 409 的错误分类落在「确定性失败」分支(弃号),文案走「他人已改动」而非泛化的「提交失败」。

## ⑤交互原型 · ⑥点击流

**N/A —— 本规格不新增任何界面**。它只在既有 F 域写路径上加一个请求字段与一条 409 分支;沿用现行确认弹窗
(`design-kit.tsx` 操作确认弹窗)与现行错误提示位,无新页面、新控件、新入口,故无原型稿与点击流矩阵。
唯一的可见变化是**一条新错误文案**(「这笔佣金已被他人改动(当前:X),请确认后重新操作」)与
后端未升级时的一次性提示(「并发保护未启用」),二者都落在既有提示位上。
四态覆盖沿用既有:默认(正常提交)/ 加载(提交 loading 锁定)/ 空(N/A,非列表)/ 报错(409 新分支 + 既有失败态)。
