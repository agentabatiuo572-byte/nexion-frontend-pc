# 结构性反思 · 两轮独立验收各抓到 P0(同型复发)

触发:CLAUDE.md「多轮不收敛 / 同型复发 → 强制结构性反思」。两轮验收、5 个 P0,且都不是
「没想到的边角」而是**同一族**认知错误。逐个打补丁不够,必须找共同根因并焊成不变量。

## 一、把缺陷列成族

| 轮 | P0 | 我当时的推理 | 错在哪 |
|---|---|---|---|
| 1 | 别名 import 绕过判据 | 「收紧到『真 import 了这个符号』就够了」 | 判了**名字出现过**,没判**调用点用的是不是这个绑定** |
| 1 | import 路径是子串判据 | 「路径含模块名 = 指向该模块」 | 同上:子串出现 ≠ 指向那个东西 |
| 1 | viaExecutor 免检金牌 | 「文件走了执行器路径就不必再查」 | 用**一处证据**替代了**逐个调用点核对** |
| 2 | 清扫接错路径 | 「resetAdminSession 就是登出」 | 按**名字**认定了函数职责,没回源确认退出按钮走哪条路 |
| 2 | 内存镜像复活清扫 | 「内存由随后的 reload 一并清掉」 | 把一条**未经验证的假设**当成了前提 |

## 二、共同根因(一条,不是五条)

**用「看起来指向 X 的表面证据」替代「X 确实成立的回源事实」。**

五个 P0 全是这一条的不同外衣:
- 表面证据 = 符号名出现过 / 路径含子串 / 有一处执行器调用 / 函数名叫 reset / 注释里写着 reload;
- 回源事实 = 绑定去向 / 路径解析结果 / 每个调用点 / 退出按钮的真实调用链 / reload 与这段同步代码的先后顺序。

值得注意的是:**我在修哨兵时明确知道这条病**(commit 里写着「判绑定去向而非名字出现过」),
却在同一轮里用同样的思路写批量脚本(靠「文件里提到模块名」判断该不该补 import,被自己的注释骗过),
下一轮又用同样的思路认定 `resetAdminSession` 是登出。**知道原则 ≠ 执行原则**——
这正是需要机器门而不是自觉的证据。

## 三、结构判断:是不是路线错了?

不是。三条理由:
1. 六项修复的**方向**每一项都被验收确认正确(归类口径、TTL 硬上限、内存兜底、清扫、剥注释),
   两轮 P0 全部落在「实现是否真的接到了该接的地方」,不在「该不该这么做」。
2. 缺陷密度在**下降且性质在变**:第一轮 P0 是判据本身可绕过(机制缺陷),第二轮 P0 是接线接错
   (集成缺陷),第三轮待验。没有出现「修了又坏」的反复。
3. 每一轮的修复都留下了**机器门**,不是口头约定:32 → 45 → 54 条红测变异,且每条都双向验过。

故:**根因非结构性,是同一类认知捷径的重复**。可以继续,但必须把这条捷径焊成门。

## 四、把根因焊进机器层(不写约定,写门)

已落地的三条:

1. **静态判据一律判「解析结果」不判「字面出现」**——哨兵的 `runtimeBindings()` 精确解析 import
   绑定与模块路径;归类门判裸状态码常量而非变量名。红测 T5-R1/R2/R3/R4、R2-P1-2 钉住。
2. **凡「一处证据代表全体」的判据一律改为逐单元核对**——撤掉 viaExecutor 免检金牌,逐个
   executor 常量核储存键与调用点;新增判据 5「用了共享 store 就必须在台账里」。
3. **接线类修复必须钉到「真实调用链的入口」而非同名函数**——清扫接 `signOut`(全部登出路径
   汇聚点)并由契约门钉死;门同时钉「退出按钮必须经 signOut」,防将来有人另开一条路。

## 五、留给下一轮的自查项(写进流程,不指望记性)

改动属于「把某个防护接到某条链上」时,动手前必须先回答并留痕:

- **这条链的入口有几个?** 逐个 grep 列出来,不靠猜。(P0-1 就死在只认了一个)
- **我依赖的前提是什么?哪一行代码证明它?** 写不出证明行号的前提一律当不成立处理。
  (P0-2 死在「reload 会清内存」这个没有证明的前提)
- **我的判据是在判事实,还是在判某个看起来相关的表面特征?** 后者一律要求升级。
