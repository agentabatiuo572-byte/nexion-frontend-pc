# K6 接管执行可观测性(裁决① · 红队视角)

状态:**Draft → 待实现**(主人 2026-08-06 裁决「补」;红队视角:只做技术功能层)

## Why(红队口径)

远程接管是**控制他人设备**的能力。当前 main 的可观测面只有一个 6 值命令态徽章
(`Device.commandState`: PENDING/PUBLISHED/ACKED/FAILED/EXPIRED/CANCELLED),运营下发后:

| 问的问题 | 现在能不能答 |
|---|---|
| 命令到设备了吗 | 只能看到「已下发」——下发到消息队列 ≠ 设备收到 |
| 卡在哪一步 | 不能。加载中 / 等会话边界 / 交接中 全部塌成 PUBLISHED |
| 为什么失败 | 不能。FAILED 无原因、无分类、无「能不能重试」 |
| 我下的目标 = 设备实际打开的目标吗 | **不能** —— 这是最危险的一条:目标被改过也看不出来 |
| 能撤销吗 / 能换目标吗 | 不能。一旦下发只能等 |

红队结论:**「下发成功」与「设备执行成功」被混为一谈**,且**期望目标与实际目标无对账**。
前者让运营误判止血已完成,后者是被中间人替换目标时的静默失陷面。

## What(三块,按红队优先级)

### 1. 执行相位账本(替换单一 commandState)

设备侧执行分相,**意图与结果分离**:

| 相位 | 含义 | 红队意义 |
|---|---|---|
| `HIT_NOT_REQUESTED` | 策略命中但未请求下发 | 区分「没打算做」与「做了没成」 |
| `COMMAND_PENDING_ACK` | 命令已发,设备未确认 | 未确认 ≠ 已生效 |
| `RECEIVED` | 设备确认收到 | 送达确证 |
| `WAITING_SESSION_EDGE` | 等待会话边界 | 卡这里 = 用户没进 App |
| `LOADING` | 目标页加载中 | 卡这里 = 目标不可达/超时 |
| `HANDOFF_FETCHING` / `HANDOFF_MERGING` / `HANDOFF_ACKED` | 账户态交接三步 | 交接失败 = 半接管态,最危险 |
| `SUCCEEDED` / `FAILED` / `CANCELLED` | 终态 | — |
| `REVOKE_PENDING_ACK` / `REVOKED` | 撤销中 / 已撤销 | 撤销同样要确证 |

### 2. 命令对账字段

- **命令 ID + 命令版本 vs 设备已应用版本** —— 版本不一致 = 设备跑的是旧命令
- **期望目标 vs 实际目标** —— 🔴 红队核心:两者不等即告警,不等待人工发现
- **因果来源**:人工请求号 + 审计号 / 自动判定号 —— 谁让它接管的
- **失败原因 + 分类 + 可重试性 + 失败阶段** —— 分类见下

失败分类(7 类):`delivery` 送达 / `target` 目标 / `webview` 页面 / `handoff` 交接 /
`lease` 租约 / `cleanup` 清理 / `contract` 契约。每类决定「能不能原地重试」。

### 3. 执行动作(带命令影响确认)

| 动作 | 何时可用 | 红队价值 |
|---|---|---|
| 撤销接管 | 已下发未终态 | **止血的止血** —— 现在完全没有 |
| 重发撤销命令 | 撤销未确认 | 撤销本身也会失败 |
| 更换批准目标 | 目标不可达 / 目标被换 | 不必先撤再重来 |
| 重试本次接管 | 失败且可重试 | 区分「可重试」与「必须换法」 |
| 查询设备应用态 | 任意 | 主动对账,不等设备上报 |

三项**命令影响确认**勾选(照原型):确认影响面 / 确认目标 / 确认撤销后果。

## T4 真实接口（联调候选）

前端不使用本地成功态；所有动作经真实后端账本并以设备上报为最终结果。`GET applied` 只读，主动对账必须先调用写权限保护的 `POST applied:refresh`，再携带服务端返回的 `reconciliationId` 轮询，未响应时保持 `fresh=false`。

### 需要的端点(五个动作 + 一个查询)

| 动作 | 语义 | 关键约束 |
|---|---|---|
| `POST /devices/{sid}/takeover/revoke` | 撤销接管 | 幂等键;返回新相位(应为 `REVOKE_PENDING_ACK`);**不得**在设备未确认前直接置 `REVOKED` |
| `POST /devices/{sid}/takeover/revoke:resend` | 重发撤销命令 | 仅在 `REVOKE_PENDING_ACK` 可调;复用同一命令 ID(不铸新号) |
| `POST /devices/{sid}/takeover/target` | 更换批准目标 | 目标须在白名单内(复用现有 origin 白名单校验);覆盖在途命令 |
| `POST /devices/{sid}/takeover/retry` | 重试本次接管 | 🔴 **后端必须自行校验可重试性**,不能只信前端:`handoff/lease/cleanup` 类失败重试会造半接管态 |
| `POST /devices/{sid}/takeover/applied:refresh` | 排入应用态对账命令 | 需要写权限、幂等键、版本和理由；只创建新对账请求 |
| `GET /devices/{sid}/takeover/applied` | 读取设备应用态 | 纯只读；新对账未响应时返回 `fresh=false`，不得修改账本或复用旧值冒充实时结果 |

### 响应契约

所有写动作返回更新后的 `TakeoverExecution`(字段见 `lib/admin/janus-c2/takeover.ts`),
前端据此刷新相位与对账;**期望目标与实际目标必须两侧齐备时才判失配**(单侧缺失是「未上报」不是「被替换」)。

### 已落地约束

- 相位枚举与标签、失败分类与可重试性判定、动作的相位约束与禁用原因(`allowedTakeoverCommands` /
  `takeoverCommandDisabledReason`)——UI 只需按这两个函数渲染按钮与禁用态
- 目标/版本对账判定与告警渲染(详情 + 队列)
- 服务端禁止加载态直接跳成功；成功 / 撤销 / 对账必须带实际目标版本、目录版本、命令应用版本、App 版本与交接凭证；旧命令、倒序和越级上报返回冲突。
- App 默认导航器无法证明页面加载和交接完成时返回 `JANUS_HANDOFF_PROOF_UNAVAILABLE`，不得上报成功；只有联调载体返回明确交接凭证后才走完整 handoff 相位。
