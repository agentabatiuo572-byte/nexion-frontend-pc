# 品牌改名 Nexion → NexGrid · 立项书

> 状态:**Draft — 待主人签字**
> 来源:差距台账 `2026-08-06-prototype-vs-main-gap-ledger.md` 旧线资产分类,唯一被判为「main 没做」的真资产。
> 结论先行:**这不是一次全局查找替换**,而是一次带数据迁移的跨仓契约变更。

## Why:现在是跨仓分裂状态

| 仓 | 品牌现状 | 证据(2026-08-07 实测) |
|---|---|---|
| `Nexion-uniapp`(用户端) | **已改名** | 52 个源文件含 NexGrid;持久化键已是 `nexgrid-*`(account-cloud / sessions / achievements …) |
| `admin-ops`(运营后台) | **未改名** | 145 个源文件含 Nexion;**NexGrid 出现 0 次**;持久化键 40 个全是 `nexion-admin-*` |
| `nexion-backend` | 未核(本机无该仓) | 需后端同事确认:Java 配置键 / 数据库表前缀 / 事件 topic |

用户端与后台叫两个名字,对外一致性与运营认知都受影响。

## What changes:四个层次,难度递增

### L1 · 纯展示文案(低风险)
页面标题、侧栏 logo 文字、页脚、邮件模板、错误提示里的品牌词。查找替换即可,过 verify 与走查。

### L2 · 代码标识符(中风险,不外露)
变量名 / 类型名 / 注释 / 文件名里的 `Nexion`。不影响运行时行为,但 diff 巨大,**建议单独一个提交**,便于审查时跳过。

### L3 · 🔴 契约面(高风险,跨仓)
**改这些等于改接口,必须与后端同批发布:**

| 类别 | 实测清单 | 改动后果 |
|---|---|---|
| 环境变量 | `NEXION_BACKEND_URL` · `NEXION_BACKEND_TIMEOUT_MS` | 部署配置要同步,漏一个直接连不上后端 |
| 代理头 | `X-Nexion-Client-IP` · `X-Nexion-Upstream-Outcome` | 后端按头名解析,不同步就丢客户端 IP 与上游结果分类 |
| 后端侧 | Java 配置键 / 表前缀 / 事件 topic(**待后端确认**) | 未知,需后端先出清单 |

### L4 · 🔴🔴 浏览器持久化键(最高风险,有用户可见后果)
`admin-ops` 有 **40 个** `nexion-admin-*` 键,其中包括:

- `nexion-admin-auth-v2` / `nexion-admin-auth-stale` —— **改键 = 全体运营当场被登出**
- `nexion-admin-{b2,b3,b5,c1,c3,c5,…}-*-commands-v1` —— 各域的**幂等命令号**本地台账。丢了它们,刷新后重试会拿到新命令号,**已提交但结果未知的高敏操作可能被重复执行一次**

**因此 L4 不允许直接改名**,必须写迁移:读旧键 → 写新键 → 删旧键,且迁移本身要有测试(注入旧键 → 断言新键出现且值一致 → 断言不重复迁移)。
uniapp 侧改名时已经踩过同族坑(见 memory `feedback_verify_harness_storage_keys`:改键后跨仓走查脚本注入的仍是旧键,断言一直红被误判为脚本脆性)。

## Done-when(可证伪)

1. `grep -rI "Nexion" --include=*.{ts,tsx} admin-ops`(排除迁移代码与历史注释)= 0 命中。
2. 注入一份**旧键**的 localStorage 快照 → 刷新 → 运营**不被登出**,且 40 个键全部迁到新名、值一致。
3. 代理头与环境变量改名与后端**同一批**发布;发布前跨仓契约门(FE/BE mapping)在**两仓齐备**的机器上跑绿。
4. 走查:侧栏 / 登录页 / 页脚 / 邮件模板 0 处残留旧品牌。
5. `docs/` 下 PRD 与验收报告的文件名与正文品牌词一并追平(注意:PRD 权威副本在 `PLAN/PRD/`,已叫 NexGrid)。

## 明确不做(out of scope)

- 不改 git 仓名与远端地址(另议,影响所有人的本地 checkout)。
- 不改已归档的验收报告正文(历史记录保持原样,只在索引处标注)。
- 不动 `nexion-backend` 仓(由后端同事在同一批次内完成,本项目只提供清单与联调)。

## 🔴 排期前必须先答的三个问题(主人 / 后端)

1. **后端契约面清单**在哪?没有它,L3 只能猜,而猜错就是线上连不上。
2. **要不要保留一个过渡期双读**(新旧键都认、新旧头都收)?保留则可分批发布,不保留则必须原子切换。
3. **git 仓名与远端**改不改?不改的话,代码里叫 NexGrid、仓叫 nexion-ops-console 会长期并存。

> 建议:**先只做 L1 + L2**(纯展示 + 内部标识符,零跨仓风险,当轮可完),
> L3/L4 等后端清单到位后单独一个批次做,并把持久化键迁移当成独立子任务带测试。
> 理由:L1/L2 立刻消除「用户端叫 A、后台叫 B」的对外不一致,而 L3/L4 的风险(登出全体运营、
> 幂等台账丢失)必须配迁移与跨仓联调,和展示层改名不是同一个量级,混在一批里会互相拖累。
