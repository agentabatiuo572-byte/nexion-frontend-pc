# PC 客服与确认框逻辑修复（2026-11-17）

## 共用数字确认（BUG-413、BUG-163-17/19）

单值和多字段的未修改判定按十进制字符串规范化比较，保留合法金额末位差异。多字段先检查普通十进制格式，再检查步长；不接受科学计数。方向比较同样不经浮点。当前值未配置且新值为 0 时不触发放大提示；未配置仍是未知，不补成已配置的 0。F2 缺层仍需后端初始化（UnilevelCommissionService.requireCompleteLayerRates:307–317），沿用 F2-P01。

## M3 接待实例（BUG-416）

结束接待的原命令按 actorId/customerId/sessionRef 保存；当前实例和历史实例分别恢复。不同 sessionRef 的历史记录不阻断当前接待结束；历史完整原记录仍保留，查询入口沿用。过期历史只查不重发。依据 SupportSessionService.end:108–116：结束携带实例引用，不匹配时 SUPPORT_SESSION_CHANGED；成功原键优先回放。旧无实例记录沿用保守核对，不推断原请求失败。

## M1 与 M3 读取（BUG-164、BUG-163-06）

M3 conversationNo 定位等资格及可见范围就绪后才消耗选中意图。M1 暂停维护明细使用每页实时 snapshot 的数量，不再和旧卡片数字强制相等；仍校验本页列表和同次 overview 的数量。analytics 各明细续页必须回传自身 queryVersion，缺版本不能绕过后端 SUPPORT_ANALYTICS_VERSION_REQUIRED；维护绩效明细使用 expectedQueryVersion。授权名册的可接待切片由 availableSupportRoster 返回，筛选 enabled !== false 且 status !== disabled，卡片同用该切片。名册 permission/error/loading/ready 分开，不增加权限；下钻与无权限说明见下文「界面与文案」。

## 客服恢复及支付理由（BUG-163）

模板／话术重试只重读 session-templates/overview，不刷新名册、会话或资格；FAQ 已独立读 knowledge/overview。URL 有 intent 时覆盖本标签页旧选项，没 URL 意图才恢复 sessionStorage。普通 403、普通 404 不证明原发送失败；权限失效仍清除私聊正文并保留只读定位。原号重放被现有 rejectedSupportWrite 明确认定为拒绝时保留原命令，并按 OP-93 第 8 条提供人工解除：先核实原操作结果，再通过既有 ReleaseModal 解除本标签页对应记录，解除后不再重试原操作。发送、首次联系和结束接待共用此规则，不自动清除被拒的重放。精确 SUPPORT_COMMAND_NOT_FOUND 才可进入未过期原样重试；单凭过期或查不到不能解除（OP-153），明确拒绝后的人工解除仍有效。

C5 支付规则理由按 Java String.trim 去掉首尾所有 U+0000–U+0020 后计算 UTF-16 长度并提交，范围仍 8–200；不改控件和文字。C2 动作台账登记当前会话撤销审批、代看和黑白名单，既有用户读写授权不变。G2 规格移除退役 KYC 累计阈值，现行只有个人与平台日额度。

## M3 转绑后的会话续接（BUG-424）

resolveMConversationContinuation 先读取线程 writeState，再核当前客户归属与 assignmentId。存在 writableConversationNo 时打开该线程；没有可写线程时进入当前客户首次联系草稿，只有发送首条消息才调用既有 POST /content/conversations（supportClient.startConversation），不自动新建线程，不改变历史 owner。已结束的历史线程沿用头部「前往当前会话」；OPEN/canReply=false 的旧线程由会话下方提示里的按钮进入（见下文「界面与文案」），两者都调用同一 continuation 处理函数，仍核资格、写权和接待状态。CONVERSATION_PEER_CHANGED 表示线程原归属/当前分配不符合写入合同，重进客户列表不保证解决；需定位可写线程或首次联系，提示文字见下文。

## E2 旧任务定价退役（协调跟进）

按已批准 E2-A07/A08/A09/A12 移除旧写入口。OPS-E-17 参照 OPS-D-11/12/13 保留 readonly 退役留痕，删除失效写锚。删除无调用方 updateE2TaskPricing，PC config BFF 不再允许 task-pricing PUT；GET/HEAD 作为兼容只读路由保留，当前改版页面没有读取调用。后端 OpsDeviceConfigController:32–37 仍提供 PUT，由后端另行退役。

## F01：转绑后的 OPEN 旧线程入口

canReply=false 的 OPEN 线程也有续接入口（会话下方提示里的按钮，见下文「界面与文案」），仅在资格就绪、有 M3 写权、未被其他人接待、当前线程详情已读且 currentAssignmentAgentId/当前归属均为本人时出现。处理仍刷新后端归属，按 writableConversationNo 定位或进入首次联系；旧线程本身不开放回复。

## F02：结束接待的普通 404

结束接待和两条发送路径共用 rejectedSupportWrite：普通 404、403、未知/幂等状态不算原请求的结论。首次结束接待普通 404 保留原记录，不提供解除；精确 SUPPORT_COMMAND_NOT_FOUND 仅用于查询查无后判断是否可在有效期内按原 sessionRef 重试，过期只查。

## F03：首次联系完成后的续接状态

首次联系收到成功回执后清除本次 continuation（包括消息已成功但列表刷新失败的情况）；选择会话或再次主动选择客户也先清除它。之后按最新会话列表重新定位，不让上次“没有线程”的结果覆盖新建线程。原首发未知仍保留原请求，不清 continuation 冒充成功。首次联系 HTTP 合同没有 expectedVersion 字段，保持后端现状；本地版本仅为快照数据。

## F04：逐条查询结束接待原记录

readSessionEndRecords(actorId, customerId) 导出该操作者/客户的全部未决结束记录。页面 sessionEndRecoveries 为每条追加 instanceState（current／historical／unconfirmed），querySessionEndRecord(record) 只查询该 key；已确认当前接待的记录单独一条提示，已确认不同实例的记录合成一个恢复面板，未确认实例单独提示（见下文「界面与文案」），每条都有「查询原结果」；未知/过期保留，权威 SUCCEEDED/FAILED 只移除对应记录。查询动作不重发，即使未过期；结束当前实例仍按原 key/sessionRef 和期限恢复，与历史查询分开。明确拒绝标记逐 key 保存于当前页面，解除也只处理对应 key。

## L02：支付规则原请求完整性

面板计数、提交与 isCompletePaymentPolicy 同用 payment-password-contract.ts 的 trimPaymentReason，按 Java String.trim 裁 U+0000–U+0020，不裁 U+00A0。合法 NBSP＋七字理由的未决请求保持完整，可在原有效期内按原 body/key 恢复。其余提交人、版本、内容完整性与授权检查不变。

## M1 明细 503 按后端原因区分（跟进3）

后端 c965e730 将明细失败分为三类：HISTORY_INCOMPLETE 表示历史证据未同步完整，单独保留等待重读状态；DETAIL_MISMATCH 表示历史已就绪但与已确认金额或事件数不一致，进入现有“核对不上”状态；SOURCE_UNAVAILABLE 表示普通读取失败，保留重试。三类都不显示部分记录或空列表。工作台的 SOURCE_UNAVAILABLE 也按普通读取失败处理，数据客户端原样保留错误码。新增两码中文映射；三类的呈现和中文见「界面与文案」。依据 SupportAnalyticsPrivateQueryService.query:45–75、financialDetails:137–186。

## M3 归属冲突即时重读（跟进3 A）

发送、首次联系（含原号恢复）收到 409 CONVERSATION_PEER_CHANGED 时，共用 refreshChangedPeer 重新读取会话列表、当前线程 writeState 和客户当前归属，并使旧 continuation 失效；沿既有选中会话跟随规则切到其当前归属范围，避免客户从“其他客户”变为“我的客户”后仍被旧筛选隐藏。首次提交被该码明确拒绝时解除对应未决记录，保留草稿原文；按原号重放被明确拒绝时保留原 body/key/clientMessageId/实例及有效期，并提供核实后的人工解除，不把重放拒绝当原命令失败或自动清除记录。两种情况都当场重读，不自动重发；后续失权仍按既有隐私合同清正文、保留只读定位。只接数据和状态，不改视觉 worker 的入口、提示、409文案。依据 MybatisConversationRepository.requirePeerForWrite:119–129 与 OpsConversationService.conversationWriteState:158–174。

## F01：续接统一按当前线程定位（跟进5）

可写线程已加载和未加载都由 canContinueConversation 核当前归属本人/写资格，入口统一走 continueClosed；不再由 select(current) 选客户代表线程。未加载先刷新获准会话快照，再以 continuation 的 writableConversationNo 精确选择，由原消息/详情读取流程加载，避免旧 OPEN 覆盖当前已结束线程。主管和其他客服只读，不得到续接按钮；现有文案/样式保持。

## F02：被拒线程在回复资格未知时保持只读（跟进5）

已选线程被 CONVERSATION_PEER_CHANGED 拒绝时，先针对该线程使 writeState 失效并中止旧详情读取，再走现有重读；仅权威详情成功返回 canReply=true 才满足可写条件。列表或详情失败不恢复旧可写资格，未知不能视为允许。现有提示位暂写“还没核对到这条会话能否回复，请重新读取。”并给重新读取会话入口；重读成功后沿既有只读提示与本人续接入口。其它线程不因这次失效被锁；R1、失权隐私处理不变，跨客户continuation时序I02仅登记。

## F04：结束记录按三种已知事实分类（跟进5）

记录有ref且当前接待ref已读到，相等才是current；明确不同才是historical，只有historical进既有“之前的接待”面板。当前接待读取未知或记录没有ref均是unconfirmed，复用现有提示逐条查询，不承诺不影响当前接待。暂放事实句：有ref未确认“接待实例未确认：可查原结果；结束入口仍按原记录及期限核对。”；无ref“记录缺少接待编号：只能查原结果；结束当前接待仍受原记录核对限制。”，过期附既有期限句。逐key查询、未过期有ref原号恢复、legacy核对/限制均保持；最终措辞与呈现交视觉。

## OP-93 第 8 条：明确拒绝重放后的人工解除（跟进6）

此前“重放被拒不解除”的概括作废。网络、超时、5xx、不可读响应仍为结果未知；明确拒绝按既有 isExplicitRejection／rejectedSupportWrite 判定，不另增分类。首发发送／首次联系明确拒绝仍清未决槽并保留草稿；首发结束接待明确拒绝仍保留记录并可人工解除。三条路径按原号重试被明确拒绝时均保留记录、标记被拒、复用结束接待的「解除原操作记录」和 ReleaseModal；取消不清记录，确认仅清所选本地记录，不发请求、不写操作记录、不代替核查结案，草稿不清。解除前仍可查询原结果，过期只保留查询及已取得的人工解除资格，不因过期额外授予解除。403／普通404不新增解除资格，隐私清正文／只读恢复定位保持。peer409的首发释放槽并重读、重放保留且可人工解除并重读。现有确认框尚未明写“不发请求、不进操作记录”，以及消息/首次联系的通用句是否合适，交视觉决定；本次未改共用确认框文字、结构或样式。
