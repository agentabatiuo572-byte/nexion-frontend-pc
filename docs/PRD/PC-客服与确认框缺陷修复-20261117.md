# PC 客服与确认框逻辑修复（2026-11-17）

## 共用数字确认（BUG-413、BUG-163-17/19）

单值和多字段的未修改判定按十进制字符串规范化比较，保留合法金额末位差异。多字段先检查普通十进制格式，再检查步长；不接受科学计数。方向比较同样不经浮点。当前值未配置且新值为 0 时不触发放大提示；未配置仍是未知，不补成已配置的 0。F2 缺层仍需后端初始化（UnilevelCommissionService.requireCompleteLayerRates:307–317），沿用 F2-P01。

## M3 接待实例（BUG-416）

结束接待的原命令按 actorId/customerId/sessionRef 保存；当前实例和历史实例分别恢复。不同 sessionRef 的历史记录不阻断当前接待结束；历史完整原记录仍保留，查询入口沿用。过期历史只查不重发。依据 SupportSessionService.end:108–116：结束携带实例引用，不匹配时 SUPPORT_SESSION_CHANGED；成功原键优先回放。旧无实例记录沿用保守核对，不推断原请求失败。

## M1 与 M3 读取（BUG-164、BUG-163-06）

M3 conversationNo 定位等资格及可见范围就绪后才消耗选中意图。M1 暂停维护明细使用每页实时 snapshot 的数量，不再和旧卡片数字强制相等；仍校验本页列表和同次 overview 的数量。analytics 各明细续页必须回传自身 queryVersion，缺版本不能绕过后端 SUPPORT_ANALYTICS_VERSION_REQUIRED；维护绩效明细使用 expectedQueryVersion。授权名册的可接待切片由 availableSupportRoster 返回，筛选 enabled !== false 且 status !== disabled，卡片同用该切片。名册 permission/error/loading/ready 分开，不增加权限；下钻与无权限说明见下文「界面与文案」。

## 客服恢复及支付理由（BUG-163）

模板／话术重试只重读 session-templates/overview，不刷新名册、会话或资格；FAQ 已独立读 knowledge/overview。URL 有 intent 时覆盖本标签页旧选项，没 URL 意图才恢复 sessionStorage。普通 403、普通 404 不证明原发送失败；权限失效仍清除私聊正文并保留只读定位。按协调人跟进7确认的本线共用规则，发送和首次联系的首发、原号重试，只要 submitted 且 rejectedSupportWrite 明确认定为拒绝，就清未决记录、保留草稿并显示既有被拒提示；不单独提供人工解除。结束接待保持明确拒绝后标记、保留记录并可人工解除（首发和重试相同）。精确 SUPPORT_COMMAND_NOT_FOUND 才可进入未过期原样重试；单凭过期或查不到不能解除（OP-153），结束接待明确拒绝后的人工解除仍有效。

C5 支付规则理由按 Java String.trim 去掉首尾所有 U+0000–U+0020 后计算 UTF-16 长度并提交，范围仍 8–200；不改控件和文字。C2 动作台账登记当前会话撤销审批、代看和黑白名单，既有用户读写授权不变。G2 规格移除退役 KYC 累计阈值，现行只有个人与平台日额度。

## M3 转绑后的会话续接（BUG-424）

resolveMConversationContinuation 先读取线程 writeState，再核当前客户归属与 assignmentId。存在 writableConversationNo 时打开该线程；没有可写线程时进入当前客户首次联系草稿，只有发送首条消息才调用既有 POST /content/conversations（supportClient.startConversation），不自动新建线程，不改变历史 owner。已结束的历史线程用头部按钮进入（有可写线程时是「打开当前会话」，没有时是「发起会话」）；OPEN/canReply=false 的旧线程由会话下方提示里的按钮进入（见下文「界面与文案」），两者都调用同一 continuation 处理函数，仍核资格、写权和接待状态。CONVERSATION_PEER_CHANGED 表示线程原归属/当前分配不符合写入合同，重进客户列表不保证解决；需定位可写线程或首次联系，提示文字见下文。

## M3 续接边角（BUG-442）

回复和首次联系（含原号重试）在已提交且被 CONVERSATION_PEER_CHANGED 明确拒绝时，仍清未决、保草稿，不自动重发。被拒上下文按当前身份、客户与来源草稿槽保留；自动跳到当前线程或退回旧线程后，待读到同一客户且当前归属仍为本人时，与手动续接共用草稿迁移：没有本次回复／首次联系未决记录、来源非空且落点为空才移动；落点已有草稿时两份都保留。被拒提示跨此次自动选中和续接保留，主动切客户或开始下一次发送后按既有提示流程处理；身份与失权清理照旧。

续接入口及历史只读说明都排除 writableConversationNo 等于当前选中线程。后端 currentCustomerConversationForRead 不按状态过滤（ConversationMapper:29–42），canReply 取当前线程编号匹配（OpsConversationService:158–174）；真正回复仍校权限、归属、接待与快照，RESOLVED/CLOSED 成功回复会转 OPEN（ConversationMapper:481–496），不因“已结束”额外强迫续接。续接核对发现客户已不归本人时，先使旧 writeState 失效、重读列表和线程／客户详情，再显示归属变化提示；读取失败不恢复旧写资格。现有提示位与屏幕组成不变，第4/5处最朴素提示交界面 worker 定稿。

I 域、法律条款、隐私等已发布内容、A2 原单查询及原操作核查的共用请求入口，为格式化的服务不可用与网关错误传递 read/write；读取沿用 displayAdminReadError 的现成服务不可用句式，写入仍保留结果未知句。RETRY_EXPIRED_TEXT 自带末尾句号，各拼接处不再另加句号。

## F01：转绑后的 OPEN 旧线程入口

canReply=false 的 OPEN 线程也有续接入口（会话下方提示里的按钮，见下文「界面与文案」），仅在资格就绪、有 M3 写权、未被其他人接待、当前线程详情已读且 currentAssignmentAgentId/当前归属均为本人时出现。处理仍刷新后端归属，按 writableConversationNo 定位或进入首次联系；旧线程本身不开放回复。

## F02：结束接待的普通 404

结束接待和两条发送路径共用 rejectedSupportWrite：普通 404、403、未知/幂等状态不算原请求的结论。首次结束接待普通 404 保留原记录，不提供解除；精确 SUPPORT_COMMAND_NOT_FOUND 仅用于查询查无后判断是否可在有效期内按原 sessionRef 重试，过期只查。

## F03：首次联系完成后的续接状态

首次联系收到成功回执后清除本次 continuation（包括消息已成功但列表刷新失败的情况）；选择会话或再次主动选择客户也先清除它。之后按最新会话列表重新定位，不让上次“没有线程”的结果覆盖新建线程。原首发未知仍保留原请求，不清 continuation 冒充成功。首次联系 HTTP 合同没有 expectedVersion 字段，保持后端现状；本地版本仅为快照数据。

## F04：逐条查询结束接待原记录

readSessionEndRecords(actorId, customerId) 导出该操作者/客户的全部未决结束记录。页面 sessionEndRecoveries 为每条追加 instanceState（current／historical／unconfirmed），querySessionEndRecord(record) 只查询该 key；已确认当前接待的记录单独一条提示，已确认不同实例的记录合成一个恢复面板，未确认实例单独提示（见下文「界面与文案」），每条都有「查询原操作」；未知/过期保留，权威 SUCCEEDED/FAILED 只移除对应记录。查询动作不重发，即使未过期；结束当前实例仍按原 key/sessionRef 和期限恢复，与历史查询分开。明确拒绝标记逐 key 保存于当前页面，解除也只处理对应 key。

## L02：支付规则原请求完整性

面板计数、提交与 isCompletePaymentPolicy 同用 payment-password-contract.ts 的 trimPaymentReason，按 Java String.trim 裁 U+0000–U+0020，不裁 U+00A0。合法 NBSP＋七字理由的未决请求保持完整，可在原有效期内按原 body/key 恢复。其余提交人、版本、内容完整性与授权检查不变。

## M1 明细 503 按后端原因区分（跟进3）

后端 c965e730 将明细失败分为三类：HISTORY_INCOMPLETE 表示历史证据未同步完整，单独保留等待重读状态；DETAIL_MISMATCH 表示历史已就绪但与已确认金额或事件数不一致，进入现有“核对不上”状态；SOURCE_UNAVAILABLE 表示普通读取失败，保留重试。三类都不显示部分记录或空列表。工作台的 SOURCE_UNAVAILABLE 也按普通读取失败处理，数据客户端原样保留错误码。新增两码中文映射；三类的呈现和中文见「界面与文案」。依据 SupportAnalyticsPrivateQueryService.query:45–75、financialDetails:137–186。

## M3 归属冲突即时重读（跟进3 A）

发送、首次联系（含原号恢复）收到 409 CONVERSATION_PEER_CHANGED 时，共用 refreshChangedPeer 重新读取会话列表、当前线程 writeState 和客户当前归属，并使旧 continuation 失效；沿既有选中会话跟随规则切到其当前归属范围，避免客户从“其他客户”变为“我的客户”后仍被旧筛选隐藏。首发和按原号重试在已提交后被该码明确拒绝时，均清对应未决记录、保留草稿原文，显示既有被拒提示。依据协调人跟进7确认的本线共用明确拒绝解除规则，不再区分重放保留分支。两种情况都当场重读，不自动重发；后续失权仍按既有隐私合同清正文、保留只读定位。只接数据和状态，不改视觉 worker 的入口、提示、409文案。依据 MybatisConversationRepository.requirePeerForWrite:119–129 与 OpsConversationService.conversationWriteState:158–174。

## F01：续接统一按当前线程定位（跟进5）

可写线程已加载和未加载都由 canContinueConversation 核当前归属本人/写资格，入口统一走 continueClosed；不再由 select(current) 选客户代表线程。未加载先刷新获准会话快照，再以 continuation 的 writableConversationNo 精确选择，由原消息/详情读取流程加载，避免旧 OPEN 覆盖当前已结束线程。主管和其他客服只读，不得到续接按钮；现有文案/样式保持。

## F02：被拒线程在回复资格未知时保持只读（跟进5）
