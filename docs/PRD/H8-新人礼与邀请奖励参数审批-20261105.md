# H8 新人礼与邀请奖励参数审批

本章覆盖 `/growth/referral-rewards` 的五项奖励参数与两种结算（H8-A01～A07）。2026-11-15 接线以 Java `111e00cd` 为合同，沿用已完成改版的界面。三金额、模式、开关和两种结算共七类操作，参数拆分直写与审批为十二个方向合同；旧视觉抓包的九个样本不替代全部方向验收。参数按方向分审批与即时保存，不以角色名称替代接口权限。

| 参数 | 提交审批 | 原接口即时保存 |
| --- | --- | --- |
| 新人 USDT 基础额 | 提高 | 降低或等值 |
| 新人 UVT 基础额 | 提高 | 降低或等值 |
| 邀请人 UVT 基础额 | 提高 | 降低或等值 |
| 新人礼发放模式 | 先过风险检查再发 → 符合资格就直接发 | 反向切换 |
| 奖励开关 | 已停用 → 已启用 | 停用 |

金额基础额分别允许 0–50 USDT、0–500 UVT、0–249999999.75 UVT，最多六位小数。方向和参考有效额使用精确整数计算，不使用浮点舍入；有效额由基础额乘 H1 当月新用户加成或邀请加成，后端四舍五入到六位。参数放大在提案预审和批准执行时检查 B1 覆盖率，批准执行重新按当时 H1 核对；非放大直接保存不查 B1。前端判为直写但收到 `A2_CONFIRMATION_REQUIRED` 时停止自动建单；HApprovalRequired保留参数、值、理由和快照，confirm回调再次核对账号/读取后才建提案。页面换成审批确认（批准后生效、另一位超级管理员批、改动从多少到多少），参数、值和理由锁定沿用，运营点「提交审批」才建提案；被别人先改过时提醒写现在的值和要改的值，重读失败写最新值没读到。固定启停沿用原意图，最新状态已相同则不发请求。

审批使用 `H/h8_reward_param_change`，`params.values` 仅含字符串 `key`、字符串 `value` 和整数 `expectedVersion`；`sourceDomain=H8`、`obj=current`、目标 `H/h8_reward_policy/current`。发起要 `growth_h8_write`，本专项不另要求 A2 通用提案权；批准要另一位超级管理员且有 `platform_a2_operation_approve`。待批准配置不变；按原号的权威 GET 返回 pending 才显示待审批，参数放大共享整份奖励政策锁。收紧仍走原 PATCH，后端没有给 H8 直写加 A2 政策锁门，不把“有待批单”解释成所有收紧都不能执行。

每次金额或发放方式成功保存（包括等值），以及启用获批准，都把 `effectiveAt` 重置为执行时刻。在此之前注册、尚未结算的新人不再进入新结算；注册时间等于生效时刻仍包含在新结算范围内，已结算和已冻结的金额不重算。停用保留已配置的生效时间、停止新结算，原冻结新人礼仍可在首笔非零实付订单后解冻。纪元 `1970-01-01T00:00:00Z` 是迁移中的初始闸值，页面和确认框统一显示未设置、所有注册都算；缺值或空字符串后端拒绝读取，前端不补成 0 或 1970。

所有写发送前耐久保存完整原对象、原 body/envelope、操作者、理由、命令号和确认事实；存储失败不发。直写和结算共用原 H8 存储键，参数提案沿用共用审批存储的唯一实例。结果未知冻结输入，刷新或概览失败仍有查询和恢复入口；只能在首次尝试后 24 小时内按完整原请求和原号重试，改目标、值、版本、理由或统计数都不能替换原请求。重试中认证、权限、限流、所有 `IDEMPOTENCY_*` 和不明确回包继续保留；首次明确 4xx 或非零业务码按共用首次拒绝规则丢号、留框。恢复后明确拒绝或成功均结束原框并先重读，成功回放的历史回执不能替代当前数据。

参数和结算提案都按原号 GET 查询当前票；仅 `A2_PROPOSAL_NOT_FOUND` 算无原单，其他 404/403/503 不算。核对 mine、obj、operationCode 和合法状态：后端 `111e00cd` 的 ticketMetadata 已对持久 command 返回 op（旧无 command 票仍可空），不沿用旧基线“只少数操作有 op”的结论。POST 成功后再 GET；GET 失败只保留“已建单、当前状态未知”的查询证据，不能凭旧 pending 回执锁成现在待审批，也不能再次 POST。过了 24 小时只能查询、不能再重试。原请求重试被明确拒绝后，核实原操作可以解除本标签页记录；查无原单或到期本身不解除。

直写严格核对 `{key,value,status:UPDATED,version:原版本+1}`。确认保存但回读失败时使用现成的“已保存，但没读到最新值”提示和重新读取入口，冻结新的修改，读成功才恢复。直接写没有按命令号的权威结果查询 API，读回当前值只能供核对，不据值相同或不同自动解除原记录；保留操作记录与审批的核对入口。旧记录缺完整原请求时只查询，不从今日值或今日操作者重建请求。
