# D1 / D5：USDT 分网络资金控制

按用户 2026-11-07 确认的图中方案及 2026-11-08 确认的 TRC20 增量范围实施。构建、TEST 发布、页面操作与真实链上资金验收分别记录。

## D1：充值与地址设置

位置：「充值与收款对账 › USDT 充值 › 充值与地址设置 › 收款与出款开关」，同一子页签下方另有「全局紧急停用」。字号沿用 rd 组件，不另设。

「收款与出款开关」为 BEP20、ERC20、TRC20 各显示一行充值开关、实际状态、未生效原因及独立提交审批按钮。开关开启且库存不足显示「地址准备中」，不把库存不足显示成网络关闭。读取不到新契约时明确提示无法编辑，不伪造默认值。兼容旧两网响应；缺少 TRC20 时该行显示尚未配置、实际状态待核实，不允许提交、补池或对账。

「分网络充值开关」表 BEP20、ERC20 各一行：网络、充值开关（开启 / 关闭）、实际开放情况、操作。实际开放时写「已开放」，开关开启但地址库存不足写「已开放 · 地址准备中」，不把库存不足显示成网络关闭；未开放时写后端给的原因。读不到分网络开关时写「读不到分网络充值开关，当前不能修改。请刷新后再试。」，不伪造默认值。

每行「调整」打开修改框，只改这一条网，写现在的值和改后的值（相同值不能提交），提交审批后由另一名仍有权限的管理员复核，另一条网不受影响。这一条网已有待复核提案时「调整」禁用。共享闸版本或网络版本变化后，待复核行写「配置版本已变，请拒绝后重新申请」，旧提案不可通过。

每行提交只改变该网充值，必须由另一名仍有权限的管理员复核。共享闸版本和网络版本变化后旧提案不可通过。草稿随本行版本更新，其他行刷新不覆盖尚未提交的本行选择。

「待复核申请」（有提案时展开）每行写提案号、发起人、「现在 → 提案值」和发起理由；复核和拒绝的确认框写现在的值和提案值。本人发起的申请禁用「复核通过」「拒绝」，原因写「这是你发起的，需要另一位管理员处理」。

提案、复核、紧急停用发生结果未知时，在 USDT 充值页签顶部常显结果未确认条（开关提案、开关提案复核、紧急停用两网），只给当前管理员；条上「读回核对」写两网开关、链上出款和待复核提案数，「按原操作重试」按原路径、参数、理由和请求号恢复，不另建同类提案或同一申请的复核请求。上一个开关提案结果未确认时，新提案入口禁用；未知提案不阻断紧急停用。后端明确拒绝重试后才出现「解除待确认」，超过 24 小时不能再重试。恢复取得明确结果后重读实际状态；读取失败明确提示，不能当作状态已核实。开关的结果未确认和待复核提案也进页面的跨区提醒。建址、补池、对账等其他写操作按 D1 通用的结果未确认规则处理（见 PRD v1 D1 ④）。

实际开放 = 网络运营开关 + 服务启动/RPC 配置 + 全局分配地址及入账总闸。普通单网关闭不关闭另一网。全局暂停时每行多一个「申请恢复」，只申请恢复所选网络充值，另一网充值保持关闭，不恢复出款。

实际开放 = 网络运营开关 + 服务启动/RPC 配置 + 全局分配地址及入账总闸。普通单网关闭不关闭其他网络。恢复共享充值闸须明确提交恢复审批，其他网络充值保持关闭，不恢复出款。

全局出款总闸作为 BEP20、ERC20、TRC20 三网共同上限单独显示和审批；分网络出款跳转 D5，D1 不增加第二套分网出款开关。紧急关闭关闭全部共享资金闸及三网充值权限，按钮与确认说明同步写明三网，后续分别审批恢复。只读人员可查看状态，不能提交或审批。

资金状态、出款能力和地址池网络选择加入 TRC20（TRON）；三网独立显示库存和对账结果。共同充值规则仍共享最低额、固定费和确认数（15–10000），已发现交易保留原规则；TRC20 还须满足固化区块核验。地址池共用补充目标，但 TRON 库存、地址及交易标识不与 EVM 混用。银行充值入口和对账渠道说明同步标明三网。

订单付款与手续费加入 `CREGIS_USDT_TRC20`，网络为 `TRC20`。复用现有网络选择、费率表、付款记录、详情和原请求恢复。未返回该渠道的旧响应可读取，TRC20 费率页显示尚未配置且不可编辑，不补写默认费用；显式返回但尚未配置费用的渠道继续沿用既有填写流程。TRON 详情说明外部钱包可能另收 TRX 或消耗能量、带宽，不误标 BNB；不把付款成功直接视为业务履约完成。

「自动归集与甲方付款」「归集与甲方付款准备」明确标注仅 BEP20。本轮不扩展 TRON 自动归集、甲方钱包配置或付款执行。

全局链上出款总闸仍作为两个网络的共同上限单独一行显示和审批，值只写开关状态，出款能力说明在名称旁问号里；修改框写现在的值和改后的值。分网络出款由面板上的「前往 USDT 提现参数」进入 D5，D1 不增加第二套分网出款开关。紧急关闭关闭全部共享资金闸及两个网络充值权限，后续分别审批恢复。只读人员可查看状态，不能提交或审批。

## D5：USDT 提现参数

位置：「资金与财务 › USDT 提现参数」（`/finance/params`），打开和点「刷新」时读取，不自动刷新。没有修改权的账号页头写「你只能查看」，不出「调整」。

**页面结构。** 页头下一句结论，下一行都带「兑付覆盖率 X，红线 Y」。结论按先后取一条：有修改结果未确认（「N 项修改结果没确认，确认前这页暂停修改」或「1 项放宽结果没确认，确认前暂停放宽，收紧照常」）；覆盖率低于红线或读不到可靠结果（红色「放宽已暂停」，收紧不受影响）；用户一个网络都用不了（「用户现在不能发起 USDT 提现」，第二行写原因和下一步）；有放宽等批准；都没有时写现状，只有审批列表读到、网络实际状态读到、提现开关开着且没有网络被挡时才说「没有要处理的事」。结论没说到的「用户不能提现」「放宽等批准」「审批状态读不到」另起一条提示。下面两组配置行，每行名称、问号说明（这是什么、什么时候生效、显示位置、改了会怎样）、当前值和「调整」：

- 「额度和时效」：每日提现次数、余额可提上限、小额免审线、到账时效。
- 「网络和费用」：TRC20 / BEP20 / ERC20 提现各一行，网络确认费（三个网络一个值，用「、」隔开），UVT 抵扣率。
- 「随运营阶段变化的设置」折叠，只读：当前运营阶段、到账审查窗口、加强合规审查，带「去运营阶段设置」。
- 页底相关页面：资金储备与应付款、资金与应付款总览、提现审核、操作记录与审批、用户行为事件，进不去的不显示。

**提现网络每行写实际状态。** 这页关着写「关闭」；开着时，读到能用写「开启 · 用户能用」，被挡写「开启 · 用户现在用不了」并写原因，读不到实际状态写灰色「开启」。用户能不能用和 App 提现同一个判断：「紧急停用开关」的提现开关开着、这页开着、出款服务接通；接打款服务时还要全局出款总闸开着、打款服务开通了这个网络、最近完成过完整对账、没有没处理的资金风险。网络本身状态来自后端 `networkStatus` / `effectiveNetworks`；提现开关 D5 接口不返回，页面另读紧急停用开关告警快照（`/api/admin/emergency/kill-switches/alerts`）。提现开关关着时开着的网络都写「用户现在用不了」，原因是提现开关；提现开关读不到时写「用户能不能用：—」，不猜。三个网络都在这页关着时结论句下一行写「要恢复，在网络和费用里点那个网络的「调整」开启，开启要审批」。打款方模式下打款服务没开通的网络（如 TRC20），这里开着 App 也不显示。

关掉网络：用户不能再用这个网络发起提现；接打款服务时，这个网络上已提交、还没交给打款服务的提现也暂停打款，已交给打款服务的继续查询核对。关掉最后开着的网络时，确认框写「提交后三个网络都关着，用户不能发起 USDT 提现」。

**整组「调整」抽屉。** 点任一行「调整」打开这一组的右侧抽屉：额度和时效四项一起提交，三个提现网络一起提交，三个网络确认费一起保存（可「恢复默认」，只回填，默认值比现在低算放宽），UVT 抵扣率单独一项。每项下面写现在的值、范围和改成后会怎样，空着或超范围时错误写全范围。底部写「已改 n 项」，含放宽时标「含放宽」「批准后生效」，全部收紧时标「立即生效」。抽屉有改动时关闭或点「刷新」都先问，刷新的选项是「放弃改动并刷新」。最终确认框写改了哪几项的前后值，理由必填。

**放宽提交审批，收紧立即生效。** 放宽指：调高每日次数、小额免审线、余额可提上限或 UVT 抵扣率，缩短到账时效，开启任一网络，调低任一网络确认费。一组里有一项放宽，整组提交审批，另一位超级管理员批准后生效，发起人不能批自己的单，批准前当前值不变；提交和批准时各查一次兑付覆盖率，低于红线或读不到可靠结果都被拒。全部收紧时提交后立即生效，不查覆盖率。放宽被挡（没有发起审批的权限、上一次放宽结果没确认、已有放宽等批准、覆盖率不够）时，抽屉里写原因；这一组已经是最紧的值时「调整」直接禁用。有放宽等批准时提交收紧，确认框提示「有放宽在等批准，收紧后那张审批单要重新发起」。修改权按字段分：每日次数、小额免审线、到账时效要 `finance_d5_daily_limit_write`，余额可提上限要 `finance_d5_balance_max_write`，提现网络、网络确认费、UVT 抵扣率要 `finance_d5_fee_write`；放宽另要发起审批权。

**结果未知。** 提交前把命令号、改动值和理由存在浏览器里，存不下就不发。收紧和放宽的结果没确认时都常显在页面上方，写发出时间和内容，读取失败时也在。
- 收紧结果未知（含 2xx 但读不出数据）：确认前这页所有「调整」暂停；只能「按原操作重试」，同一命令号、同内容、同理由，要有原命令里每个字段的修改权。
- 放宽结果未知：只暂停放宽，收紧照常。有操作记录读权或发起审批权的账号先「查询原操作」查原审批单，查到就回读；明确查不到才能按原操作重试；两种权限都没有的直接重试原内容，已提交的不会重复提交。只有 `A2_PROPOSAL_NOT_FOUND` 算查不到，其他读取失败按结果仍未确认。
- 只有后端明确拒绝了重试（4xx 带业务码），才出现「解除待确认」；本地出错、网络错、结果还是未知都保留原操作。解除只放开本页的锁，不发请求，不写操作记录。
- 超过 24 小时不能再按原操作重试，记录和锁都留着，到操作记录与审批核对。

**确认框覆盖率行。** 放宽的确认框写「兑付覆盖率 X，红线 Y」，两个数都一位小数，后果和检查说明放进提示图标；低于红线时换成红色全文「… 兑付覆盖率 X，低于红线 Y，提交会被拒绝」。

到账审查窗口、加强合规审查、小额免审线和到账时效的实际生效规则，写在 PRD v1 D5「现行参数口径」。

**待后端。** D5 读接口直接带提现总开关（现在两次读取之间可能短暂不一致，点「刷新」对齐）；财务主管读待批审批（BE-RBAC）未交付，财务主管看不到有没有放宽在等批准，按命令号能查自己发起的原审批单。

页面实际网络与 App `/api/withdrawals/policy` 同源：D5 开关、全局出款总闸、服务商币种、RPC、风控与对账均满足才可用。TRC20 也必须满足项目实际收付权限及独立 TRON 节点要求，配置缺失或未启用仍按真实原因显示不可用。页面不把「D5 配置开启」宣称为 App 已可提现。

TEST 自动完整对账周期为 5 分钟（`NEXION_CREGIS_FULL_RECONCILE_MS=300000`，上一轮结束后计时）；每轮核验到约 5 分钟前。最近成功与对账进度的 15 分钟安全门槛、成功后新失败的暂停条件均保持不变，避免原 15 分钟周期造成的约 5 分钟固定空档。真实对账或其他安全条件不满足时仍按实际原因显示不可用。此项是运行参数修正，不改 D5 页面、网络运营开关或审批流程。

## D5：加强合规审查与大额审查窗口（2026-11-08）

按本轮确认的关闭/开启效果图及 TRC20 增量，右侧「随运营阶段变化的设置」依次显示当前运营阶段、加强合规审查、分网络审查窗口、当前执行规则。复用现有参数行、虚线和间距，标题 13.5px、说明 12px、值 15px；保留 H1 读取权限控制的只读跳转，不增加开关或修改入口。左侧业务配置、审批与版本流程保持原样。

顶部小额免审卡说明为「低风险时按各网络规则判断免审」；左侧绿色提示明确「新提现按网络规则和风控结果审核；BEP20/ERC20 开启加强审查后须人工复核。TRC20 每笔仍须满足阶段窗口。到账截止时间按配置计算，链上确认后才显示到账。」右侧加强审查说明仅对 BEP20/ERC20 暂停小额免审，TRC20 按原免审与风控判断；当前执行规则摘要为「按网络规则审核」，不对三网统称全部人工。字号、布局、参数和按钮保持原样。

以下大额窗口条件和加强审查开启后的人工复核要求仅适用于 BEP20/ERC20；TRC20 保留原小额免审与风控判断，不因该开关开启而全部强制人工。

| 当前加强审查 | BEP20/ERC20 提现的审核方式 | BEP20/ERC20 大额窗口 |
|---|---|---|
| 关闭 | 沿用小额免审及现有 K3/K4 风控 | 不附加 H1 等待，即使配置 N 大于 0 |
| 开启，金额 ≤ 服务端门槛 | 全部须人工复核，小额免审暂停适用 | 不附加 N 天 |
| 开启，金额 > 服务端门槛 | 全部须人工复核 | 附加服务端 N 天；N=0 不额外等待，仍须人工复核 |

TRC20 每笔提现按原提交时间加 H1 的 N 天计算阶段窗口，不受加强审查开关或 1,000 USDT 门槛限制；N=0 无额外阶段等待。小额免审只免人工，不免 TRC20 阶段等待；是否人工、延迟、冻结仍按原免审及 K3/K4 风控规则处理。窗口到期不自动解除其他风控，不等于批准、出款或到账。

原单使用提交时不可变的阶段 N 天快照，不按当前 H1 天数回退或追改历史单。原阶段窗口无法核实时停止审批与首次出款；原快照不完整时也停止并保留原单供核查，不把缺失记录当作 N=0 或已满足等待。D2 沿用既有错误提示位置，将 `TRC20_WINDOW_SNAPSHOT_UNAVAILABLE` 显示为原阶段窗口尚未核实、暂不能审批或出款，将 `TRC20_WINDOW_SNAPSHOT_INVALID` 显示为原阶段窗口快照不完整、需核查原单；不新增按钮、样式或回填历史窗口流程。

门槛来自 D5 `GET /api/admin/withdraw/limits` 的只读 `complianceReviewThresholdUsdt:number`（本轮服务端为 1,000 USDT），`sourceByField.complianceReviewThresholdUsdt='compliance-rule'`；`complianceHoldEnabled`、`cooldownDays` 继续来自 H1。PUT 回读相同契约。界面不写死 1,000 或效果图用于演示的 7 天，窗口天数始终呈现服务器实际值。N>0 显示 TRC20 每笔适用；N=0 显示无额外阶段等待。

开启时「当前执行规则」明确 BEP20/ERC20 全部人工、仅严格超过门槛的大额附加 N 天；TRC20 每笔阶段等待与原免审、风控判断分别说明，不贴全金额人工标签。到期或批准不代表到账，需要人工复核的仍须放行，链上确认后才显示到账。关闭合规不能解除已有风控冻结/延迟，也不能修改历史费用；BEP20/ERC20 使用同一合规规则，网络可用性仍分别核验。

旧接口同时未提供门槛和来源时，BEP20/ERC20 大额条件及执行规则显示待核实并提示刷新或到 H1 查看；H1 已提供的 N 天及 TRC20 阶段说明仍按权威值显示。不默认门槛或声称缺失的规则已核实。只缺一项、来源不符、非正数或非法值时沿用 D5 加载失败、清空旧值与重试。接口失败及版本冲突仍使用既有恢复路径。

验收实际打开 D5 并刷新，核对关闭、开启 N>0、开启 N=0、旧接口缺字段及异常恢复；检查权限受限者没有新增写入口，跳转仍受 `growth_h1_read` 控制。页面操作和独立设计评分另存验收证据，不以构建通过代替实景验收。

## D2：TRC20 供应商原单核对（2026-11-08）

三网沿用 Cregis 提现详情和原 CID 核对恢复。只有服务端明确允许恢复且本单 `source=provider` 时显示核对入口；核对只绑定、查询原单，不新建出款。供应商已接手的本单不提供通用放行、退款或重新发送操作；尚未取得本单供应商事实的处理中、已发送或异常订单也不显示通用退款动作。权限、原请求幂等键和未知结果恢复流程沿用既有实现，后端仍是最终执行边界。ERC20 丢失链上确认的原冻结及占额规则保持不变。

## App / H5 Lite 与业务影响

充值先读只读 `GET /api/deposits/policy`，不通过请求各网地址探测开关；只显示开放网，并从 policy 读取准确费用。选中后才申请地址，全部关闭或读取失败不默认申请 BEP20。库存不足仍允许显示该网的准备中状态。

提现及地址换绑只使用实际开放的提现网络；全部关闭时不能换绑或发送验证码。服务端申请、保存换绑、首次出款分别复核权限，成功幂等回放和已发出原单查询继续可用。外部 USDT 下单及付款履约受选定网充值开关控制，余额购买沿用原流程。
