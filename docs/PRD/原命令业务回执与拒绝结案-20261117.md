## 回执合同

详细 GET、`by-command-key` 的列表项及调查 POST 都保留原身份、事务状态、锁和调查记录，增加 `businessCode: number | null`、`businessState`、`batch`。`receipt-status` 仍只返回 `{state}`，没有新增业务码、原因或完整回包。业务码是已存原响应的数值码，没有原因文字。

| businessState | 后端条件 | PC 分类及收尾 |
| --- | --- | --- |
| PROCESSING | 原事务 PROCESSING | PROCESSING，保留记录和保护，不人工中断 |
| FAILED | 原事务 FAILED | FAILED，保留；不等于未执行 |
| SUCCEEDED | 原 SUCCEEDED / CONFIRMED_SUCCEEDED 且原码 0 | 确定本次业务命令成功才解除并独立重读；下表集合结果例外 |

| UNKNOWN | 无法取得有效原码或其它事务状态 | 原SUCCEEDED且码为空时沿同一已核成功名单；其它UNRESOLVED，受控终态按各自证据收尾 |

`businessState` 缺失时仍用原四分类和精确成功名单：SUCCEEDED、NOT_EXECUTED、BUSINESS_RESULT_UNAVAILABLE、UNRESOLVED。新字段在现有网络接收边界校验一次，原 actor/method/path/key/hash、目标和锁校验不变。查询失败、查无、过期、换账号及当前值相同不构成解除依据。

新后端对没有 `code` 的原生回包给 UNKNOWN，例如 A2 原票、I4 Document、用户支付/昵称 Map、D3 字节导出及A4 H3重投视图。协调人续单2明确：原状态SUCCEEDED、投影UNKNOWN、原码为空时，沿用旧后端那一份逐类核实过的successOnly名单，拒绝全部抛异常的依据不因投影字段出现而失效；名单之外仍未决。名单在代码只定义一处，两代后端共用，带0/非0码的投影不走此兜底。A4_EVENT_RETENTION_RUN不在名单，未取锁也会正常返回，查询不得自动结案。

## 拒绝和受控结案

`REJECTED` 只证明原回包拒绝本命令，不能说物理未执行或资金未动。`businessCode` 只有数字，不能匹配 `isExplicitRejection` 所需的原原因码及 `IDEMPOTENCY_*`、归属未明、J4 partial、精确 403/503 例外；不伪造 reasonCode 来调用该函数。查询到未受控拒绝保留记录，两条出路：24 小时内原请求原号重放取得完整原拒绝原因，再按现有明确拒绝判据处理；或有调查权的人按原记录结案为 REJECTED。两路使用同一证据原则，不能因仅数字码就把 J4 partial 清掉；重放的完整拒绝原因比纯投影多，能明确拒绝的旧流程保持。

`fundCommandCanConcludeRejected` / `eCommandCanConcludeRejected` 只在原 SUCCEEDED、业务 REJECTED、有效非零原码时为 true，供 `closureKnown` 同一套表单按真实资格提供 REJECTED。旧后端缺字段、FAILED、PROCESSING、未知或无有效码都不给这个结论，提交函数同样检查，不把必退回的 REJECTED 发出去。后端最终重新锁原记录并取原响应判定；不成立为 409 INVESTIGATION_KNOWN_RESULT_CONFLICT，处理中为 409 INVESTIGATION_COMMAND_STILL_PROCESSING。

受控结案写入 investigation.conclusion=REJECTED、evidenceType=ORIGINAL_BUSINESS_REJECTION:{code}、factType=ADMIN_RECEIPT，原状态变 CONFIRMED_REJECTED；locked=false，newOperationAllowed=false。前端识别该终态并清原记录/原对象保护，重读当前状态；不会标成成功或未执行，不自动授予补偿、支付或新审批资格，原请求不可再次重跑。

成功审计也可把原存储非0回包的命令结案为CONFIRMED_SUCCEEDED。receiptState仍读取原响应，投影REJECTED并保留原非0码；这不是非法组合，接收边界必须接受，分类按受控成功结束原记录，不能因原业务投影仍被拒而把已结案命令卡住。不修改原回包、不把原非0伪造成0；身份、锁和证据关联继续校验。

## 状态查询、D2 完整性和界面交接

没有类型族的 scope 仍须 supported 且 `AdminCommandOrigin.readAuthority(scope)` 非空，调用者须持该读权且匹配 stored origin_admin_id；旧无原人或非本人返回 UNKNOWN，查无返回 NOT_FOUND。A2/L/F_TEAM/A3/E3 的逐条绑定可能没有 scope 级读权，仍会 422，不能宣称所有动态范围都可用最小状态接口。typed A1/A6/A7/F4 分支不变：A6/A7/A1 权限登记仍依赖成功审计证明原人，被拒但没有成功审计仍 UNKNOWN；A1 账号/头像、F4 材料可从精确 scope 核原人。前端没有把 RECEIPT_SCOPE_INVALID 特判为可解锁；所有现行调用仍保守。D5–D7 新详细回执含业务字段时省掉第二次状态 GET，旧后端仍查两次。

F4材料最小状态REJECTED只说明拒绝，不能区分原拒绝与受控拒绝，也不证明未执行，因此与详细查询的原拒绝一样不给自动结案outcome。详细CONFIRMED_REJECTED仍按受控结论结束。最小SUCCEEDED及旧端无详细投影时的其它回退路径保持，页面按完整不可变材料历史证明未执行的既有分支未改；新增原拒绝本身不构成该历史证明。最小接口不带后端版本，不据同名REJECTED猜版本或制造兼容特例。

D2 数据投影是 `accepted:string[] / rejected:string[] / conflicts:{withdrawalId,reason}[]`。`rejected` 是大额转人工，不是命令整体被拒；冲突保留原 reason，不改写成业务未执行的资金保证。接收边界核三列表及不重复 ID，页面再核保存的原目标集合恰好被完整覆盖才解除整批；全部冲突也属已知逐笔结果。新回执即使已经 CONFIRMED_SUCCEEDED，仍核完整逐笔结果；旧后端的既有受控终态不变。投影没有 batchId 和顶层大额原因，不编造这些字段填旧回包结果框。缺项、额外项、重复、坏体、未知或失败继续保留。

本项只接数据和现有句子的分支，未新增产品句子/表单选项/组件。原拒绝暂落现有「已处理」；受控拒绝与批次收尾暂用现有「已有结论」「刷新页面查看现在的结果。」而非已执行/未执行。视觉需补 REJECTED 独立标签、正确的原因/副作用边界、仅按资格出现的结案选项、拒绝结案后的说明，以及 D2 逐笔投影展示。共享 CLOSURE_KNOWN 旧句「操作记录里没有这次成功记录的，现在结不了案」在新拒绝范围已过时，须视觉改写；本项不把它登记成新的后端事实。
