## 并行执行

每设备同一时刻最多一个工作流，不同设备可以同时执行。fleet 使用有界任务线程池、公平按到期时间补位；发现、健康检查独立推进。任务取消、失权、停用或 generation 改变仍阻止后续经济请求；关闭时先停止派发、等待在途退出，再释放持久 journal 与文件锁，保持原任务恢复和 UNKNOWN 不重放规则。

TEST fleet 当前上限为 2。Ollama 0.33.3 对向量模型固定单路，故采用 11436/11437 两个相同镜像、模型摘要的独立 runner。完整前摘要校验、真实推理、后摘要校验期间独占一个 runner，异常后归还；实际 HTTP 多并行缺少足量、不同的 loopback 端点时拒绝启动。11435 继续供 1202 single 和后端独立校验使用；fleet 仍排除 1152/1202。不得用多个 RUNNING、重叠 HTTP 排队或伪造进度代替真实推理重叠。

执行器按 60 秒周期轮询下一项。完成后至下一次轮询可短暂等待派单，合法供给或生命周期限制也可能产生等待；这不属于金额阈值产生的冷却，不承诺任意时刻每台设备都有运行中任务。

任务输入、模型摘要、raw 输出、设备实例、任务号、执行身份和回执仍独立绑定，后端校验通过后才在原事务唯一结算。按账号的必要金融锁不因并行而移除；每日 UVT 去重和六个物理槽规则保持不变。

## 并行资金快照与明确回滚恢复

实际并行验收暴露了旧资金读取缺陷：事务在等待账号锁前建立的 RR 快照，会使单笔结算的 before 钱包值落后于上一设备刚提交的余额。资金 Adapter 的钱包快照须使用 `FOR UPDATE` 当前读，不改变事务隔离或放宽金额差额、revision 与证据守恒断言。此异常必须整笔回滚，不得保留半份收益。

通用错误或网络未知不能因“未查到回执”就重放。对本次新出现、已停止执行器并归档完整请求集合的两笔失败，只有完成服务端异常调用链、事务回滚、后端重启清除在途请求及锁定零金融证据的独立裁定后，才能按原任务和原请求哈希形成明确的 SYSTEM 恢复审计。裁定方式须如实标记为完整两请求集合的对应，不伪称逐笔日志关联。只读恢复审查接口还须核验固定两台实例、原 NEXT/COMPLETE key 哈希、原输入/结果/nonce 摘要与当前合法绑定；持久的一次预算花费后沿原 manifest 重算并回传，不改旧 UNKNOWN calls。重启或再次未知只读核对回执，不能再次花费预算。1152 的旧 UNKNOWN 不属于该裁定范围。
