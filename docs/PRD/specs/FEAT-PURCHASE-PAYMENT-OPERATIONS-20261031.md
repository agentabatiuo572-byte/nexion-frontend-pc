# D1 订单直付费用与异常核验

2026-10-31 实施合同；本地候选和 fixture 通过不代表 TEST 实景或支付商真实验收。

D1 `/finance/recon` 既有页面内增加订单直付区域，不增加独立客户 360 页面或一级菜单。钱包余额付款保持原支付密码规则，渠道费与网络费固定为零；HDPay 银行直付和 USDT-BSC / ERC20 链上直付不要求支付密码，不受其锁定影响。HDPay 支付商托管付款页面保持原交互。

D1 使用既有后台分段控件切换「订单付款 / 银行卡充值 / USDT 充值 / 充值流水与对账」，各业务长表只在对应分区展示。切换保留已加载的筛选、分页与未保存费用草稿。订单付款区保留钱包零费与支付密码说明；费用先按「银行卡 / USDT」切换，USDT 再按 BEP20 / ERC20 切换，每次只展示当前外部渠道的费用行。渠道列表以权威响应为准，旧版两渠道响应不虚构 ERC20。跨渠道草稿按渠道标识保存，显示本次待保存渠道；保存仍提交全部已修改且有效的渠道，不因当前可见页签改变提交集合。「修改历史」与「刷新」位于同一工具栏，历史、未知操作审计及付款详情审计入口统一采用后台按钮样式，进入原 D 域操作审计。

业务分区上方持续展示当前操作员的未保存费用渠道数、订单付款、银行卡充值及 USDT 操作未决数；USDT 读取或操作出现实际错误时显示需要查看的提醒，不把正常未配置或地址池业务告警当作未知命令。切换分区不得遮蔽这些提醒，可通过原样式按钮返回对应分区查看、撤销或按原命令恢复，不阻止正常切换。登录身份或权限周期变化时重新建立本页工作区，清除旧身份的临时草稿与提醒摘要；持久未决命令仍按原归属与恢复规则处理。

USDT 共同充值规则的 A2 提案单独按当前操作员统计：尚未取得提案号且非终态时显示「提案结果待核对」；已取得提案号但未终结时显示「提案待审批或处理」，不得称为未知提交。已知 approved / rejected / withdrawn / expired 终态不计为未决，原核对完成入口仍保留。提醒明确引导至「USDT 充值 → 充值与地址设置」查询原提案或按既有期限使用原请求重试。

费用及最低充值额配置区读取 `/api/admin/finance/purchase-payment-policy` 权威值与版本。渠道为 `HDPAY_BANK`、`CREGIS_USDT_BSC`、`CREGIS_USDT_ERC20`；渠道费为本金乘百分比再加固定费，BSC 与 ERC20 分别收取报价中的网络确认费，HDPay 网络费必须为零。费率范围 0–100%，固定费和网络费非负，最多两位小数。钱包零费说明只读。读取失败不显示默认费率，不允许保存。

每个外部渠道必须返回 `configured`。未配置时三个费用字段为 null，生效费用显示“—（未配置）”，编辑框留空，直付报价与新付款单不可创建；不得把迁移或历史默认零费用作为已配置。运营必须明确填写费率、固定费及各链网络费，明确保存全 0 可以表示免费。每次只提交已修改且完整填写的 1–3 个渠道，保存 HDPay 不会顺带启用尚未配置的其他渠道。HDPay 固定不收网络费。最低充值本金继续取原权威值，费用未配置不阻断既有充值规则或原付款单恢复。

费用 `configured` 仅为开放条件之一；保存确认应说明费用配置生效，实际能否付款仍取决于通道、收款地址及其他运行条件是否可用，不承诺费用保存后即可收款。

编辑范围来自同一接口的 `constraints.ratePct`、`constraints.feeUsdt`、`constraints.minTopupPrincipal`。缺失或不完整时只读；前端按服务端范围验证并展示边界，不自行扩大可写范围。当前后端范围为费率 0–100%、单项费用 0–1000000 USDT、最低充值本金 1–1000000000 的整数。

最低充值本金按渠道配置，必须为正整数，界面显示两位小数、编辑不接受小数；HDPay 以 USD / USDT 本金计，BSC / ERC20 以 USDT 计。订单直付本金和费用允许小数，不受充值最低额限制。HDPay 最低额通过此权威配置调整，旧通道配置卡不再暴露另一个 HDPay/VietQR 最低额写入口。BSC / ERC20 共用 Cregis 最低额，仅在此只读展示，仍须在既有 Cregis 充值规则提交 A2 提案并由另一位有权限管理员批准，不新增旁路。

规则读取要求 `finance_d1_read`，写要求 `finance_d1_fx_manage`。保存前展示前后值、原版本与生效范围，填写理由并确认；调用 PATCH 时带 `expectedVersion` 和 `Idempotency-Key`。新规则仅影响之后创建的报价，既有付款单保留报价费用快照。前端遵循既有 A2 理由策略并取接口约束交集，后端仍独立验证。成功以服务端返回及重新读取的配置为准；操作记录在既有审计入口查询，页面不把配置读回冒充独立审计回执。

订单付款记录支持状态、渠道、分页与详情。状态分别为创建中、创建结果未知、等待付款、已核实资金待交付、业务已交付、人工核查、过期。详情展示用户、业务、渠道、本金、用户渠道费和网络费、实付总额、费用版本、付款单版本、支付商单号、支付商实际费用及异常原因；支付商实际费用缺失显示“尚未提供”，不得按用户收费推算。收到资金与业务交付分别表达，处理中与人工核查不得显示购买成功。

付款记录的「状态 / 付款方式」筛选沿用后台既有 12px 标签与共享下拉控件样式，统一间距、边框和圆角；窄内容区按完整筛选项换行，与记录标题、刷新和分页保持协调。选择状态或付款方式仍按原条件查询并回到第一页，刷新保留筛选条件。

时间统一按后台业务时区转换并标注时区，不把 UTC 字面值直接作为本地时间。原业务交付事实取服务端 `fulfilmentStatus`，已交付后新增到款或链重组异常仍明确“原业务已交付，资金异常待核查”，禁止再次交付，并保留具体异常原因；保留原业务回执与逐笔链上凭证（txid、日志索引、原始精确金额、区块、确认数、核验状态）。支付商实际费用和链上凭证保留服务端精确小数，不套用配置费率的两位小数输入约束。

`finance_d1_bank_reconcile` 可在原付款单详情填写理由并确认“重新核验并尝试交付”。请求仅发送原付款单、原版本、理由与唯一命令号；后端重新查询原支付商身份或链上凭证，重新检查当前购买、资格、库存及六槽位约束。CAS 变化拒绝原状态覆盖。短付、超付、迟到及业务条件不满足继续留待人工核查。不存在强制成功、另建收款、自动退款或转钱包余额入口，返回人工核查也不宣称交付成功。

保存及人工核验都先持久化当前操作员、原对象、原请求内容与命令号。超时、坏包、身份切换或未知返回保留记录，刷新不能铸新号；新操作被阻止。可读取当前权威状态，但当前值不能单独证明原命令结果。首次提交后 10 分钟内可用原请求和原命令号重试；超时或时钟异常后保留记录并引导既有操作审计核查，不提供“清掉记录重试”按钮。同一操作员恢复可见，另一操作员不得重放原命令。后端仍须独立鉴权、幂等、CAS 和审计。

验收覆盖：有权与无权、权威配置失败、整数字段和费用小数边界、HDPay 零网络费、Cregis 最低额只读及原审批、旧付款费用快照、配置版本冲突、结果未知跨刷新同号重试、原付款单人工核验、持续人工核查且无虚假成功。真实 TEST 页面与外部资金链路需另行验收，不使用真实资金或外部短信构造测试。

付款详情同时展示原六位业务金额、两位收款本金及舍入差额；银行卡显示冻结的真实 VND 汇率和整数盾应付，按整数字符串精确格式化，不经过 Number 损失精度。BSC 单列说明外部 BNB Gas、ERC20 说明外部 ETH Gas 不计入平台总额。缺失快照显示尚未提供，不补 0。

ERC20 接入与钱包充值/订单直付分账规则见 [USDT ERC20 接入](FEAT-USDT-ERC20-INTEGRATION-20261031.md)。新增 ERC20 默认费用未配置，不自动打开资金能力。
