# 激活设备连续派单与页面刷新

2026-10-31 Asia/Tokyo。依据用户对“暂无进行中作业，等待新作业”的反馈及连续自动接单要求，仅用于 TEST/test。本专题补充[全设备统一六槽与按激活实例数并行](UVEL_全设备统一六槽与按激活数并行_TEST_20261030.md)，覆盖旧 Online、taskLock 及主 PRD 中“任务完成后按60秒周期领取下一项”的描述；旧运行采样保留为历史证据。

## 连续派单规则

1. 合法有效激活设备自动接单执行，无需用户或运维再次开启。只有当前任务取得身份、产物哈希及原任务关联均通过校验的正回执，完成本地持久确认后，才允许进入下一任务调度；HTTP 200、预计进度100%、RUNNING 或推理返回都不等于完成正回执。
2. single 在正常完成或恢复取得正回执后，跳过本次 poll 等待，回到下一轮并重新核验当前执行资格；fleet 将该实例 `due` 设为当前单调时钟时间，沿原约1秒调度节拍在下一调度轮重新判断资格与接单。正常完成、服务端确认已完成及原任务正回执恢复均遵守此规则；恢复当次仅收口原任务，不在同一恢复调用中额外领取新任务。
3. `UVEL_CLOUD_POLL_SECONDS=60` 保留用于设备发现、空队列及既有失败/不可确定分支的等待或退避，不再作为成功任务完成后的固定冷却。空队列、可证明未发送的 NEXT_NOT_SENT、异常及尚未确认结果均保持原等待与原键恢复规则；没有有效任务供给时允许真实空闲，不承诺任意时刻每台设备都有运行中任务。
4. 每次新接单继续核验当前身份、归属、有效激活、pending停用、健康、generation、取消与全局 STOP。N台有效激活设备仍提供N路真实推理，每台最多一个工作流；线程池、runner独占、实例互斥、journal与文件锁不放宽。单账号最多六槽，负责多账号的执行器按总有效N提供容量。
5. UNKNOWN完成请求仍只读对账，负回执不授权第二次 complete 或新 next。旧1152隔离及既有逐笔恢复预算不变；本次缩短成功后的调度间隔不新增恢复授权，不改 eligibility、报价、输入/模型/产物绑定、唯一回执或账本事务。

## 页面只读刷新

- App/H5 首页与赚取页可见时，现有共享任务读取约每2秒请求 `GET /api/tasks/assignments`，使用1秒请求缓存与同范围在途合并；卡片折叠不会停止此读取。手机运行上报与设备/Home汇总保持各自原有节奏，不由任务展示轮询驱动派单或结算。本轮没有 App 产品代码变更。
- 离开相关页面或进入后台停止其可见任务读取；返回立即读回。账号、同账号重绑、前后台及运行版本代际变化后的晚响应不得覆盖新快照；慢fleet读取不得覆盖已确认的较新任务投影。
- 卡片只显示当前设备的真实任务、最近完成与已结算收益。读取错误或未知不当作成功的空闲；预计时长到点仅等待执行结果确认，不本地完成任务、造进度或发收益。
- 两秒是读取启动节流，并非服务端推送或固定显示时限。短于采样间隔的任务可能完整落在两次读取之间；网络、在途请求及运行上报等待也可能使瞬态任务未被画面捕获。验收应关联同一device/task、真实执行时间线、任务投影与完成收据，不能只凭某次空卡或未拍到RUNNING判断未执行。

## 退出前置检查异常与严格本地分类

本轮发布退出验证发现旧worker的既有竞态：经济请求的STOP前置检查在持久 `intent` 之前抛普通 `Halt`，外层将1209误记为 `UNKNOWN_NEXT`。主负责人已保存原state SHA256（前缀`6ca362`）及原nextKey SHA256（前缀`8bd1ea`）的现场证据：原key在 `calls` 中任意operation记录均为0，后端活跃任务为0，原SQLite以root权限0600封存；先恢复旧服务，未手工改写原journal。后端active=0仅为佐证，不能独立授权重发。

最终源码对未来STOP前置中止显式使用 `NotSent`，沿既有NEXT未发送路径保存原key为 `NEXT_NOT_SENT`。对既有误分类，只允许原 `Journal.classify_unsent_next` 在原文件锁及事务下作以下本地原子分类，不发HTTP、不结算，也不清空历史：

1. 原state的键集合必须精确为 `{phase, binding, nextKey}`，phase为 `UNKNOWN_NEXT`；额外task、input、result或预算字段均不接受。
2. binding必须为dict，键集合与当前配置完全一致，各字段类型和值均一致；不得用Python宽松数值相等接受整数与浮点、布尔等同值异型。nextKey必须是合法原NEXT key，保持同一key，不生成替代key。
3. 按原key查询 `calls` 的全部operation，必须完全零记录。满足条件时，同一事务插入 `operation=NEXT_PREINTENT_RECOVERY`、`outcome=NOT_SENT` 的本地审计marker，`request_hash` 为原state规范JSON的SHA256，再将state转为同key的 `NEXT_NOT_SENT`；任一步失败整笔回滚。
4. `Worker.recover` 使用该分类；`Fleet.restore` 必须先校验自身hash目录、当前binding及exclusion，再在计算隔离状态前调用。分类本身没有HTTP，fleet仍等待正常discovery、资格、健康、STOP与容量门；不将真实UNKNOWN加入ready/reconcile集合，不清除现有隔离、generation或停止标记。
5. 任意既有calls（包括INTENT、UNKNOWN、CONFIRMED、REJECTED或NOT_SENT）、字段/类型/绑定/key不符、来源不明或真实已发送UNKNOWN均继续隔离。只有原持久“先FULL提交intent、再进入HTTP”的不变量与严格零calls证据共同证明未发送；不能由task=null、active=0或没有回执倒推。旧1152及四份既有逐笔恢复预算原样保护，此分类不增加这些预算或任何完成重放授权。

部署后的现场证据确认：原journal由代码产生一条 `NEXT_PREINTENT_RECOVERY/NOT_SENT` marker，其hash与原state一致，随后同原key仅一条 `NEXT/CONFIRMED`；后端nextKeyHash唯一绑定1209/fleet-1209的已完成任务 `CTA-19BCCF53BC664FA3ADD5C86CE986172F`，纳入下述93笔严格核验。没有人工改journal或生成任务/账本。最终独立证据复核已确认原key唯一性及关联，旧1152和四份既有恢复预算/calls保护比对通过。
