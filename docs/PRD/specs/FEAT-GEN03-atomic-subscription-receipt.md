# FEAT-GEN03 · 创世节点认购回执与即时一致性

> 状态：CURRENT / server-canonical  
> 生效日期：2026-08-28  
> 适用范围：Java 后端、5173 UniApp、钱包账单、创世订单

## 1. 用户可见结果

创世一级认购由同一个服务端事务完成余额扣减、资金流水、认购订单和持有席位。成功响应是该事务已经提交的权威回执，必须同时返回最新余额、已售/余量、当前账号订单和持有记录。5173 收到成功响应后立即更新这四类事实，不等待第二次查询，也不再显示“席位锁定成功”这种尚待结算的中间态。

认购成功提示统一为“余额、订单与创世席位已同步”。刷新只用于重新读取权威事实，不是扣款或生成订单的触发条件。

## 2. 失败原因必须区分

| 结果 | 前端提示 | 资金与订单口径 |
|---|---|---|
| `GENESIS_WALLET_INSUFFICIENT` | USDT 余额不足，并展示应付额与当前余额 | 明确拒单；不得新增扣款、流水、订单或席位 |
| `GENESIS_USER_CAP_REACHED` | 已达到单账户上限 | 明确拒单；不得写入业务事实 |
| 账户龄、国家/地区、地域禁售等资格拒绝 | 需要认购资格，并引导查看服务端原因 | 明确拒单；不得写入业务事实 |
| `GENESIS_MARKET_PAUSED` / `GENESIS_SOLD_OUT` | 市场关闭 / 已售罄 | 明确拒单；不得写入业务事实 |
| `GENESIS_SANDBOX_USER_RUN_CONFLICT` | 当前验收场次不一致 | 明确拒单；不得跨 RunID 读取或写入 |
| 网络中断、超时或未知协议错误 | 认购结果暂未确认，先刷新余额和订单 | 结果未知；保留同一幂等键，禁止直接换键重买 |

“连不上服务器”只能在客户端确实能够证明连接失败时使用；不得把余额不足、资格不符、RunID 冲突等服务端业务拒绝翻译成服务器离线。未知结果也不得宣称“余额分文未动”，因为服务端可能已经提交而响应在途中丢失。

## 3. 回执与重读规则

1. 客户端在发请求前持久化账号范围的认购意图幂等键；未知结果的重试沿用原键。
2. 服务端在事务内锁定库存与钱包，完成扣款、订单、持有和流水后才返回成功。
3. 客户端先校验账号与 RunID 围栏，再原子投影成功回执中的余额、库存、订单和持有事实。
4. 成功回执之后不阻塞等待账号态重读；后续重读失败不得清除刚确认的订单或把成功降级成失败。
5. 本地清理 pending 幂等键失败属于客户端存储维护失败，不得推翻已提交的服务端结果。
6. 钱包 store 必须使用自身账号 epoch 校验回执，不能复用另一个 store 的独立计数器。

## 4. 时间契约

数据库 `LocalDateTime` 按业务时区 `Asia/Shanghai` 解释。创世订单、持有、挂单、排放记录和钱包流水对 App 输出时必须转换为带 `Z` 或明确偏移量的 ISO-8601 时间；客户端拒绝无时区时间字符串。

示例：数据库 `2026-08-28 11:10:12` 表示上海时间，对外返回 `2026-08-28T03:10:12Z`。东京设备显示为本地 `12:10:12`，而不是把数据库墙上时间误当 UTC 后显示成 `20:10:12`。

## 5. 与资格配置的区别

本规格只约束认购事务完成后的回执、错误分流和时间展示，不新增或修改资格来源。资格仍唯一使用 FEAT-GEN02 的三项服务端配置 `eligibility.enabled / maxPerUser / minAccountAgeDays`，成交事务继续复核国家/地区、销售窗口、市场与库存。

## 6. 验收

1. 余额充足的受控账号认购后，不刷新页面即可同时看到余额减少、已售数增加、余量减少、订单和持有新增。
2. 成功响应后的补充读取被模拟为失败时，上述已确认事实仍保留，页面仍显示成功。
3. 余额不足再次点击时显示“USDT 余额不足”，并证明钱包余额、资金流水、订单和持有数均无变化。
4. 钱包流水与创世订单代表同一成交时，在不同时区设备上展示为同一时刻。
5. 服务端所有创世与钱包时间字段均带时区；无时区响应被客户端失败关闭。
