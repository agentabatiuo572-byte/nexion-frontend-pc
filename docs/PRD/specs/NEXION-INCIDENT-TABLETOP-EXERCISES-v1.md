# NEXION 故障桌面演练包 v1

> **现行裁决(2026-08-07)**:全项目已取消 KYC、钱包配对、C4 与 K5；本文相关旧字段、门禁、用例、权限或流程仅保留为历史基线，不得作为现行实现、运营或验收依据。

> 文档状态：可直接主持的演练基线  
> 性质：桌面推演，不执行生产删除、转账、密钥轮换、Kill-Switch 或真实用户通知。需要技术实操时必须另建隔离演练 Run ID。  
> 目标：验证人、流程、证据与决策闭环；不是考记忆，也不是证明系统没有缺陷。

## 1. 统一演练规则

### 1.1 角色

| 角色 | 责任 |
|---|---|
| Facilitator | 只按时间释放 inject，控制节奏，不替团队回答 |
| Incident Commander（IC） | 定级、目标、分工、决策日志、交接与结束 |
| Tech Lead | 影响面、止损、恢复、数据核对、技术证据 |
| Product/Operations | 用户影响、功能边界、业务优先级、恢复验收 |
| Security/Privacy | 账号/数据/取证、泄露评估、通知触发 |
| Finance/Risk | 资产冻结/对账、风险控制、补偿建议 |
| Legal/Compliance | 市场/监管/商店/合同通知判断，不由研发代签 |
| Support/Comms | 工单合并、用户话术、状态更新、双语/三语一致 |
| Observer/Scribe | 记录事实、假设、决定、时间、缺口与评分，不参与指挥 |

一个人可兼任多个角色，但 IC 与 Scribe 不应为同一人；资产或恢复高风险服务的批准不得由单人自批。

### 1.2 每次演练材料

- 精确候选/架构图、值班表、SOP、供应商通讯录、参数/Kill-Switch 目录、数据/声明/市场矩阵。
- 一份空白事件日志：`time / fact / hypothesis / decision / owner / due / evidence / reversal`。
- 模拟 dashboard、工单、日志、账本/订单摘要和供应商消息；所有数据明确标 `EXERCISE`。
- 禁止提前把 inject 或标准答案发给参演者。

### 1.3 演练 Preflight 与中止条件

- 演练负责人批准精确 Exercise ID、隔离 Run ID、参与人、材料分级、开始/结束时间和保管位置；只使用模拟或不可逆脱敏数据。
- 禁止向演练环境、文档、录屏和聊天中放入生产写凭据、真实密钥、完整通讯录、用户 PII/附件或可直接操作生产的链接；敏感架构/参数只给需要角色，演练结束按分级归档或销毁。
- 参演者只能提出生产止损候选、授权链、验证与回退计划。任何真实 Kill-Switch、转账、密钥、数据或通知动作必须退出桌面演练，进入独立的正式事件/变更授权流程。
- 一旦发现真实事件、真实数据泄露、误触生产或证据可能被破坏，Facilitator 立即喊停，保全现状并移交真实 IC；不得继续以“演练”名义处置。

### 1.4 标准节奏（90 分钟）

1. 0–10 分钟：范围、安全说明、正常基线和角色确认。
2. 10–55 分钟：依次释放 inject；团队每次必须区分事实、假设和待验证项。
3. 55–70 分钟：恢复/沟通/补验方案与是否结束事件。
4. 70–90 分钟：无责复盘、评分、行动项、Owner 和截止触发点。

## 2. 评分表

| 维度 | 分值 | 满分表现 |
|---|---:|---|
| 发现与定级 | 15 | 依据用户/资产/数据/范围定级，及时纠正，不被单一指标误导 |
| 指挥与职责 | 10 | IC 明确、任务单一 Owner、交接和决策日志完整 |
| 止损 | 15 | 提出正确的止损候选、授权链与回退计划，不破坏查询/对账；桌面演练中不执行生产开关 |
| 事实与证据 | 15 | 服务端/账本/审计/供应商证据一致；结果未知不被猜成失败 |
| 恢复与验证 | 15 | 回滚/修复后完整业务验收、存量核对、无重复副作用 |
| 用户/外部沟通 | 10 | 不夸大、不隐瞒、不承诺无依据时限，多渠道一致 |
| 安全/隐私/法律 | 10 | 及时保全证据、识别通知/商店/合同触发，权限最小化 |
| 复盘与改进 | 10 | 行动项可验证、有 Owner/触发/优先级，更新 SOP/测试/监控 |

通过线：初审严格大于 96，复审严格大于 98。复审由未主持且未编写该次模拟数据的人，根据同一证据独立评分。演练未通过不是扣分表演；必须修订材料并重演失败环节及其前后链路。

硬性不通过：未经正式授权执行任何生产动作；把未知资金结果猜成失败/成功并据此重试；泄露秘密/PII；删除或覆盖证据；为审核、用户或监管隐瞒真实影响。触发后分数无效，立即按 1.3 转入正式处置。评分前由 Facilitator 与复审人用一个样例对齐 0/50/100 锚点：无证据或反向操作=0，识别但闭环不完整=50，事实、授权、执行边界、验证和记录齐备=100；任一安全/隐私/资产维度不得被其他高分抵消。

### 2.1 各维度 0/50/100 证据锚点

| 维度 | 0 分 | 50 分 | 100 分 |
|---|---|---|---|
| 发现与定级 | 无事实源或按猜测定级 | 识别主要影响但漏用户群/资产/数据之一 | 引用时间戳和版本，完整覆盖范围、最坏群体并可随证据纠正 |
| 指挥与职责 | 无 IC/Owner/日志 | 有分工但交接或批准链缺证 | IC、单一 Owner、授权、交接与决策日志均可复核 |
| 止损 | 直接生产操作或扩大损失 | 提出候选但缺影响/回退/授权 | 收紧方向、影响预览、授权链、回退与保留查询/对账齐备 |
| 事实与证据 | 猜测结果或破坏证据 | 找到部分来源但权威冲突未收口 | 账本/审计/供应商/用户态一致，未知结果保持未知并持续查询 |
| 恢复与验证 | 只宣布恢复 | 有定向验证但漏存量/跨域 | 完整入口、异常/并发/权限、存量对账和无重复副作用证据齐备 |
| 用户/外部沟通 | 隐瞒或无依据承诺 | 内容安全但渠道/人群/更新节奏不完整 | 事实、未知项、影响、行动和更新节奏清楚且多渠道一致 |
| 安全/隐私/法律 | 越权、泄密或漏掉硬触发 | 识别义务但通知/保全/最小权限未闭环 | 证据保全、最小权限、法务/监管/商店/合同触发及批准均记录 |
| 复盘与改进 | 无可验收行动项 | 有 Owner 但期限/证据/重演缺失 | 每项有优先级、触发/期限、关闭证据、文档更新与非 Owner 重演 |

评分按每维权重线性折算；只能在锚点之间依据可观察产物插值。缺原始证据的单维最高 50 分；没有阶段必交产物的相关维度最高 50 分；不得用其他维度加分抵消。初审与复审必须在报告中逐维引用证据路径和时间戳。

## 3. 演练脚本

### EX-01 重复提现与账本负余额

**目标**：验证结果未知、幂等、广播、账本和跨域止损。关联 THR-020/021/026/027/030。

| 时间 | Facilitator inject |
|---|---|
| T+0 | 3 名用户称同一提现单出现两个链交易；提现成功率 dashboard 正常。 |
| T+8 | 支付/节点供应商说 30 秒超时期间“可能已接收请求”，无法立即确认。 |
| T+15 | 查询发现 1 个用户 `balance_after < 0`，另 2 个仅 UI 重复显示。 |
| T+25 | 运营员提议直接将重复记录改为失败并恢复提现入口。 |
| T+35 | 第二节点显示其中一笔处于 reorg 风险；客服已收到 60 个相似工单。 |
| T+45 | 财务发现同一幂等意图被两个 worker 使用了不同供应商 reference。 |

关键决策：先关哪条写路径、是否保留查询/对账、如何防再次广播、按用户/链/版本核对、何时通知。  
成功标准：不盲目重试/改状态；资产范围可复算；两笔链交易及全部账本事实不可变保留并关联到同一提现意图，最终形成一个可审计的用户资金结论；多付、未确认或重组分别进入批准的追回、补偿、冲正或持续观察方案；恢复需经过完整对账和审批。

### EX-02 支付回调伪造与奖励已发放

**目标**：验证 Webhook、订单、奖励/等级、退款/负向事件。关联 THR-019/023/027/028。

| 时间 | inject |
|---|---|
| T+0 | 反作弊告警显示 40 个新账号在一分钟内支付成功并领取邀请奖励。 |
| T+10 | `signature_status=FAILED`，但订单已被标为 PAID。 |
| T+20 | 部分奖励已转成其他资产/用于下单；推荐层级扩散到 120 个账号。 |
| T+30 | 供应商确认这些 providerPaymentId 不存在。 |
| T+40 | 市场团队准备推送“系统升级，奖励稍后恢复”。 |

成功标准：隔离伪造路径、保全原始回调但限制访问，不直接删流水；先隔离可疑奖励和后续权益，只有在已生效条款、会计依据、风险/法务批准和用户影响评估齐备时，才创建版本化调整、补偿或追偿记录；沟通不把安全事件伪装普通升级。

### EX-03 KYC 供应商不可用且返回错人结果

**目标**：区分服务不可用与身份串线，验证失败关闭、隐私与申诉。关联 THR-013/031/032/033/046。

| 时间 | inject |
|---|---|
| T+0 | KYC P95 延迟上升，待审核队列增长。 |

| T+45 | 供应商要求通过邮件发送完整证件和请求日志。 |

成功标准：停止错误结果传播；不使用次级投影绕过；不邮件传证件；确定受影响主体、删除/更正/通知和供应商合同升级路径。

### EX-04 Redis 会话/权限缓存分区

**目标**：验证会话、RBAC 缓存、多实例不一致和恢复。关联 THR-003/004/008/042。

| 时间 | inject |
|---|---|

## 4. Facilitator 追问卡

当团队过早说“已解决”时，从中选择：

- 你引用的是事实、日志投影还是假设？时间戳和版本是什么？
- 如果依赖实际上已经成功，但响应丢了，会不会重复副作用？
- 旧 App、缓存、第二实例、第二供应商和另一个国家是否仍暴露？
- 谁有权批准收紧与恢复？是否同一个人既修改又复核？
- 用户、账本、审计、outbox、供应商和 App 可见状态是否一致？
- 这项修复会删除证据、扩大数据访问或让隐私/商店声明失真吗？
- 最坏的 1% 用户群是谁？平均指标是否掩盖他们？
- 如果今晚再次发生，哪一个自动控制会阻断，哪一个告警会证明它工作？

### 4.1 Facilitator 私有评分卡

参与者只收到其角色应见的模拟材料；Facilitator 与独立复审人另持私有评分卡，防止参与者照答案表演。每个 EX 必须在开始前填写：

| 私有字段 | 最低内容 |
|---|---|
| 权威来源 | 哪一份账本、供应商查询、审计、对象清单或构建清单能推翻当前假设 |
| 禁止路径 | 不得执行的生产动作、盲重试、证据删除、越权查询和对外承诺 |
| 阶段必交 | T+15 事实/假设分离；T+30 影响与止损候选；T+60 授权恢复/沟通；T+90 验证与行动项 |
| 升级触发 | 资产/PII/身份/商店影响阈值、未知结果时限、法务/供应商/管理层呼叫点 |
| 结束证据 | 状态一致性、对账/删除回执、访问吊销、用户可见结果、审计和证据哈希 |

评分人逐阶段引用原始时间戳和产物，不按口头印象给分；预先泄露的答案、演练外补写的时间线和未经授权取得的数据不计入分数。
