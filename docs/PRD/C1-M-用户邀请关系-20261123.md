# 用户邀请关系：邀请人与团队奖励范围（后台用户 + 客服中心）

2026-11-23 定稿，含实施合同与端到端验收。设计见[用户确认的画布](https://claude.ai/artifact/8d2jtQ2sxFX5uanzsoGvCD)。相关契约见[运营控制后台 PRD v1 的 C1](Nexion_运营控制后台PRD_v1.md#c1-查找用户与查看资料)和[专属客服中心功能契约](M-专属客服中心功能契约.md)。

## 1. 目标

运营和客服在用户列表、用户资料里能直接看到一个用户的邀请关系：

1. 邀请人是谁（用户口中的「上级」）；
2. 团队奖励范围内的团队成员有多少（相隔 1–7 次邀请，用户口中的「能分成的下级」）；
3. 超出团队奖励范围的团队成员有多少（相隔 8 次及以上）。

现状（origin/test，2026-11-23）：四处页面都看不到邀请人；后台详情「团队规模」只数注册时写入的投影（BUG-624 含本人的问题后端已修，待页面验收）；客服「全部团队成员」不分次数；没有任何地方能看到相隔 8 次及以后的人数。

用户已定（2026-11-23）：团队奖励范围固定按相隔 1–7 次算；列表只加邀请人，人数放资料页。

## 2. 用词

后台文案沿用现有用词（直推→直接邀请，佣金→奖励，人员层级用「邀请次数」说法，不用 上级/下级/层级/分成）：

| 用户说法 | 页面用词 |
|---|---|
| 上级 | 邀请人 |
| 下级 | 团队成员 |
| 第 n 层 | 相隔 n 次邀请 |
| 能分成的下级 | 团队奖励范围内 |
| 超出分成的 | 超出团队奖励范围 |

## 3. 口径（一棵邀请树，四处共用）

- **邀请树**：每个用户的邀请人 = `nx_user.sponsor_user_id`（注册时写入；业务代码里没有改绑入口，`nx_sponsorship` 业务代码里没有写入方，不用）。只连同一环境（sandbox）的用户；本人不算；按成员去重。
- **账户状态**：冻结、受限、封禁的账户照算（关系还在）。已删除的账户本身不算，但它邀请的人照算，相隔次数按原位置数（A 邀请 B、B 已删除、B 邀请 C：C 仍是 A 的相隔 2 次）。已删除账户不算「数据不完整」——这是对现有客服统计的改动（现在 `SupportInvitationReadService.java:119,142,166` 会把它算成不完整）。
- **邀请人**：直接邀请这个用户的人。用有效客服邀请码（CS 开头）注册的用户没有邀请人（M 契约 :299）。
- **相隔次数**：直接邀请的人相隔 1 次，他们邀请的人相隔 2 次，依此类推。
- **直接邀请** = 相隔 1 次的人数。
- **团队奖励范围内** = 相隔 1–7 次的人数（含直接邀请）。固定按 7 次算，不随这个用户的等级、也不随团队奖励设置变化。
- **超出团队奖励范围** = 相隔 8 次及以上的人数，不设上限。
- **全部团队成员** = 团队奖励范围内 + 超出团队奖励范围。四个数由同一次计算、同一时点的数据得出，必须能对上。
- **页面问号说明**（不在正文展开）：「这里按邀请次数统计人数。具体奖励以团队奖励设置和实际结算为准。」不写结算机制细节。
- **数据不完整**：只有被看用户本人的环境不能确认，或往下能到达的关系不能证实（有环、重复或冲突的关系、团队成员环境冲突或未知、往下读取中途失败）时，人数不给确数（见 §5）；被看用户自己的邀请人有问题（指向不存在的账户、在另一环境、补读失败）只影响邀请人显示，人数照常。不写 0、不估算（ST-34、M 契约 :464）。只在已读到的根用户和可达关系上判断，不承诺发现不可达的孤立数据。确认 0 人照实写「0」。
- **和 App「我的团队」的差别**：App 团队页只沿正常状态、未删除的成员数，遇冻结或删除的中间人会截断其后，且每页最多 500 条（`AppTeamNetworkMapper.java:29-45`、`AppTeamNetworkService.java:22,49-55,75`），所以可能比这里少。客服被问到时以这里为准：后台含冻结等状态和相隔 8 次以后的人。

## 4. 页面

### 4.1 后台「查找用户与查看资料」列表（C1，`/users/search`）

- 新增「邀请人」，默认可见，放在「用户」后第二列：一格两行，第一行昵称，第二行用户编码（等宽，TX-28）。写法按 §5。用户列和邀请人列各约四分之一宽，长昵称放得下时完整显示，放不下才省略并悬停看全文。
- 所有有列表读权的角色都显示（客服账号经 C1 读取时，范围外邀请人按 §4.6）；不改变风险、余额、设备的现有裁剪。
- 不做链接：整行、Enter 和「查看资料」打开的都是这个用户（ST-06）。
- 加邀请人后仍是 6 列（用户 2026-11-23 定方案一）：「状态」和「用户分层 / 团队等级」合成一格两行，表头「状态 / 用户分层 · 团队等级」，状态在上；风险、余额、操作不变。
- 不加人数列。

### 4.2 后台用户详情（C1D，`/users/search/{userNo}`）

| 落点 | 入口 | 显示 |

| 客户资料（M3CustomerProfile）展开视图 | M1「客户」视角抽屉、M3 会话右栏「展开资料」 | 「基本信息」组加「邀请人」行（数据来自身份）；「首充与邀请统计」组的「全部团队成员」拆成团队奖励范围内、超出团队奖励范围、全部团队成员三行；组 note 一句说口径 |
| 客户资料摘要 | M3 会话右栏（`m3-customer-profile.tsx:325-336`） | 邀请人放右栏头部（用户编码、当前专属客服下面），只出现一次；「首充与邀请」折叠写四个人数（直接邀请、团队奖励范围内、超出团队奖励范围、全部团队成员） |

### 4.5 邀请人可点的条件

邀请人能点开，要同时满足三条。后端按当前账号判断第 1、2 条，返回 `navigable`；前端再判第 3 条；打开目标时后端再校验一次：

1. 当前账号能读这位用户本人（来源可读）；
2. 当前账号能读邀请人（目标可读：C1 详情按 `requireRead` 的现有范围，客服按本人绑定 / 负责组 / 全部的获准范围）；
3. 目标页面对当前账号可达（CP-30、ST-58）。

后台详情用邀请人的用户编码打开 `/users/search/{userNo}`；客服用获准的 `customerId` 打开 `/service/customers/{id}`。`navigable=false` 时响应里不含非空的目标 ID，页面只留文字。客服不因此获得 C1 权限。列表里的邀请人一律不做链接。

### 4.6 邀请人不在客服范围内时（用户 2026-11-23 定：方案 A）

客服能看这位客户，但邀请人可能是别的客服的客户、外组客户、已转出的客户或未分配的人。这时显示邀请人的昵称和用户编码，不可点。只此两项：不带邀请人的归属客服、分组、队列状态、手机号、资金、会话或任何导航 ID；不能按邀请人搜索；不进导出和实时推送。邀请人已删除时只给用户编码和「已删除」。例外的入口和字段同时列在[专属客服中心功能契约](M-专属客服中心功能契约.md)。

**适用范围**：凡是后端按客服对象范围裁剪的读取都按这条处理，包括客服中心各接口，以及客服账号经 C1 列表、C1 详情的读取（`OpsUserService.java:350-356,647`、`OpsUser360Service.java:101-105` 对这类账号仍按客服范围）。不受客服范围裁剪的后台读取照常显示。

**共用响应**：共用客户行的所有响应都可以带邀请人两项，包括带关键词的 `/customers` 请求和「主动联系本人客户」选择框用的响应（选择框照旧不显示）。邀请人不参与关键词匹配、不影响结果条数和对象授权。

## 5. 状态

邀请人的状态和人数的状态互相独立：人数读取失败不影响邀请人显示，反之亦然。

**邀请人**

| 状态 | 条件 | 写法 |
|---|---|---|
| 有邀请人 | 同环境、未删除 | 昵称 · 用户编码；可点按 §4.5 |
| 无邀请人 | 已确认没有邀请人（含有效客服码注册） | 「无邀请人」弱字 |
| 邀请人已删除 | 同环境、已删除 | 用户编码 +「已删除」，不可点 |
| 无法确认 | 邀请人指向不存在的账户、环境冲突或未知、读取失败 | 橙黄警示标签「无法确认」+ 问号写原因，不给任何目标标识 |

**人数**（四个数一起）

| 状态 | 写法 |
|---|---|
| 完整 | 实数；0 写「0」 |
| 数据异常（被看用户本人环境未知或在环上，或下面的关系有环、重复或冲突、团队成员环境冲突或未知；状态与显示的对应见 §6.3） | 四个数写「—」，下面常显橙黄提示条加图标：「邀请关系数据有异常，人数暂不显示。请联系值班人员核对。」不退回观察值 |
| 没读全（遍历中途读取失败，后端原因 `SOURCE_READ_FAILED`，即使已读到部分人） | 四个数写「—」，下面常显橙黄提示条加图标「人数没有读全」，右侧「重试」重读这一块（§6.6 第 4 条） |
| 人数读取失败（外层资料读到） | 后台保留推荐团队的成员样本与团队订单额，四项人数写「—」，人数处显示「邀请人数」及橙黄「加载失败」、原因和重试，摘要写「人数加载失败」。客服只将人数四行替换成同一失败提示，首充和金额照常。 |
| 整个来源读取失败 | 后台推荐团队区块显示「推荐团队加载失败」、原因和重试，关键数字写「—」，收起时摘要写「推荐团队加载失败」。客服整个统计读不出时用整组失败样式（ST-30、ST-34、ST-40、M 契约 :319）。 |
| 加载中 | 骨架或「正在读取」，按所在组件现有写法 |

**权限**

- 整页 / 整位客户无读权：按 ST-38 和 M 契约 :201 显示无权限页，清掉上一位客户的身份和链接，不残留。
- 单区块无读权（如 FINANCE 看推荐团队）：整块不显示（ST-39）。
- 列表整表读取失败：按列表现有错误行，不显示旧数据。

**新旧版本交叉**（前端 PR0 先上，§6.4、§6.6）：
- 含 PR0、未含 PR2 的前端 + 新后端（不含 PR0 的旧前端不兼容新后端，所以后端必须在含 PR0 的版本部署后才上）：旧键 `teamSize`、`directCount` 保留（值为新口径），旧页面照常显示在旧标签下；新键被 PR0 的解析放宽接住，不显示；M1「统计依据」等处的邀请人数非 AVAILABLE 时不显示观察值（PR0 一并改）。
- 新前端（PR2）+ 旧后端：响应里没有 `inviter` 时不显示邀请人（列表不出现空的「邀请人」列、页头不出现空事实、不当成「无邀请人」、不出死链）；没有 `countStatus` / `withinRewardRange` 时，四行人数、关键数字、折叠摘要、抽屉都写「—」，不显示原因提示。
- 客服旧采样代（新后端刚上、还没算出新一代）：四个数写「—」，不显示「数据异常」提示（原因码 `GENERATION_UPGRADING`，§6.6），首充、金额照常。

## 6. 后端与 PC 接口合同（B73、B74）

### 6.1 计算

- 按 §3 沿 `sponsor_user_id` 向下数，一次遍历得出 `direct`、`withinRewardRange`（1–7）、`beyondRewardRange`（≥8）、`total`，以及完整性状态和原因。可在 `SupportInvitationReadService` 的遍历上加相隔次数；已删除节点不再记为不完整。7 是常量，不做配置。
- 客服统计走采样（`SupportAnalyticsFactSampler` 每分钟编译、`SupportAnalyticsCacheCodec` 版本化反序列化）：两档人数必须和现有 `direct`、`descendants` 在同一次遍历、同一采样代里产生；缓存结构升版本，旧代没有新字段时按「不完整」处理，不报错、不补 0。
- 后台详情可以实时算，但四个数同样出自一次遍历。
- 列表接口只批量取直接邀请人，不做递归、不逐行查详情。

### 6.2 邀请人对象

新版响应里 `inviter` 对象总是存在（不能因 `JsonInclude.NON_NULL` 整个省略，`UserProfileListView.java:11-13`），这样页面能区分「无邀请人」和「没读到」。

**基础字段**（所有带邀请人的接口都有，列表行只有这四个）：

```
inviter: {
  state: "PRESENT" | "NONE" | "DELETED" | "UNKNOWN",
  userNo: string | null,      // PRESENT、DELETED 时有；其余为 null
  nickname: string | null,    // PRESENT 时有
  reason: string | null       // UNKNOWN 时有，取值见下面的邀请人原因码
}
```

**详情另加的字段**：

| 接口 | 另加 |
|---|---|
| C1 详情（`/360`） | `navigable: boolean`（§4.5 第 1、2 条都满足时 true；前端再判路由可达） |
| 客服完整档案（`/full-profile`）、客服客户资料（`/customers/{id}`、`/360`） | `navigable: boolean`；`customerId: string \| null`（navigable=true 时非空，否则 null） |

- **列表行**（C1 列表、客服客户名单、客服统计共用客户行）只有基础四个字段，不带 `navigable` 和 `customerId`，范围内的正常邀请人也一样（列表不做链接，也不逐行判断目标权限）。
- 后台接口不返回 `customerId` 这个键，也不返回邀请人的数字 `id`。
- **邀请人原因码**（`reason`，和人数原因码是两份白名单）：`DANGLING_SPONSOR`（指向不存在的账户）、`ENVIRONMENT_CONFLICT`（邀请人在另一环境）、`UNKNOWN_ENVIRONMENT`（邀请人环境未知）、`SOURCE_READ_FAILED`（邀请人读不出）。PC 解析按这份白名单，未知码按「无法确认」显示。

- **往上和往下的问题分开记**：现有遍历（`SupportInvitationReadService.java:70-92`）对已读节点之外的父引用做检查，实际只会是被看用户本人的邀请人；查出的问题记到根用户上（`:142`），补读父账户失败还记进整批共用的 `SOURCE_READ_FAILED`（`:90`），都会让人数变成不完整（`:166-168`；`SupportAnalyticsService.java:764-767,793-797` 据此把 confirmed 置空）。改为三种读数分开，状态和原因一起分开（不能只从输出里删原因、却仍保留旧的不完整状态；也不能整体忽略 `ENVIRONMENT_CONFLICT` 或 `SOURCE_READ_FAILED`）：

  2. 被看用户本人环境未知、被看用户在环上，或往下的路径有问题：影响人数（人数原因码，§5「数据异常」）；被看用户在环上时，邀请人本身能读到就照常显示；
  3. 往下读取中途失败：人数 PARTIAL + `SOURCE_READ_FAILED`，§5「没读全」。
  `DELETED_NODE` 不再进人数原因（§3）。
- 不新增权限码；搜索的匹配字段、权限和条数口径不变（返回行按 §4.6），不能按邀请人搜索；导出、实时推送不加邀请人字段。

### 6.5 累计充值 / 提现「没有」和「没读到」分开（只改展示投影）

现状：`summary.depositedUsd`、`withdrawnUsd`、`withdrawRequestedUsd` 由 `OpsUser360Service.supportTotal`（`:539-543`）从 `FinanceSupportReadService.totals`（`:18-41`）的 `byCurrency` 取 USDT 行；币种行只在有余额、核对入账、提现汇总或异常时建立，没有 USDT 行就返回 null，各合计默认 null / UNKNOWN（`:59-62`），正小计标 PARTIAL（`:69-77`）。所以「从没有过」和「读不到」页面分不清。

要的结果（三个字段各自判断，只看 USDT；`byCurrency` 里没有 USDT 行的用户按「确证没有对应金额」处理，三个字段都给 `"0"` / READY，前提是来源读取成功）：

| 字段 | 来源读取成功、确证没有对应的单 | 有单但没有对应金额（待付、处理中，或只有别的币种） | 有已核对的正小计 | 有异常、读不到 | 无权限 |
|---|---|---|---|---|---|
| `depositedUsd`（累计成功充值） | `"0"` / READY | `"0"` / READY | 原值，保留现有 PARTIAL 含义 | 现状（null / UNKNOWN），页面「—」+ 原因 | 不返回 |
| `withdrawnUsd`（累计成功提现本金） | `"0"` / READY | `"0"` / READY | 同上 | 同上 | 不返回 |
| `withdrawRequestedUsd`（处理中提现本金） | `"0"` / READY | 有处理中的单时为其本金合计（例：只有一笔处理中 80 USDT → `withdrawnUsd`="0"，`withdrawRequestedUsd`="80"） | 同上 | 同上 | 不返回 |

- 关键数字下面「最近一笔」不受这张表影响：它按全币种最近一单单独读取（`UserLatestFundActivityMapper.java:71-80`），「暂无充值」「暂无提现」只在最近一笔读取成功且确实没有记录时写（现有规则，PRD v1 :1873）；只有别的币种记录时，USDT 合计是 0，最近一笔照常显示那一笔。
- **只改展示投影**：C1 详情 / 完整客户档案的 summary、客服客户资料的资金组按上表；**客服群发圈选（`SupportBulkService.java:494-512`）不改**，仍按原来的 READY / UNKNOWN 输入选人，收件人范围不变。
- 金额一律十进制字符串（`m-support-enhancements.ts:41-55` 要求），不给裸数字。

### 6.6 实施合同补充（实施前审查后定）

1. **按入口投影**：C1 详情（`OpsUserController.java:202`）和客服完整档案（`SupportWorkbenchController.java:84-90`）都调用 `OpsUser360Service.detail(Long)`，同一账号可能两条路都能走。投影时带上入口：C1 入口不返回 `customerId` 键；客服入口按 §6.2 给（可导航时非空）。会话详情默认带的客户资料（`OpsConversationController.java:223-225`、`OpsConversationService.java:150,217-219`、`SupportCustomerProfileService.java:253-263`）也带 `identity.data.inviter`，规则同客服客户资料。对象授权一律沿用原入口的。
2. **客服采样旧代**：`SupportAnalyticsCacheCodec`（`:10-30`）现在先强类型反序列化再看版本，新代加字段后旧代会 503。改为先认版本：旧代可读部分照常给（首充、金额等），邀请人数四项状态 UNKNOWN、原因 `GENERATION_UPGRADING`（页面写「—」不提示异常），不报 503；新一代发布后自然切换。
3. **外层区块状态和内层人数状态分开**：C1 详情 `referral.sourceStatus` 只表示整块读没读出来；人数自己的状态放 `countStatus` / `countReasons`，不要把人数 PARTIAL 写进 `sourceStatus`（`user360-client.ts:750-755` 会把非 READY 分区裁掉，样本和订单额会一起丢）。
4. **重试**：「重试」重新请求这一页原来的数据源：C1 详情（C1D）重读 C1 的 `/360`；完整客户档案（C1S，超管可能看得到推荐团队）重读原来的 `/full-profile`；客服个人抽屉、资料展开视图、会话右栏重读各自原来的客户资料接口。**重试成功就用新回包整体替换这一页的数据**（后端按当前权限的最新投影为准，权限收窄后被裁掉的区块随之消失），只保留界面状态（展开的折叠、滚动位置），不整页刷新浏览器；**重试失败时保留现有数据**，只在这一块显示错误和重试。重试成功后的效果和页头「刷新」成功一样（只多保留展开的折叠、打开的记录列表和当前定位；「当前定位」指推荐团队分区标题留在原来的屏幕位置，左侧分区导航的高亮照导航原有规则）；重试进行中，本页的写入口和页头刷新时一样暂不可用；本页有写操作在提交时，「重试」不可点。不做「只合并某一块」的局部合并（2026-11-23 重新规划：局部合并在权限收窄时会残留旧区块）。读到的是后端当前已发布的数据；客服统计来自每分钟采样，重试不会触发重算，所以「没读全」可能要等下一代才恢复。不新增单独的人数接口。授权被撤销时整位客户清空（ST-38）。
5. **等级字段**：客服客户资料 `identity.level` 现在取第一个非空的 vRank 或 userLevel（`SupportCustomerProfileService.java:79,300`），页面分不清是 V 还是 L。后端另给 `identity.data.vRank`、`identity.data.userLevel` 两个字段（`level` 保留给旧前端）；页面只按确证的字段写「团队等级」「用户分层」，缺哪个就不写哪个；在客服的折叠摘要、基本信息、右栏头部（`m3-customer-profile.tsx:246-247,324`）三处都按这条；PR1 不改客服这三处的等级写法（旧 `level` 分不清 V 和 L），随 PR2 接新字段。

2. **资料**（后台详情、个人工作台客户资料抽屉、M3 右栏摘要与展开资料）：邀请人和 §6.6 第 7 条规定的人数与上表一致；成员样本只含相隔 1–7 次、不含本人和已删除账户（A 的样本里没有 D、没有相隔 8 次的 I，合法后代仍在；另造 20 个可见成员加若干排序靠前的已删除成员，验样本仍凑满 20 个）；后台和客服同一用户数字一致（客服采样覆盖后再比）；后台关键数字最多 4 个，入选与未入选、点击定位、正文不重复、成员列表不含本人。
3. **完整客户档案**：专属客服、主管只核对邀请人；总管理员按实际返回的团队段核对推荐团队区块。
4. **角色**：后台 SUPER_ADMIN、RISK、AUDITOR、GROWTH 看到邀请人和人数；FINANCE、只有列表权的账号看到邀请人、看不到推荐团队。客服：专属客服（本人绑定）、兼任主管、无组主管（合法空态）、负责组主管、总管理员。核对接口实际返回字段，不只看按钮。
5. **范围外邀请人**（§4.6）：选邀请人确实在测试客服账号全部获准范围之外的用户（兼任主管可能读得到同组其他客服的客户，按账号实际范围挑）。用 E（邀请人 D 已删除）分别以普通后台账号、M 客服、有 C1 权的同一客服查看，三者都是「D 的编码 · 已删除」、不可点。再找一位邀请人是别的客服客户的用户，三种账号都显示昵称和编码；客服两种读取都不可点、响应无非空目标 ID、不带邀请人的归属客服等其他字段。
6. **可点**（分两条断言）：对象范围不准读邀请人时，服务端不给非空目标 ID、页面不可点；对象范围准读（`navigable=true`）时，ID 按 §6.2 返回，但当前账号前端菜单到不了目标页时页面仍不可点（`use-reach.ts:11-19`、`console-nav.ts:537-544`）；能点时打开成功；同一客服身份抓一次默认会话详情（`includeCustomerProfile` 默认），核对 `customerProfile.groups.identity.data.inviter` 字段，`includeCustomerProfile=false` 时不带资料；完整档案不回退到 C1 接口；撤销原绑定后旧资料清空。
7. **状态**（按 §5）：无邀请人、已删除、确认 0、加载中、切换客户不残留上一位。人数分别造：PARTIAL + SOURCE_READ_FAILED（「—」+ 橙黄「人数没有读全」+ 重试）、其他 PARTIAL / UNKNOWN（「—」+ 橙黄「数据异常」提示）、FAILED（后台：人数写「—」并显示局部失败行，样本与订单额照常；客服：一行「邀请人数 · 加载失败 · 原因 · 重试」）、推荐团队整个来源失败（「推荐团队加载失败」）、客服整个统计组失败、重试后恢复、重试仍是同一采样代；每种都看卡片、折叠摘要、邀请人和首充 / 金额是否照常。
7a. **版本交叉**（§5「新旧版本交叉」）：PR0（首个部署版本只含 PR0 时就用它）+ 新后端先走一次兼容检查；之后 PR1 + 旧后端、PR1 + 新后端、PR2 + 旧后端、PR2 + 新后端四种组合各走一遍 C1 列表 / 详情和客服三处资料；新后端刚上线、旧采样代还在时开 M1 与 M3 资料，确认无 503、人数「—」无异常提示、首充与金额照常，新一代发布后切换。
7c. **重试入口**：超管从完整客户档案（C1S）点推荐团队「重试」，确认请求的是原来的 `/full-profile`（不是 C1 的 `/360`），摘要和成员样本按返回更新；再造一次普通读取失败和一次撤权（撤权时整位客户清空）。
7d. **客服等级**（PR2）：客服折叠摘要、基本信息、右栏头部三处，用 L 与 V 不同的客户、只返回 vRank 或只返回 userLevel 的客户、旧后端两项都没有的情况各看一次：只写确证的那个，缺的不写，不把 L 写成团队等级。
7b. **资金零值**（§6.5）：无单、只有另一币种、只有待付 / 处理中、有异常、读取失败、有正小计六种样本，逐字段看三个 summary 值、`financial.byCurrency` 对应的 fieldStatuses、两个最近一笔的状态和文案（重点样例：只有别的币种；只有一笔处理中 80 USDT），按入口：C1D、C1S 用有资金读权的账号核三个 summary、USDT 行三个字段状态和两次独立的最近一笔读取（只有别的币种：三个 USDT 小计 "0"，最近一笔保留原币种；只有一笔处理中 80 USDT 提现："0" / "0" / "80"，最近提现显示该单；最近一笔读取失败时不写「暂无」）。M3 资金组只核 USDT 行 `creditedDepositTotal`、`successfulWithdrawalPrincipalTotal`、`processingWithdrawalPrincipalTotal` 的值、`fieldStatuses` 和页面显示（M3 没有独立的最近一笔读取，不验「暂无」文案）；特别是没有 USDT 来源行的样本（`SupportCustomerProfileService.java:161-175` 会补 USDT 行、现状填 UNKNOWN），确证零值要成为 "0" / READY，来源失败仍保留失败状态。群发：固定一组「改前资金 UNKNOWN、改后展示 0」的已绑定客户，选 USDT、金额上下限都为 0、关闭「含未知」，再打开「含未知」各预览一次，用同一账号和数据比较改前改后的**候选客户 ID 集合**和每位的入选 / 排除结果，必须完全一致；只预览不发送。
8. **异常关系**（只在隔离库直接写数据后从只读页面观察，不经注册入口绕过校验，不改共享库）：
   - 直接关系无效：X 有一个同环境的直接邀请 Y（Y 没有团队），再让 X 的邀请人指向不存在的账户。看 X：邀请人为橙黄「无法确认」+ 问号，响应 `inviter.state=UNKNOWN`、`reason=DANGLING_SPONSOR`；X 的四个数仍是确数 1 / 1 / 0 / 1。看 X 原来的邀请人：X 和 Y 都不再计入。再把 X 的邀请人改指另一环境的账户，结果相同（reason=ENVIRONMENT_CONFLICT）。
   - 直接关系有效、下面的路径异常：P 正常邀请 X，把 X 的某个团队成员改到另一环境（环境冲突）。看 P：邀请人照常，四个数「—」+「数据异常」；列表里 P 的邀请人照常（列表只查一层）。
   - 被看用户在环上：把 P 自己的邀请人改成 P 的某个团队成员（每人只有一个邀请人，环只能从环上的账户看到）。看 P：邀请人照常显示那位成员，四个数「—」+「数据异常」（人数原因列表含 CYCLE，即 C1 的 countReasons 或客服的 invitations.reasons；inviter.reason 为 null）。
9. **口径不随设置变**：同一棵树，改这个用户的等级、切换团队奖励设置（七层开启与否）后，四个数不变；受限、封禁、冻结的成员都计入；环境未知的样本人数「—」。
10. 搜索的匹配字段、权限和条数口径不变（返回行按 §4.6，带邀请人两项不算搜索范围扩大）；导出、实时推送的范围和字段没有变化。
