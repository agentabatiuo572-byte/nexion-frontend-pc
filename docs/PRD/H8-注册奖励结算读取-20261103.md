# H8 注册奖励与结算记录

`/growth/referral-rewards` 读取 `GET /api/admin/growth/referral-rewards?pageSize=20[&cursor=…]`。页面显示开关、三项基础额和 H1 当月有效额、发放方式、生效时间、待结算/风险拦截/累计结算及最近结算。每次 20 条，后端按结算行 ID 倒序分页；更早记录失败保留已有列表和原游标，可重试同一后页。金额必填、非负、最多六位，不把缺失或空字符串当 0；计数必须是非负安全整数。首屏、参数确认和去向图对纪元生效时间统一显示“未设置 · 所有注册都算”；空生效时间不是合法成功响应。

每条结算的 `invitedUserId` 必须为正安全整数。没有有效邀请人的新人仍可有新人礼，`inviterUserId=null` 显示“没有邀请人”，邀请奖励为 0。后端有效邀请人来自 sponsor 关系，还核对账号、环境及钱包；不提供手工指定邀请人。结算记录状态 SETTLED 可能包含仍在冻结的新人礼，不证明可提现；页面未取得个人冻结、首购、钱包、风险状态或每批审批人的明细，不能由最近记录推断某人的当前结算资格（H8-BE-03 待后端）。

待结算按有效注册、时间闸、未结算和风险资格统计，**没有钱包 JOIN**；实际候选要求新人钱包，所以待结算大于 0 时本批也可能实际结算 0 笔。此差异按 H8-PD01 如实显示，H8-BE-01 未交付前不替后端统一口径。risk_bucket 额外拦待复核风险，direct 仍有账户/账户组硬拦截；两种方式都不替代首购冻结或 K1 收益分桶。

批量和指定新人都只 POST A2 审批，不直接调用结算执行 API。批量框沿用旧空输入，不填不能提交；填写 20 时提交 limit=20，范围 1–100，共享确认框按step=1验证整数，小数不能提交；不因Number(value)的后备写法重复增加校验。后端实际执行在 limit 缺省时也默认 20，但 A2 描述器要求明确整数 limit，所以前端不能靠省略 limit 实现空框默认。指定新人不发 limit，command 固定该 invitedUserId；两种共用目标 `H/referral_settlement_batch/pending`，一次仅一张待批单。发起要 growth_h8_settle 加 A2 提案权；批准要另一位有 A2 批准权及结算业务权的管理员，没有参数审批的专用超级管理员要求。

结算提案保存 H8 版本、H1 月份、完整 rewardSnapshotHash，不冻结名单。批准时重新校验快照，在当前名单按注册时间/ID 升序选取最多 limit 位；开关、三额全 0、快照变化或 B1 不满足会拒绝。**提交结算审批不查 B1**，批准执行在结算前后检查，失败回滚本批。新人可没有邀请人；首购冻结新人礼先 hold，再在首笔 PAID、实付大于 0 的订单后按原金额/原模式和风险资格释放。非冻结及解冻后的收益按 K1 分可提现、待审核或锁定，邀请人有且金额大于 0 才入账，两边按实际金额记账。

指定新人已结算且没有新候选时，若其原礼包还冻结、已首购且符合原模式风险条件，可以只释放该原礼包，返回 settled=0/released>0；否则拒绝，绝不改发别人。不能把“已结算过就不发”当作绝对不可能释放资金。停用禁止新结算，但后续订单事件仍能释放旧礼包。
