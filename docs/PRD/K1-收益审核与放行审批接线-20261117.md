## 状态走向

### A09 放宽收益审核阈值

1. 原直接 PATCH 保存原值、版本、理由、操作人及原键。旧后端成功、收紧/同值成功仍重读生效，退役 key 不提审批。
2. 仅明确 APPROVAL_REQUIRED 才切现有 DraftModal 的审批模式。保留新值和理由，使用已有“提交审批/批准后生效”，再次确认才创建独立提案；改成收紧则继续原直写。
3. 新 POST 前完整 request、独立原键、认证提交人、原来源进入现有 session journal；持久保存失败不发送。业务权 + create/write 提案权缺一不可。
4. POST 成功先只记“已建单”；随后 GET 原键核 mine、operationCode、obj、action、真实 status、资金类型及可读摘要。仅当前 GET 的 pending 显示待审批、保留对象锁；历史 POST 的 pending 不当当前状态。
5. OBJECT_ALREADY_PENDING 显示后端拒绝，不冒充本人的成功单。建单 STALE 进入原“读取最新”，留新值和理由。查 pending 时重读规则，聚合 version 已变则提示原票仍待审、需按现行流程结束旧票后重新核对，不自动重提。
6. 本人原键 GET 到 approved 后重读正式规则；rejected/withdrawn/expired 解除本页记录并重读。不调用批准接口、不判断谁能批、不自行撤回旧票。
7. 未知保原 body/key。人工重试先 GET 原键，明确查无、未确认建单且仍在 24 小时内，才手动重发保存的原 POST。查询/权限失败、幂等未收敛或冲突、不可读回包均保留。
8. 超过 24 小时只查。仅未确认建单、原键权威 A2_PROPOSAL_NOT_FOUND，并经现有解除框确认且再查仍无，才解除本地提案记录。曾确认建单的不按查无解除；原直接写不适用。

### A11 人工放行被保护收益

1. 原直接 POST 成功保留旧行为。直接结果未知只保原请求，绝不自动重发或转审批。
2. 明确 APPROVAL_REQUIRED 后复用现有操作确认容器重开审批模式，以 initialReason 保留理由；再次确认才保存独立提案/键。只传 entryNo，不传三额、maker、before。
3. 待审批锁定该 entry，其他收益不受本地锁影响。POST→原键 GET→pending 的证明同 A09；查终态后重读收益列表，由服务端批准只将绑定那笔转为 withdrawable，前端不再 manualRelease。
4. 建单/直接调用明确 STALE 或 ENTRY_NOT_PROTECTED 时只重读列表、显示原拒绝，不自动换新单。查 pending 也重读列表；可读净额/资产/来源/保护桶变化给出核对提示，原票仍保留。
5. 列表找不到 entry 只说明不在当前最多 200 条里，不推断全额追回或不受保护。批准失败仍留 pending，GET 不返回 checker 上次错误，前端不能伪造“已驳回/已过期/已放行”。
6. 未知、手工原请求重试、权限和过期规则同 A09。现有直接写受控核查及 eCommandClosureRequests 原样保留；A2_COMMAND 成功只证明建单，还须查询原票，不据创建成功解锁另提。
