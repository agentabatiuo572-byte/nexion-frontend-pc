## H4 售后政策的整单退款执行

`6f9a1a52` 在管理政策列表和详情的 `REFUND / PROMOTION_WALLET_REFUND_V1` 行提供可选 `execution`。已经发放的 UVT、USDT 奖励按同币种可用余额追回，余额不足计入平台损失并以 `REVERSED` 结案。赠品设备收回、未完成的计算任务取消、运行停止，已到账收益保留并计入平台损失。独立纠正追回不足仍可进入人工审阅。发放或退款依据不明确时沿原核查，未发放奖励走取消。

PC 政策读取接收同一行的执行元数据与原合同。旧服务、其它政策及活动目录可以没有 `execution`。原 v1 `content.insufficientRecovery=MANUAL_REVIEW`、合同哈希、引用和写操作仍按原约定。实读列表和详情都看到 `execution.insufficientRecovery=PLATFORM_LOSS_AND_CLOSE` 与原存档值同存。新事实只读，只在政策详情里呈现。

页面呈现（「政策」页签点开「售后追回」）：有 `execution` 时，详情在批准信息下面分两段。第一段「整单退款实际怎么处理」，一句说明「系统现行做法，和这一版批准与否无关；每笔结果看奖励台账」，再逐项用运营的话写：什么时候处理（整单退款确认之后）、钱包奖励（从同一币种的可用余额里追回）、余额不够时（不扣成负数，也不扣别的币种）、赠送的设备（收回设备，取消没做完的任务；已到账的收益不追）、追不回的部分（记为平台损失，这笔直接结案）、结案后的状态（已冲正）、转人工审阅（只在批准的纠正追不回时）、发放情况核不清（按原来的退款核对处理）。页面认不出的取值写「读不出」，原值收进这一段下方折叠的「技术信息」。第二段「政策原文」标「存档」，说明「这一版存下的原文，批准和引用都按它核对」，原有各项照旧，其中「追回不足处理：人工审阅」后注「存档写法，实际见上」。草稿和已撤销的版本带这组说明时同样呈现，不当作批准或执行的凭证。没有 `execution` 的政策和旧读取保持原来的详情样子。

奖励冲正确认框的「用户会怎样」按所选依据和奖励类型分四种：整单退款 + 钱包奖励「从同币种可用余额追回，不扣成负数；追不回的由平台承担并结案」；整单退款 + 赠机「收回赠机，停止没做完的任务；已到账收益保留，记为平台损失并结案」；批准的纠正 + 钱包奖励「只追回能确认还没花掉的部分；追不回的转人工审阅」；批准的纠正 + 赠机「只收回没跑过任务、没有收益的赠机；收不回的转人工审阅」。依据是后端 `PromotionRewardService.reverseLocked`、`revokeRefundGifts` 与 `EarningsReleaseService.recoverReward`（纠正只追可证明未消耗的部分）。已冲正的奖励详情提示改为「已冲正结案」：有平台损失时说明未追回的部分由平台承担，没有时只说不能再发放（纠正路径追全才结案，不产生平台损失）。「已追回」「未追回奖励」两项带原奖励的单位（币种或台）。
