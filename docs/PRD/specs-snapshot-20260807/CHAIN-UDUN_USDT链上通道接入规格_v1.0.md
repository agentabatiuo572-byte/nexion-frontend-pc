## 一、这次核源推翻的两个前提(动笔前必须先讲)

### 🔴 前提一:「重叠面 = 链上一层(地址派生 / 扫链 / 签名 / 归集)」— 实测只覆盖两项

改向决议(triage §一 D1′)按 2026-08-02 调研写的是四项。**实测接口全集只覆盖「地址派生」与「出金签名」**:

| 那四项 | 优盾实际覆盖 | 后果 |
|---|---|---|
| 地址派生 | ✅ `/mch/address/create` | — |
| 出金签名 | ✅ `/mch/withdraw` | 但无序号 / 无过期证明 / 无顶替接口 |
| **扫链** | ❌ 只推回调,**无区块哈希 / 确认数 / 事件序号,且无任何查询接口** | **平台仍须自接链上数据源**,才算得出确认数、判得了重组、做得了对账取数与灾备 fencing |
| **归集** | ❌ **无 API**(调研:PC 客户端手动,过程不能关机) | 热冷分层 / 归集阈值 / 按需归集旁路 **无接口可驱动** |

→ **省的不是"链上那一层",是"地址派生 + 提币工单"这一层半**,而且要**新增**一整套"不信任外部通道"的补偿层。

### 🔴 前提二:「自建完成后替换优盾,平台接口不变」— 接口能不变,**地址不能**

`[KNOWN, HIGH]` 链上事实:用户已保存的收款地址永久有效,其私钥恒为**当初派生它的那棵 HD 树**。

→ 自建上线后,**优盾时期派生的存量地址仍只能由优盾那组助记词签名**。真实形态不是"替换",是:

> **双 rail 并存** —— 新地址走自建 rail;存量地址长期由优盾侧密钥继续保管与归集,直到走完一次**全量地址换发 + 用户重新保存新地址**(而这是一次有用户感知、有资金滞留风险的迁移动作)。

→ 本规格必须自带「**地址管辖台账**」与「**换发迁移**」两个对象,否则将来切换那天才发现存量地址无人管。
→ **反向推论(直接影响拍板)**:优盾用得越久、地址派生得越多,将来的迁移越贵。**这是一个随时间单调增长的退出成本。**

## 二、架构主张(拟)

### 2.1 契约在前,实现在后

定义 **链上通道契约 `ChainRail`** —— 它就是上游 CHAIN 规格里平台业务侧的全部调用点。业务侧 / 账本 / 风控闸 / 熔断 / 对账 / 灾备**只依赖契约,不依赖实现**。

| 契约方法 | 幂等键 | 优盾实现 | 自建实现 |
|---|---|---|---|
| `allocateAddress(账号, 网络)` | {账号+网络} | `/mch/address/create` | HD 派生 |
| `isPlatformAddress(地址, 网络)` | {地址+网络} | `/mch/exist/address` + 本地映射库 | 本地映射库 |
| `submitPayout(出金单号, 地址, 金额, 网络)` | **出金单号** | `/mch/withdraw`(`businessId` = 出金单号) | 出金域签名 |
| `queryPayout(通道单号)` | — | ❌ **优盾无此接口** → 回链自查 + 回调补 | 出金域台账 |
| `sweep(地址集)` | 任务号 | ❌ **优盾无此接口** → 见 §五 拍板项 2 | 归集域签名 |

🔴 **`chainRead.*`(确认数 / 区块哈希 / 余额 / 按 txId 查交易)不在 rail 契约里** —— 它**恒由平台自有链上数据源实现**,两种 rail 形态下都一样。这条是本架构的地基:**通道可以换,链上事实的取数口不换。**

### 2.2 三类条款分治

| 类 | 内容 | 处理 |
|---|---|---|
| **原样保留**(优盾不覆盖,CHAIN 怎么写还怎么建) | 复式账本六储备子账户 · 资产侧/负债侧双对账 · 追偿应收 · 处置队列 · 六道风控闸 · 熔断 · 重组冲正 · N 域后台 · 映射库备份与 fencing · 审计日志与每日签名锚 | 引用上游,**不复述**(防两份副本各自漂移) |
| **结构性降级**(在"私钥由外部单机持有"形态下**不成立**) | 三域分片不重叠 · 完整私钥不存在 · 门限≥2 · 签名侧硬上限 · 所见即所签 · 归集/出金域隔离 · **「任何单人不能独立动资金」** | 落「**承诺降级对照表**」,并硬约束:**降级期间这些承诺不得出现在任何对外文案与后台标签里** |
| **新增**(接外部通道才需要) | 回调不可信补偿层 · rail 健康与套餐状态监控 · 退出触发器与撤离剧本 · 双 rail 并存与地址管辖台账 · **脱离演练** | 本规格主体 |

## 四、三条硬问题的拟定答案(方向级,签字后展开)

### 4.1 MD5 弱验签怎么补 → **不补它,绕过它**

事实:`md5(body+key+nonce+timestamp)`,单一共享密钥双向使用。MD5 不是 MAC;密钥泄露即双向可伪造。**但真正的问题不是算法强度** —— 就算换成 HMAC-SHA256,回调本身也缺区块哈希与确认数(§0.2),**依然不足以作为入账依据**。

三层落法,**第三层才是真防线**:

| 层 | 做什么 | 定位 |
|---|---|---|
| L1 传输 | 优盾出口 IP 白名单 · 强制 HTTPS(双向 TLS 若支持)· `nonce`+`timestamp` 重放窗口收紧到分钟级并落库去重(优盾侧不保证) | 抗误传与扫描 |
| L2 报文 | 验签照做,但**降级为"抗误传",不作为入账授权** · `tradeId`/`businessId` 幂等 · 金额/地址/币种与平台自有单据逐字段比对,任一不符即挂起不入账 | 抗篡改 |
| **L3 真锚** | **回调只当"去链上看一眼"的触发信号。入账依据一律回链自证**:按 `txId` 用平台自有数据源查回 → 合约地址**逐字节匹配** · 收款地址属本平台映射库 · 金额一致 · 取到**区块哈希** · 确认数达该金额档门槛 · 再经重组保留深度未回滚 | **唯一授权依据** |

🔴 一条 L3 同时堵掉四个洞:MD5 弱 · 无确认数 · 无区块哈希 · 回调可伪造。且它**本就是上游 CHAIN 的入账判据**(L501/L512/L547),不是新发明。
🔴 **代价必须写进采购**:L3 意味着平台仍需**至少一路(建议两路互相独立)链上数据源** —— 接优盾**省不掉**这笔。
🔴 **不做 L3 的后果**:谁拿到 `key` 谁就能给任意账号铸余额,铸出来的余额走自动放行档提走 —— 与上游负债侧对账要防的攻击同形,只是入口从"改业务库"换成"发一条伪造回调"。

### 4.2 单机热钥的爆炸半径 → **无上界(= 链上全部资金),且失陷点是一台常年开机的 PC**

按上游"在线被完全攻陷时盗损有明确上界"的口径算:

> **上界 = 该助记词派生的全部地址上的全部资产** = 全部用户收款地址 + 热钱包 +(若同树)出账账户与手续费账户。

成因:一组助记词 → 一棵 HD 树 → 拿到它可直接在链上签走每个地址的钱,**不经优盾云、不受任何限额约束**(限额是优盾控制台的工单流程,链上签名不问它)。上游把上界压到"浮存额"的那套结构(出账账户独立 · 私钥归出金域 · 分片集合互不重叠)**在这里整个不存在**。

| 能做到 | 做不到(须显式声明为未兑现) |
|---|---|
| ① **敞口上限**:收款地址到阈值即归集走,热侧只留 T+1 出金所需,其余转**平台自持冷存** ← **唯一真正压缩半径的手段** | 分片不重叠 |
| ② 归集机专机专用 · 除优盾外全禁网 · 全盘加密 · 物理管控 · 操作留痕 | 门限签名 / 「任何单人不能独立动资金」 |
| ③ 助记词分段离线备份、异地保管、按上游备份登记表登记 | 签名侧硬上限 |
| ④ 优盾控制台开双人复核、**关闭"代付"自动放行** | 所见即所签 |
| ⑤ 提币地址白名单(**须问优盾是否支持**)· 硬件钱包持钥(§0.5,须问与自动归集是否兼容) | 归集域 / 出金域隔离 |

🔴 **本条最重要的一条架构硬约束:冷存必须平台自持,不能放在优盾里。** 否则爆炸半径 = 平台全部资产,而非热侧余额。
🔴 **参数化交付**:「优盾树上任意时刻余额上限」为可配参数(建议锚在日均提现额的倍数),超过即强制归集到自持冷存,并在 N 域给出水位与超限告警。**这条把定性风险变成一个可管理的数字。**

### 4.3 到期禁用 + 赎金的退出路径 → **让赎金条款对我们不适用**

🔴 **核心结论**:赎金条款是给"把私钥交给对方托管、只能求它还钱"的商户准备的。**我们的设计从第一天就不进入那个状态** —— 私钥主权自持(§0.5 协议原文:私钥在商户本地),因此**商户号被禁用不等于资产被扣留**。谈价不是解法,不进入那个状态才是。

| # | 环节 | 内容 |
|---|---|---|
| **E1** | **私钥主权自持 + 脱离演练** | 助记词由平台持有并离线备份。**上线前置**:用一笔小额,在**完全不经优盾**的情况下用备份助记词离线签名并广播成功 —— 这叫脱离演练,**不通过不得上线**,此后按周期复演(照上游 CHAIN05 演练判据分层) |
| **E2** | 敞口最小化 | 同 §4.2 ①,被禁用时暴露的资产量有界 |
| **E3** | **映射库自持** | 「地址↔账号↔派生索引」由平台自己落库 + 独立备份 + 异地留存 + 定期恢复校验。**丢了才是真正不可逆的损失**——钱在链上,但不知道是谁的 |
| **E4** | 退出触发器(自动侦测,不等被禁才发现) | 接口返回 `4166`/`4169`/`4226`/`4261` · 回调停摆超阈值 · 套餐到期日 T-30 / T-7 未续 → 自动置**通道降级位**:停发新充值地址 · 前端改引导另一通道或暂停充值 · 出金转人工 |
| **E5** | 撤离剧本(可演练 · 有 RTO) | 声明退出 → 停止新地址分配 → 用自持助记词把全部派生地址与热钱包资产扫到自持冷存(**不经优盾**)→ 老地址继续被动监听(用户仍可能打钱)→ 保管期与报案照上游 CHAIN05 链退役条款 → 注销商户号。**RTO 目标与演练周期写进规格** |
| **E6** | 合同前置(**主人行动项,非技术项**) | 签约前书面拿到:① 到期/停用后资产取回的流程、期限与费用(**白纸黑字,不接受"以帮助中心为准"**)② 单方停服的判据与申诉通道 ③ 调价提前通知期 ④ 签约主体与 Cregis 品牌迁移后的旧线承诺(§0.8)。**这四条谈不下来,就把 E2 的敞口上限设得更低** |

## 五、待主人拍板(3 项 · 每项带选项 / 我的推荐 / 不做会怎样)

### 拍板 1 🔴 接入深度 —— 这是本规格的总开关

核完接口后有一个绕不开的第一性问题:**为满足上游判据,反正要自接链上数据源、反正要自持冷存、反正要自持助记词并具备离线签名能力 —— 那优盾还剩什么?** 剩「地址派生的工程实现」与「提币工单的 UI 流程」,而这两样恰是自建线里工作量最小的部分。

| 选项 | 内容 | 代价 / 风险 |
|---|---|---|
| **A 厚接入** | 全信优盾:回调即入账 · 归集用它的 PC 客户端 · 冷存也放优盾 | 最快(粗估 2-3 周)。接受两个风险:**余额可被伪造回调铸出** · **一台 PC 一锅端全部资产**;退出看对方脸色 |
| **B 薄接入(推荐)** | 只用它三样:地址派生 + 回调触发 + 提币工单。平台自持助记词备份 · 自持冷存 · 自接链上数据源做入账自证 · 自建归集脚本作为脱离能力 | 同时拿到"快速上线"与"退出主权"。仍要建上游约 60-70%(账本/对账/风控/熔断/N 域**本来就要建**,真正新增的只有一路链上读取 + 一个归集脚本) |
| **C 不接,直接自建** | 回到包 D | 最慢,但无对手方 |

**我推荐 B**,并配一条硬约束:**优盾树上任意时刻余额上限**(可配参数)。理由:它把 A 与 B 的风险差距量化成一个能管理的数字,而不是一句"我们小心点"。
🔴 **中间地带不成立**:要么按上游判据接(B),要么承认放弃那些判据(A)。**默认"接了优盾就又快又安全"是错的** —— 这是我这次核源后最想让主人先知道的一句。
**不做会怎样**:不定这一项,后面 6 个功能单元没法写 —— 归集、对账、冷存、退出四条线的写法全由它决定。

### 拍板 2 归集怎么做(优盾**无归集 API**)

| 选项 | 代价 |
|---|---|
| ① 人工按日用优盾 PC 客户端归集 | 要人守;PC 须常年开机 = 攻击面常驻 |
| ② 不归集,出金时从收款地址直接付 | 省事,但每笔 gas 更高,且暴露面 = 全量地址余额 |
| **③ 自建归集脚本(用自持助记词,绕开优盾客户端)** | **推荐**。它同时就是 E1 脱离能力的日常验证,并把优盾降级为"只发地址 + 推回调" |

**不做会怎样**:归集不落定,§4.2 的敞口上限没有执行手段,爆炸半径压不下来 —— 那么拍板 1 选 B 也只是名义上的 B。

### 拍板 3 过渡期对外口径

过渡期**不得**对外宣称多签 / 冷存托管 / 机构级密钥保管(§2.2 已列为结构性降级,**说了就是不实陈述**)。需要主人认可,因为它影响转化文案与后台标签。
**不做会怎样**:文案里出现"多签保管",而实际是一台 PC 上一组助记词 —— 这是最不该踩的一类风险。
