## 1. 权威边界与调用链

M1 只聚合权威事实，不自行创造工单、会话、SLA 或坐席样本：

```text
M2 工单 + M3 会话 + M4 SLA + M5 坐席
  -> /content/tickets + /conversations + /support-agents + /support-knowledge
  -> M1 KPI / SLA 风险 / 坐席负载
  -> 四条深链回到 M2/M3 对应过滤队列

M1 可见负载版本
  -> PATCH load-config / POST rebalance
  -> 稳定 Idempotency-Key
  -> nx_config_item version SELECT ... FOR UPDATE
  -> expectedVersion CAS
  -> 配置写入 + A2 required 审计同事务
  -> 成功后刷新权威快照；409/未知结果保留表单
```

必须成立的不变量：

- “活跃工单”与 M2 `scope=active` 都是 open、in_progress、pending_user；待回复与 M3 `seg=unread` 都是未归档进行中会话且 unread > 0。
- M2/M3/M4/M5 任一独立来源失败，只关闭受影响事实集并明确告警，不能伪装为真实 0，也不能拖垮其他健康区块。
- 配置重放靠幂等键；不同运营员并发靠 visible version CAS；两者不能互相替代。
- 负载和坐席理由统一 8–200 字；权限拒绝、版本冲突、A2 失败或网络结果未知均不得显示成功。
- 当前 A4 registry 没有 M1 负载配置专用 canonical schema；本轮不伪造内部事件。M1 相关业务事件继续由 M2/M3 的权威业务动作生产，配置治理事实以 A2 required 审计为准。

## 5. 权限、刷新、并发与失败关闭复审

- 读取使用 `service_m1_read`；写接口使用 `service_m1_write`，控制器还要求当前账号是超管或客服主管，只有写权限但非主管仍返回 403。
- 前端在负载响应缺失时不物化写参数并禁用写入口；刷新或重登重新读取服务器快照，不从 localStorage 恢复业务配置。
- 同键同载荷重放返回同一结果；同键异载荷由持久幂等服务冲突；两个不同键提交同一旧 version，最多一个成功，另一个 409。
- 会话详情任一 500/畸形适配错误时不再用摘要补真；M4/M5 503 只影响对应区块并给出可见告警。
- 401/403、409、500、网络中断都不先关弹窗或报成功；结果未知保留同一命令内容和键。
- A2 持久化失败与负载配置处于同一事务，不能形成“配置已改但审计没有”的半成功。

## 6. 统一部署后的锁定终验

1. 串行修复共享工作树的无关 Java 编译错误，执行 M1/M2 定向测试；应用 `20260727_m1_support_load_cas.sql` 后部署 8110/3002。
2. 从可见侧栏进入 M1，逐卡比对数字与 M2/M3 落地列表行数，并覆盖 M4 SLA、M5 坐席变更后的 M1 刷新。
3. 双浏览器读取同 version，用不同幂等键并发提交：一个成功、一个 409；刷新失败方后再提交成功。
4. 验证理由 7/8/200/201、无权限角色 403、同键重放、同键异载荷、响应中断同键重试。
5. 注入工单/会话详情 500 与畸形 200、M4/M5 503；核对错误不等于 0、受影响区块失败关闭、健康区块仍可用。
6. 核对 `nx_config_item` version、A2 before/after、actor、reason、Idempotency-Key；注入 A2 失败确认业务回滚。
7. 精确恢复配置和夹具，由非 M1 修复者从可见入口执行同范围初审与复审后，才把本报告改为最终通过。
