## 二、业务对象与调用链

J3 是服务器权威篡改拒绝事件的只读可观测面，不持有账户处置权。

```text
App 敏感业务入口
→ server-canonical 校验
→ 拒绝客户端伪造状态/结果/ID
→ RISK_TAMPER_DETECTED 持久 outbox
→ TamperDetectedEventProjector
→ J3 nx_emergency_tamper_event
→ K4 风险分贡献 + B5 TAMPER_DETECTED 雷达信号
→ PC J3 总览/路径/账户告警
→ C2 精确账户或 K1 精确风险簇处置
```

权威接口：

- `GET /api/admin/emergency/tamper/overview?window=&accountPage=&accountPageSize=`
- `GET /api/admin/emergency/tamper/config-alerts`
- `PUT /api/admin/emergency/tamper/alert-config`
- `POST /api/admin/emergency/tamper/reports`

权威数据：

- `nx_event_outbox`：服务器拒绝事件。
- `nx_event_consumer_delivery`：J3 投影消费回执。
- `nx_emergency_tamper_event`：J3 事件事实。
- `nx_risk_signal` / K4 风险贡献：B5/K4 下游投影。
- `nx_emergency_control_setting`：J3 阈值与 K4 开关。
- A2 审计：总览读取、配置成功/拒绝/失败、报表导出。

## 四、缺陷闭环

### [P0] PCFULL-179 · 试用篡改拒绝未进入 J3

复现与证据：

1. 技术链路从真实控制器追踪 `/api/trial/eligibility`。
2. H2 `AppTrialLifecycleService.state(userId)` 返回服务器权威状态。
3. 客户端 `clientStatus` 冲突时，控制器直接 `ApiResult.fail(409, "TRIAL_STATE_CONFLICT")`，没有调用 `TamperDetectionPublisher`。
4. `/api/trial/charge` 收到客户端 `chargeSucceeded/chargeFailRate` 时也直接返回 409，没有发布事件。
5. `TamperCoverageRegistry.ACTIVE = REGISTERED` 仍把两条路径算作已接线，页面因此错误显示 11/11。

根本原因：

H2 用真实生命周期服务替换旧 canonical 试用实现时，只迁移了业务拒绝结果，没有迁移 J3 server-only 事件发布职责；旧服务单测继续直接调用已不再承接真实路由的实现，形成了“测试通过但生产路由漏事件”的替身测试。

影响：

- J3 低报两类真实篡改尝试。
- K4 风险分缺少对应贡献。
- B5 雷达缺少对应风险信号。
- 11/11 覆盖状态不真实。
- 运营可能把“零事件”误判为没有攻击尝试。

实际修复：

- H2 权威状态比较仍在真实控制器完成；试用状态冲突后调用 server-only `rejectTrialStateTamper`，避免 J3 再读取第二份试用状态。
- 客户端伪造扣款结果时委托 canonical `chargeTrial` 的持久幂等范围；同一 `Idempotency-Key` 的响应丢失重试不会重复生成 J3/K4/B5 事件，且不会进入 H2 真实结算。
- 两类路径仍返回原 409，且不执行领取、扣款或结算副作用。
- 新增控制器单测，锁定真实路由必须委托事件发布；扣款篡改时明确禁止调用真实 charge。
- PC 跨仓合同锁定真实控制器与 server-only 路径名、端点。

## 五、墨菲定律审查

- 客户端伪造试用状态：服务器 409，修后必须同时发 `free_trial_state`。
- 客户端伪造扣款成功/失败率：服务器 409，修后必须同时发 `charge_fail_rate`，不得执行钱包/D4/设备写入。
- 客户端不能提交 `isServerAuthoritative`：该字段只在 server-only publisher 内生成。
- 未知路径：publisher 和 projector 均使用 11 项白名单，未知路径失败关闭。
- 非 server-canonical 事件：projector 拒绝 `TAMPER_EVENT_NOT_SERVER_CANONICAL`。
- 同一事件重复投递：消费回执和事件唯一标识用于防重复计数。
- J3 配置并发：页面提交 expected 快照；后端业务互斥行先于幂等记录加锁，陈旧页面 409。
- 配置结果未知：同一人工命令保留原幂等键；页面不宣称成功或失败。
- 配置已提交但刷新失败：明确“已生效并已记审计，页面刷新失败”，不重复提交。
- 报表已生成但浏览器下载失败：只重试本地下载，不重复生成报表或审计。
- 503/协议异常：页面清除不可确认的高风险操作，显示重试出口。
- J3 不直接冻结：只在有目标权限且告警态合法时显示 C2/K1 深链；最终处置在目标域重新确认。
