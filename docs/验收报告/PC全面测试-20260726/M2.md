## 1. 锁定范围与权威边界

PRD v4 的模块名仍是 `[I6a]`，当前产品导航名为 M2；本轮按业务能力而不是编号字面锁定同一范围：

| 能力 | 权威来源 | 不变量 |
|---|---|---|
| 列表、搜索、分类/状态筛选、分页与空态 | `nx_support_ticket` + 后端分页 | 读取失败或协议歧义不能伪装为空队列；服务端总数必须完整取回 |
| 回复、状态、优先级、负责人、解决/关闭/重开 | 工单详情可见 `status + version` | 同一意图稳定幂等；不同意图并发由数据库 CAS 裁决；成功后再回读 |
| 已解决与已归档 | `status` 与 `archived` 两个独立字段 | 只有终态可归档；归档可恢复；恢复后仍是已解决队列，不偷改状态 |
| 内部备注 | 独立 `internal` 消息 | 不作为用户回复；专权、幂等、CAS、A2 必达审计 |
| SLA | M4 服务端 SLA 快照 | 抽屉展示当前分类的首次响应、解决目标、队列与升级口径 |
| M2 → M3 升级 | 工单真实用户 + 可接单客服 + 单事务 | 工单轨迹与会话同时成功或同时回滚；保留真实 userId、ticketNo、conversationNo |
| C1/C/D/E 深链 | 后端 `nx_user` 存在性 | 只有服务端确认用户存在才开放；M2 不代替 D2/K5 做资金或合规裁决 |
| 权限、审计、刷新重登 | A8/RBAC、A2、服务器快照 | 无 `service_m2_write` 不出现写入口；客户端不持久化权威业务状态 |

锁定的失败分支包括：401/403、404、409、422、500、HTTP 200 畸形、Ghost 负责人、幽灵 userId、分页中断、重复点击、结果未知重试、不同键并发、归档非法状态、会话创建失败、审计失败、刷新与重登。

## 3. 初审发现与修复闭环

| 缺陷 | 级别 | 初审证据 | 修复 |
|---|---|---|---|
| PCFULL-270 稳定幂等键未穿透 M2 API | P1 | `runMWrite` 保存 key，但 `writeTicketRows` 与升级调用未传入客户端，结果未知后重试会换键 | 新建、回复、状态、优先级、负责人、归档、内部备注、升级均接收同一 key；成功写入并回读后才清除 |
| PCFULL-271 不同意图并发无 status/version CAS | P1 | 原 SQL 仅按 ticketNo 更新，可静默覆盖另一运营员刚完成的写入 | 新增 `version` 列与迁移；请求强制携 `expectedStatus + expectedVersion`；单条 SQL 比对并递增，缺前置 422、陈旧/竞态 409 |
| PCFULL-272 畸形 200 和分页缺页失败开放 | P1 | 宽松适配会把缺 records/total、坏详情或空的后续页补成可写空队列/默认工单 | 列表、分页完整性与详情整体校验；任一歧义全有或全无，`ticketsAvailable=false` 并关闭写入口 |

完整缺陷记录位于 `docs/验收报告/PC管理端全面测试缺陷记录-20260726.md`。

## 4. 修复后调用链

```text
M2 权威详情(ticketNo, status, version, userExists)
  -> PC 保留 logical command + stable Idempotency-Key
  -> 请求携 expectedStatus + expectedVersion
  -> Service 校验权限/载荷/状态/真实用户
  -> UPDATE ... WHERE ticket_no + status + version
  -> version = version + 1
  -> 同事务消息/内部备注/会话 + A2 必达审计
  -> 后端确认成功
  -> PC 重新读取全量分页与每条权威详情
  -> 才显示成功并清除 pending command
```

关键审查结论：

- 同键同载荷重放由持久幂等返回原结果；同键异载荷拒绝。结果未知时 value、基线、reason 和 key 均保持不变。
- 不同键并发不依赖幂等表碰运气，数据库行的 status/version CAS 只允许一个旧快照写成功。
- M2→M3 先以工单可见版本原子领取升级轨迹，再创建绑定真实用户的会话；`@Transactional` 保证会话、轨迹或审计任一步失败都不留下半链。
- 负责人只接受 M1 返回的启用、允许转交且包含 support 服务类型的真实客服；服务端再次校验，Ghost owner 返回 404。
- 内部备注只增加 internal 时间线与版本，不覆盖 `last_message` 冒充最近对客回复，也不会发送给用户。
- C1 支付方式、分类跨域链接和 M3 升级都要求 `userId > 0 && userExists=true`；D2 提现和 K5 合规仍由 owner module 裁决。
- 读取侧拒绝未知状态/分类/优先级、缺版本/用户存在性、坏消息、分页缺页与畸形 200；失败后不提供任何写操作。

## 6. 墨菲定律对抗复审

- 第一次请求已提交但客户端超时：重试必须复用同一 key 与原始快照，不新增第二条回复、会话或审计。
- 两个运营员从 version=7 同时改负责人/状态：只允许一个成功，另一个 409；失败页保留输入并提示刷新。
- 状态在读后写前已变化：即使 version 意外相同，expectedStatus 也必须阻断；反之状态相同但 version 变化也必须阻断。
- HTTP 200 缺 ticket、缺 version、userExists 为字符串、未知枚举、坏消息时间或 total 大于已返回记录：整组工单不可用，不显示“0 条”。
- Ghost owner、幽灵 userId、删除中的用户：负责人写 404；C1/跨域/M3 入口关闭；直接调用升级 API 仍 422。
- 已解决、已关闭、已归档相互独立：非法归档 409；恢复归档不重开；重开不自动取消归档之外的未知副作用。
- 内部备注与对客回复并发：CAS 只允许一个旧版本成功；internal 内容不进入用户侧，也不改变对客最近正文。
- 会话创建、A2 审计或幂等完成标记失败：整个升级事务回滚，工单轨迹和会话不能单边存在。
- 401/403、500、网络中断：页面不显示成功、不推进本地状态、不清空回复/内部备注输入。
- 刷新、退出和重登：只从当前账号可访问的服务器快照重建；旧账号、旧权限和 pending UI 不泄漏。

## 7. 统一部署后的锁定终验

1. 串行执行后端聚焦与全量测试，应用 `scripts/migrations/20260727_m2_ticket_cas.sql`，部署同一候选的 8110 与 3002。
2. 从登录页和可见侧栏完整重跑搜索、分类/状态筛选、8/15/30 分页、详情、空态、刷新与退出重登。
3. 使用可回滚夹具依次执行 open → in_progress → pending_user → resolved → archived → unarchive → reopen → closed，逐步核对 DB、页面、版本、消息与 A2。
4. 验证回复、优先级、真实负责人转交、内部备注和分类 SLA；内部备注不得出现在用户端或对客最近消息。
5. 两浏览器从同一版本对回复/状态/负责人/优先级/归档/内部备注逐类并发，核对单成功、单 409 和无覆盖。
6. 对每类写注入超时、同键重放、同键异载荷、500、审计失败和畸形 200，确认结果未知重试恰好一次且输入保留。
7. 以真实用户工单升级 M3，核对同一 userId、双方交叉链接、单会话、单轨迹、单审计；注入会话创建失败确认全回滚。
8. 使用幽灵用户、Ghost owner、无权账号和匿名账号验证 422/404/403/401，确认 UI 与直接 API 双侧失败关闭。
9. 从 M2 深链进入 C1 支付方式和 C/D/E owner 页面；提现与 KYC 只允许进入 D2/K5 处置，不在 M2 直接放行。
10. 精确清理验收工单、消息、会话、幂等和业务夹具，保留审计证据；由未参与 M2 修复的子智能体从可见入口按同一范围执行初审与复审。

## 8. 第一性原理、评分与血量

第一性原理是“工单成功不是页面按钮变色，而是同一权威版本上的业务写、消息/会话、审计和重新读取完全一致”；奥卡姆剃刀要求一条工单权威行、一套持久幂等和一个数据库 CAS，不复制前端状态机；贝叶斯证据严格区分旧运行态浏览器证据、当前源码合同证据和部署后真实写证据；墨菲定律覆盖超时、并发、幽灵实体、畸形成功、审计失败和半事务。
