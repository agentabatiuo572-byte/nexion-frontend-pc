## 第一性原理闭环

兑换的最小业务事实不是页面数字，而是“同一服务端报价与风控快照下，一次幂等命令原子改变订单、钱包、账本、手续费资金池和事件”。据此检查：

1. 报价只认 G3 `nx_price_index`，caps/费率只认 G2 `nx_config_item:wallet.exchange.*`。
2. KYC 只认 C4/K5 服务端状态，地域只认 J2，熔断恢复只认 J1。
3. 客户端只提交方向、原始数量、是否接受排队和幂等键，不提交价格、到账额、费率或 gate 结论。
4. 成交必须同时闭合钱包、兑换单、D4 双账、手续费 30/70 分配与 `exchange.swapped`；任一失败回滚。
5. 排队不扣余额；处理批次用当时 G3 价格和最新 G2/C4/J2 规则重验；取消只改变可取消订单状态。

奥卡姆剃刀的修复选择是直接复用现有 `/api/exchange`，没有在 App 再造一套远端 store 或公式。贝叶斯更新中，源码同时出现 localStorage、随机报价、本地余额写与服务端现成真实接口后，“用户兑换可能是假成功”从风险假设升级为 P0 证实缺陷。墨菲审查进一步假设重试、并发、未知响应、队列跨日、费率开启、账户 CAS 冲突、刷新和重登都会发生，因此命令保留稳定幂等键、响应严格解析、资金分配失败关闭。

## 权限、幂等、CAS 与跨域审查

- 权限：PC 按 `finprod_g2_cap_*`、`finprod_g2_fee_rate_write`、`finprod_g2_write`、`finprod_g2_swap_toggle` 裁剪；后端服务再次校验精确权限。匿名读取管理 BFF 被拒。
- A2/CAS：对象被 A2 锁定时参数、swap、订单动作返回 409；队列取消只允许 `QUEUED`，批次完成使用状态条件更新；钱包更新禁止负余额并递增 version。
- 幂等：PC mutation key 在未知结果时保留；App swap/cancel key 在失败时保留；后端按 scope+payload 指纹执行一次，不同 payload 冲突关闭。
- B1：提高用户/平台 cap、降低费率/最低费、REJECT→QUEUE、恢复 swap 均由服务端红线校验；G2 只允许止血暂停，恢复归 J1。
- G3：用户与队列成交都从服务端当前价格计算，不接受客户端报价。
- C4/K5：累计达到阈值且未认证时生成 KYC_REQUIRED 与 K5 工单；客户端镜像无法绕过。
- J2：地域命中由服务端 gate；在队单处理时重验。
- D4/D3：成交原子写双资产钱包账本并发布 `exchange.swapped`；NEX→USDT 由下游反映资金池流出。
- D1/G3 手续费：30%/70% 账户及流水均带 exchangeNo 唯一证据，总额等式由数据库 CHECK 约束。
