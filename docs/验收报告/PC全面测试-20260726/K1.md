## 三、PCFULL-185 修复闭环

### 3.1 三层真实证据

K1 事实查询以 `nx_user` 为账户根，统一投影：

- IP：最近 24 小时已消费 `nx_user_registration_otp.client_ip`，按手机号和国家码关联真实账户。
- 设备：`nx_risk_decision.device_fingerprint`。
- 支付：活动/已绑定/已验证 `nx_wallet_bank_card.card_token`。

支付去重使用支付工具 token，不使用 BIN。BIN 只能代表一组发卡号段，拿 BIN 识别“同一支付工具”会大面积误判。PC 只显示品牌和尾四位，原 token 只在服务端内部参与去重。

IPv4 只展示 `/24` 掩码；其他地址只展示前缀。聚类计算仍使用原始服务端键，页面不暴露完整 IP、指纹或卡 token。

### 3.2 用户、邀请与资金上下文

每个聚类节点的上下文来自：

- sponsor：`nx_user.sponsor_user_id`。
- 新人礼：`nx_referral_reward_settlement` 中已完成结算事实。
- 累计入金：优先 `nx_user_wallet.cumulative_deposit_usdt`；仅在字段缺失时回退到已成功、USDT、入账方向且属于认可入金业务类型的 D4 ledger。
- 账户状态：直接使用 `nx_user.status`；空值保持未知，不把未知伪造成 ACTIVE。

这组字段只帮助运营判断风险影响，不由浏览器计算资金或自行决定冻结。

### 3.3 注册入口失败关闭和并发

OTP 校验通过但创建账户之前，注册事务按顺序执行：

1. 从已消费 challenge 回读服务器记录的 client IP。
2. IP 缺失或为 `unknown`：503 `USER_REGISTRATION_CLIENT_IP_UNAVAILABLE`。
3. 对 K1 `maxSignupPerIp24h` 参数行执行 `SELECT ... FOR UPDATE`。
4. 参数缺失、非整数或不在 1–10：503 `USER_REGISTRATION_K1_CONFIG_UNAVAILABLE`。
5. 统计该 IP 过去 24 小时已真正创建的不同账户。
6. 已达到上限：409 `USER_REGISTRATION_K1_IP_LIMIT`。
7. 只有通过以上检查才解析 sponsor、创建 `nx_user`、安全记录、钱包、注册 outbox 和 session。

同一 K1 参数行锁让不同请求编号、不同手机号的并发注册串行通过“读取当前计数 → 创建账户”临界区；幂等键不是并发上限的唯一保护。

### 3.4 H8 资金入口

所有 H8 待结算查询均把 K1 活动风险定义统一为：

```text
detected / flagged / frozen
```

命中任一状态即不进入新人礼/邀请奖励钱包写入，且与调用方是否选择 `holdRisky` 无关。`released/cleared` 才允许按 H8 原有 A2 快照、互斥锁、唯一结算键、钱包、D4 和 A4 链继续。

### 3.5 PC 提示

## 七、墨菲定律审查

- 两个注册请求在同一毫秒通过计数：参数行 `FOR UPDATE` 串行化，不依赖应用内锁。
- K1 参数表缺行或被写成非法文本：注册 503，不采用默认值放行。
- 代理未提供可信 IP：注册 503，不把 `unknown` 聚成巨大误判簇，也不绕过上限。
- 同一手机号反复消费 OTP：计数只统计已存在的不同账户，聚类 IP 事实仍需要已消费 OTP 与真实账户关联。
- 支付 token 为空或银行卡非活动：不进入支付簇。
- 相同 BIN 的不同卡：不会被视为同一支付工具。
- gift/deposit/account status 缺失：保留未知，不伪造为 0/ACTIVE。
- detected 尚未人工 flagged：H8 已阻断，避免“调度器先发钱、运营后处置”的竞态。
- released 后重跑 H8：仍受 H8 唯一 settlement 和幂等回执保护。
- A2 提案等待期间簇版本变化：批准回放仍须经过目标域 expected version/CAS。
- C2 同时被其他风险源冻结：K1 release 只释放 K1 source，不能覆盖其他域所有权。
- K1 overview 读失败：页面不保留旧写按钮。
- PC 成功响应丢失：同一命令键重试并先回读权威状态，不能生成第二条业务命令。
