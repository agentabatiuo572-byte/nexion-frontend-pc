## 第一性原理闭环

E5 的业务目标不是“后台有几个动作按钮”，而是让运营人员在不破坏设备所有权、订单履约和数据中心引用的前提下，安全改变真实设备运营状态，并让结果可以确认、重放、审计和跨域传播。

最小可信链路为：

```text
PC 可见入口
→ 权限与危险动作确认
→ 普通设备动作直接执行 / 高风险动作创建 A2 申请
→ 服务端状态机、设备上限、引用保护与幂等校验
→ nx_user_device / nx_compute_datacenter 等权威表
→ A2 审计 + A4 outbox/consumer
→ E1/E2/E3/E4/E6/J1 与 App 设备状态重新读取
→ 刷新、重登和失败恢复后仍与权威事实一致
```

按奥卡姆剃刀，不再为数据中心动作增加第二套前端约束，而是在五个真正写入的服务方法入口统一要求 `A2ReplayContext`。按贝叶斯更新，最初“PC 已经走 A2，可能安全”的低风险判断，在直调服务测试出现三个 `code=0` 后更新为已证实 P1 权限旁路。按墨菲定律，假设任何持有业务权限的调用方都可能绕过 PC，因此保护必须位于幂等写入和数据库变更之前，不能依赖按钮隐藏或前端提案逻辑。

## 缺陷与修复

| 编号 | 级别 | 现象 | 根因 | 修复 |
|---|---|---|---|---|
| PCFULL-036 | P1 | PC 会创建 A2 申请，但持有 E5 写权限的客户端可直接调用数据中心新增、编辑、删除、暂停、恢复接口并立即改变业务事实 | 五个服务方法仅检查 A2 对象锁，没有要求调用来自已批准的 A2 replay | 参数校验后、幂等和写入前统一检查 `A2ReplayContext.isReplaying()`；非 replay 全部返回 `409 A2_CONFIRMATION_REQUIRED` |
| PCFULL-037 | P2 | 删除确认窗声称系统没有跨域硬阻断、会保留 `dc_location` 孤儿引用 | PC 文案停留在旧方案，未同步现行服务端引用保护 | 文案改为明确 E5 设备、E4 待履约订单、E1 SKU 三类引用计数必须全部为 0；删除后同步清理运营状态且不删除设备库存 |

### PCFULL-036 修前证据

新增回归测试：

```text
OpsDeviceServiceTest.e5DatacenterMutationsRequireA2ReplayEvenWithBusinessPermission
```

修前结果：

```text
Tests run: 1, Failures: 1, Errors: 0, Skipped: 0
create  -> code 0
update  -> code 0
delete  -> code 0
pause   -> code 404（对象已被前一步直接删除）

```

这不是测试夹具误报：新增、更新和删除已经返回成功，并在同一个假仓储内发生真实副作用，证明服务端本身没有 maker-checker 边界。

### PCFULL-036 修复点

- `createDatacenter`
- `updateDatacenter`
- `deleteDatacenter`
- `pauseDatacenter`
- `resumeDatacenter`

五个入口均采用相同失败关闭规则：

```text
请求与理由合法
→ 不是 A2 replay：409 A2_CONFIRMATION_REQUIRED，不能进入幂等执行器
→ 是 A2 replay：继续对象锁、状态、引用、幂等、审计与事件逻辑
```

既有成功路径、删除引用阻断和无引用删除测试已改为显式进入 A2 replay；新直调测试不进入 replay，并断言幂等执行器零调用，防止“先写后拒绝”。

### PCFULL-037 修复点

删除确认现在明确：

- 只软删除数据中心卡片配置，不删除设备库存。
- 只要仍有 E5 设备、E4 待履约订单或 E1 SKU 引用，服务端就拒绝删除并返回引用计数。
- 三类引用全部为 0 后才允许执行。
- 仍需检查 A2 没有相关待确认申请并填写操作理由。
- 删除成功后同步清理数据中心运营状态，不能留下页面宣称的孤儿引用。

## 权限、幂等、状态与异常审查

| 维度 | 当前工程结论 | 统一部署后必须实测 |
|---|---|---|
| 读取权限 | E5 页面和接口受设备运营读权限控制 | 只读角色可查看，匿名 401，完全无权限角色 403/菜单不可见 |
| 普通激活/取消激活 | 由 `device_e5_write` 直接执行，服务端状态机约束 | 合法前态成功，非法前态 409，刷新/重登持久 |
| 强制激活/解绑 | PC 走 A2；服务端已存在 replay 硬门禁 | maker 不得自批，checker 执行；直调始终 409 |
| 批量暂停/恢复 | 用户级批量命令，要求理由和幂等键 | 结果计数准确、重复请求无重复副作用、部分失败不能伪报全成功 |
| 数据中心增改删/暂停恢复 | 本轮补齐五动作 replay 硬门禁 | UI 建议 → A2 → checker → 服务端落表；所有直调 409 |
| 每用户 6 台上限 | 激活和强制激活均检查有效设备数 | 第 6 台边界成功/保持，第 7 台失败；A2 不能绕过 |
| 删除引用保护 | 设备、待履约订单、SKU 任一计数大于 0 均拒绝 | 返回三类真实计数且零副作用；清理引用后才允许 |
| 幂等 | 服务方法经稳定 scope + key 执行 | 同键同 payload 返回同结果，同键不同 payload 冲突关闭 |
| 对象锁/CAS | 非 replay 写检查 A2 活跃对象锁 | 并发提案只有一个可执行；被锁目标的直接普通写安全拒绝 |
| 超时/结果未知 | BFF 写请求必须区分未提交与未知结果 | 人工注入断连，保留原幂等键，先读权威状态再决定重试 |
| 重复点击 | 前端提交态与服务端幂等共同保护 | 连续双击只产生一次业务变更、一次有效审计和一条 outbox |
| 审计/A4 | 代码记录规范事件和必要理由 | 核对审计操作者/理由/before-after、outbox PUBLISHED、consumer SUCCESS |

## 域内外调用链审查

| 交界 | 业务不变量 | 最终运行态断言 |
|---|---|---|
| E1 → E5 | SKU 的数据中心引用不能在 E5 被悬空删除 | 被任一未删除 SKU 引用时删除返回 `DATACENTER_HAS_REFERENCES`，并带 `skuCount` |
| E2 → E5 | 全局任务可派不代表故障设备/DC 可接任务 | 设备或 DC 暂停后新任务不得派发；恢复后按 E2 当前配置执行 |
| E3 → E5 | E3 生命周期是设备真实阶段，E5 运维不能伪造或回退生命周期 | 激活/取消激活只改变允许运营字段，不能覆盖报废/回收终态 |
| E4 → E5 | 待履约订单依赖设备和数据中心；激活事实决定 E4 是否可进入 activated | 有待履约订单时 DC 删除被阻断；设备实际激活后 E4 才可确认完成 |
| E6 → E5 | E6 配置提供计算/资格参数，E5 展示运行状态 | E6 参数变化不得伪改历史运行快照；E5 的当前可用性仍以真实设备状态为准 |
| J1 → E5 | 紧急开关优先于普通运营动作 | 紧急停派开启时，E5 恢复 DC/设备也不能绕过全局开关 |
| E5 → A2 | 高风险设备动作与全部数据中心变更必须 maker-checker | maker 申请、checker 执行、直接 API 409、对象锁和拒绝审计完整 |
| E5 → A4 | 成功动作发布规范事件，下游可追踪 | `admin.device_activated`、`admin.device_deactivated`、`admin.datacenter_*` 的 schema/outbox/consumer 一致 |
| E5 → App | App 用户设备状态来自同一权威设备事实 | PC 操作后 App 前台刷新读取新状态；接口失败时不能回退本地伪状态 |

### E5-R02 列表、筛选、分页与真实指标

### E5-R03 普通激活与取消激活

1. 用隔离夹具准备合法前态设备。
2. 从可见按钮输入理由并确认激活。
3. 核对响应、`nx_user_device`、页面刷新、审计和 `admin.device_activated`。
4. 再执行取消激活并核对 `admin.device_deactivated`。
5. 刷新和重登后结果不回退。
6. 对非法前态执行同一动作，必须 409 且零副作用。

### E5-R04 用户批量暂停与恢复

1. 准备同一用户多台不同运行态设备。
2. 从页面执行批量暂停，核对实际受影响设备和返回计数。
3. 相同幂等键精确重放，状态、审计和事件不得重复。
4. 相同键不同 payload 必须冲突关闭。
5. 执行恢复并核对原本不应变更的终态设备保持不变。
6. 模拟部分失败和请求结果未知，页面不得显示虚假全成功。

### E5-R05 强制激活与解绑的 A2 闭环

1. maker 从 E5 可见危险动作入口创建强制激活申请。
2. maker 尝试自批必须失败。
3. checker 从 A2 可见入口批准并执行。
4. 返回 E5 刷新，核对设备状态、审计、事件和每用户 6 台上限。
5. 同一设备执行解绑，重复 maker-checker 流程。
6. 对两个直接业务端点发合法请求，均必须返回 `409 A2_CONFIRMATION_REQUIRED`。

### E5-R06 数据中心五动作 A2 闭环

1. maker 依次从 E5 发起新增、编辑、暂停、恢复和删除申请。
2. checker 执行，每一步均返回 E5 核对持久化状态。
3. 在每一步之前对对应直接端点发合法请求，必须 409，且幂等记录、业务表、审计、outbox 均无新增。
4. 同一目标存在活跃提案时，第二提案或越权写失败关闭。
5. 暂停后新派单停止；恢复后仅在 J1 允许时恢复。

### E5-R07 数据中心删除引用保护

1. 分别准备 E5 设备引用、E4 待履约订单引用、E1 SKU 引用和三类同时引用。
2. 通过 A2 执行删除。
3. 四种场景都必须返回 `DATACENTER_HAS_REFERENCES` 和正确计数，数据中心、设备、订单、SKU、运营状态零副作用。
4. 清理全部引用后再次执行才成功。
5. 页面确认文案必须与服务端实际保护一致。

### E5-R08 每用户六台设备上限

1. 准备 5 台、6 台和 7 台边界夹具。
2. 普通激活与 A2 强制激活分别执行。
3. 不能通过强制动作、批量恢复或并发请求绕过 6 台上限。
4. 两个并发激活最多一个成功，并核对最终数据库计数。

### E5-R09 权限与越权

1. 只读角色：可进入 E5，所有写按钮不可见。
2. maker：能创建被授权提案，不能批准。
3. checker：能批准但不能借审批获得未授权业务权限。
4. 无 E5 权限角色：菜单/页面/接口均拒绝。
5. 匿名上下文：401。
6. 伪造前端 operator、越权 userId/deviceId、跨 DC 参数均由服务端拒绝或使用可信登录身份。

### E5-R10 超时、结果未知与防重复

1. 在五类代表动作提交后、响应返回前注入上游断连。
2. 页面必须明确“结果未知”，保留原幂等键，不得自动生成新键盲目重试。
