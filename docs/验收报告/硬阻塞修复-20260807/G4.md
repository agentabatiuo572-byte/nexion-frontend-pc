## 1. 首要裁决

本轮声称的通用 500 缺陷已修复，代码路径与新增单测一致：

1. `GenesisCatalogService.redeem()` 在 `redeemedCount(userId)==0` 后执行条件更新。
2. 若另一个不同邀请码事务已先为该账号落库，数据库唯一键 `uk_genesis_invite_redeemed_account(redeemed_by)` 使当前更新抛出 `DuplicateKeyException`。
3. 服务现在捕获该异常并抛出 `BizException(409, "GENESIS_INVITE_ACCOUNT_ALREADY_REDEEMED")`。
4. 全局异常边界对 `BizException` 原样返回其 code/message，因此此已知并发败者不再进入通用 `Exception` 的 500 分支。
5. 新增测试 `concurrentSecondCodeForSameAccountReturnsStableConflictInsteadOfDatabase500` 直接模拟唯一键碰撞，断言 409 与精确机器码；本轮独立执行通过。

因此，“同一账号并发兑换两个不同码”的落库不变量和错误契约均已闭合：最多一个成功，败者得到稳定、可恢复、可向用户解释的 409，而不是结果不明的通用 500。

G4 总结论仍为 HOLD，不是因为本次并发修复失败，而是最终签字仍缺两类证据：真实 MySQL 双事务竞争/部分写入故障注入，以及登录态可见入口的刷新、重登、权限和关闭态撤单真实走查。另有一项非阻断契约偏差：生成器确实只生成 16-hex，但服务端和 UniApp 输入正则仍接受 `[A-Z0-9]{16}`，尚未严格收窄为 `[A-F0-9]{16}`。

## 3. 事务回滚复核

### 3.1 邀请码并发败者

- `redeem()` 是公开 `@Transactional(rollbackFor=Exception.class)` 方法。
- 用户兑换外层经 `AdminIdempotencyService.execute()`，业务 action 在 `AdminIdempotencyTransactionExecutor.runClaimed()` 的 `@Transactional(isolation=READ_COMMITTED, rollbackFor=Exception.class)` 内执行。
- 唯一键冲突被转换为运行时 `BizException` 后继续向外抛出，事务不会提交；幂等执行器随后用独立事务把命令记录标为 FAILED，便于同号重试。
- 本兑换方法在失败 UPDATE 前没有其他业务写，审计在 UPDATE 成功后才执行，所以不存在“码未核销但成功审计已落”或“两个码同时 used”的部分结果。
- 同一 Idempotency-Key 重试时，若另一事务已完成兑换，将在 `redeemedCount(userId)>0` 处稳定返回相同的账号已兑换 409。

结论：**本次 DuplicateKey 路径的事务回滚成立，不会泄漏通用 500 或部分业务状态。**

### 3.2 档位整表事务

- 三类后台档位动作仍统一经幂等执行器的 `runClaimed()` 事务运行。
- 更新档位的当前行、相邻行、`tiersVersion` 推进与审计在同一事务内；任一步抛出运行时异常，整笔回滚。
- 删除路径的相邻边界补齐、软删、版本推进、末档覆盖已售量复核与审计同属该事务。
- `AdminIdempotencyServiceTest` 继续断言 `runClaimed()` 有事务、`markFailed()` 使用 `REQUIRES_NEW`；本轮连同 G4 测试共 36/36 通过。

结论：**事务结构没有回退。** 但当前仍没有专门的 MySQL 故障注入测试证明“第一条档位 SQL 已成功、第二条或版本推进失败”后的真实表状态复原，因此该项作为最终签字证据仍记 HOLD，而非认定代码失败。
