## 2. 指定修复复核

### 2.1 canonical GET、刷新与重登：PASS

真实 PC 链路为 `fetchF5CommissionAuditOverview()` → `/api/admin/teams/commissions` → BFF 改写 `/api/admin/commissions`（PC `lib/admin/f1-client.ts:1500-1508`、`app/api/admin/teams/[...path]/route.ts:43-45`）。后端 `F5CommissionMapper.queryEvents()` 已选择 `e.version AS version` 与 `e.frozen_from_status AS frozenFromStatus`（后端 `F5CommissionMapper.java:14-28`），服务层 canonical 结果保留二者；新增测试以冻结行 `version=6/frozenFromStatus=COOLING` 验证响应未丢字段（`F5CommissionReadVersionTest.java:24-57`）。

PC 将返回值映射为 `version/frozenFromStatus`（`lib/admin/f1-client.ts:1276-1290`），行操作把当前 `row.version` 带入 A2（`f5-audit.tsx:63-70`）。刷新或重登重新 GET 后，不再把已冻结事件错误重建为版本 0。

### 2.2 自动解锁并发旧快照：PASS

到期扫描已携带 `version`（后端 `TeamCommissionMapper.java:964-981`）。自动解锁 SQL 同时约束事件 ID、`expectedVersion`、`COOLING`、到期时间与未删除标记，成功才写 `UNLOCKED` 并执行 `version=version+1`（`F5CommissionMapper.java:322-335`）。处理器只有在 CAS 恰好更新 1 行后才继续；0 行立即返回，不写操作、审计或 outbox（`CommissionEventUnlockProcessor.java:20-33`）。

因此同一到期快照并发执行时只有一个事务胜出；自动解锁成功后，旧 PC/A2 命令仍携带旧版本，服务层版本预检或 SQL CAS 稳定返回 `F5_COMMISSION_VERSION_CONFLICT` 409（`OpsTeamService.java:925-950`）。这同时封闭“自动任务对运营员”和“双运营员”竞态。

### 2.3 exactly-once、审计与回滚：PASS

CAS 胜者使用确定性 `F5-AUTO-UNLOCK-{eventId}` 同时作为 `operation_no` 与 `idempotency_key`，且只在事件已处于 `UNLOCKED/version=expectedVersion+1` 时插入（`F5CommissionMapper.java:337-355`）。迁移为 `nx_commission_operation.idempotency_key` 建立唯一约束并保存 `expected_version`（`20260807_nexion_hard_blockers.sql:235-255`）；操作号自身也受表唯一约束。

处理器以 `@Transactional(rollbackFor=Exception.class)` 包裹状态 CAS、操作记录、`recordRequired` 审计与 `COMMISSION_UNLOCKED` outbox（`CommissionEventUnlockProcessor.java:20-49`）。操作冲突抛 409；required audit 为 fail-closed 且加入调用方事务；outbox 插入异常同样向外传播。任一步失败都会回滚前序写入，重试可重新竞争；提交成功后的重扫因已非 `COOLING`/版本已推进而跳过，不能产生第二套操作、审计和 outbox。

自动解锁处理器没有资金台账依赖；手工 `COOLING/UNLOCKED/FROZEN` 路径也明确不新增 ledger（`OpsTeamService.java:1033-1056`），所以“佣金生成时已有的应付台账”不会在到期解锁时被同额再记一次。
