## 三、关键对抗结论

### 1. B1 低线与不可用

- 放宽参数和人工放行共享 `requireCoverageForAmplifyingRelease()`，不存在 PC 说有门、服务端却绕开的旧差异。
- snapshot 调用抛异常、返回 null、`reliable=false`、coverage/redline 缺失或非正数全部 503 失败关闭；真实低于红线为 422。
- 参数放宽检查发生在聚合版本行锁与跨字段校验之后、任何配置写入之前；人工放行检查发生在分录行锁之后、改桶之前。
- audit 写失败、配置第二次写失败、release 失败或幂等成功态落盘失败，均由 `runClaimed` 外层事务回滚业务写；失败元数据另用新事务记录，不掩盖原异常。

### 2. RBAC 与未知结果

- 读取保护分录仅需 `risk_k1_read`；修改释放参数和人工放行均要求精确的 `risk_k1_cluster_release`，没有回退到宽泛 `risk_k1_write`。
- PC 按同一 authority 隐藏两类写入口；清单 GET 或 overview 刷新失败时清陈旧数据并禁止写。
- 参数命令号的指纹包含 key/value/expectedVersion/reason；结果未知原样重试复用同号，输入或版本改变铸新号。人工放行按 entry 维持同号；服务端 payload hash 防同号改理由静默吞单。

### 3. 三桶、提现与簇熔断

- reward entry 与钱包 credit 在同一事务；source/ref/user 和 idempotency key 有唯一约束，钱包 credit 失败会回滚 entry。
- release 只改变保护分录桶，不重复 credit 钱包；status 在簇受限时把已记录 withdrawable 投影到 bonus_locked。
- 提现不是信任 UniApp 展示值：服务端锁钱包后重查簇和 protected amount，再做版本条件 reserve；因此陈旧客户端快照不能扩大资金流出。

## 四、未关闭风险

### R-01（硬门）OPEN-ENG-001 自动可信证明未签

缺签名 carrier 身份、防重放、设备凭证与生产调用契约。当前实现安全地停在 `manual_only`，所以结论是 **HOLD**，不是 FAIL；只有工程前置完成并通过端到端独立验收后，自动可信证明才能改为 PASS。

### R-02（P2）UniApp 同账号 ABA / 并发刷新仍可能接受旧响应

`refreshEarningsReleaseStatus` 只比较 `activeEarningsReleaseAccountKey`。A 请求在途 → 退出绑定 default → 同一 A 重登 → 旧 A 响应返回时，key 又相等，仍可覆盖新会话；同账号两次刷新也没有 latest-request revision，旧失败可能清掉新成功。建议绑定单调递增 generation，并在成功和失败分支同时比对 `{accountKey,generation}`，补可控 Promise 的 A→logout→A、先慢后快、先快后慢行为测试。

该风险不造成跨账号读取，提现提交仍由服务端失败关闭，因此不把当前 manual-only 主链降为 FAIL。

### R-03（实证缺口）未做真实 MySQL 双连接与认证浏览器写路径

本轮遵守只读/测试边界，没有创建夹具、人工放行、调参或提现；本机 8080 未监听，GET 返回连接失败。行锁、事务、RBAC 主要由代码、Mapper SQL 和测试证明。上线前仍应在隔离夹具补：同簇双连接抢槽、同 entry 双命令、B1 snapshot 不可用/低线、audit 失败回滚、403 角色矩阵、刷新/重登与认证 release-status 实载荷。
