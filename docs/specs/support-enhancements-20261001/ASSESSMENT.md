## 4. 无顾问处置：一个设置、明确边界

建议决策顺序：先确认当前归属 → 能合法继承则继承 → 其余确实无顾问客户按 D01 处理。

| 场景 | 建议行为 |
|---|---|
| 已绑定，顾问离线/忙碌 | 保留原顾问，留言等待；不参与随机 |
| 已绑定，顾问停用/资格失效 | 保留归属和交接记录，由主管正式转绑；不能按“无顾问”偷偷重分 |
| 正常邀请、规则有效、未超限 | 继续直接邀请人的继承段，不额外随机 |
| 自然注册、邀请人未绑定、继承超限 | 自动模式随机，主管模式入池；原因仍保存用于解释和排查，但不是额外设置 |
| 继承规则未配置 | 不猜层数、不做继承；真正无归属时仍可执行独立的 D01 设置，随机成功不等于继承已启用 |
| 没有合格顾问 | 不阻断正常客户求助，入池且明确无候选；建议对自动模式新产生的此类记录安排可追踪重试，不暗改历史池处理范围 |
| 存量关系待核对 | 先确认真实客户、有效归属数量和关系一致性；确认确实无归属后才能按模式处理，重复/孤儿/未裁决矛盾继续待核对 |
| 自动与主管分配同时发生 | 只有一个归属能提交；后到者刷新实际结果，不覆盖已完成绑定 |
| 候选选中后停用 | 提交前重验，不能绑定失效账号；重试仍遵守同一任务和实际结果 |
| 修改设置、顾问新增、浏览器重试 | 不重排已有绑定，不因同一操作重试重新抽签；存量池遵循 P01 |
| 下级先绑定、上级后来补绑 | 不自动迁移既有下级；后续新注册才按直接邀请人的当前段判定 |

随机候选按真实顾问账号去重，沿用有效账号、客服角色、启用专属坐席等资格；不拿会话并发上限当绑定客户上限。建议等概率随机，不宣称人数必然平均，不依赖在线状态暗改长期归属。超管修改模式需显示影响、确认、理由和审计；改为主管模式后尚未提交的自动任务应重新核对最新模式。

## 5. 圈选群发：逐客私聊，保留服务责任

- 入口建议同时放在“我的客户”和 M3“主动联系”。只能圈选当前顾问本人客户；主管审阅不等于可以冒名群发。
- 支持单选、当前页全选、筛选后跨页选择；若提供“全部筛选结果”，必须显式显示实际人数、可排除名单，并固定确认时的客户集合。发送途中新进入筛选的客户不能被自动追加。
- 建议圈选维度：账户/维护状态、等级、标签、注册区间、最近活动、充值/提现区间。全部由真实数据查询，未知数据单列，金额按 P03。
- 内容覆盖文字、图片、快捷模板/话术、SKU 及当前有效跳转；只做人工发起，不顺带扩大为定时营销系统。群发是一批独立 1v1 消息，各客户看不到其他接收者。
- 确认页展示名单与数量、排除原因、发送内容、用途、当前顾问。发送前及逐客落库时重验归属、坐席资格和“不再维护”状态。
- 批次保存逐客结果：待发送、发送成功、失败、跳过。成功是服务端消息已落库，不能宣称已读或送达。可取消尚未发送部分，已发送不假装整体回滚；刷新或关闭浏览器不丢失任务结果。
- 重试只处理未成功项，沿用逐客稳定消息标识；超时未知先查原结果。客户中途转绑则跳过，不让新顾问替原发起人继续发送。
- 普通联系不计维护；维护发送每客成功才记执行，同消息重试不重复记账。群发不能自动清除客户已有问题的待回复状态，不能自动标维护成功。
- 群发图片可上传一次，但各接收者必须得到各自可授权和撤权的消息引用；不能把原单客私有附件链接直接复用给所有人。

## 6. 360、数据真实性与头像

客户资料建议分为身份与联系、资金与设备、风险与标注、服务与维护四组，保留所有有效旧字段及新版字段。360 提供本人客户范围的完整服务视图，关联工单和历史会话可直接定位当前客户。内部备注与风控信息不得放入对客消息或客户端。

当前全局 360 只有模块权限和角色投影，没有客服归属过滤；因此不能为恢复入口直接给客服全局 360 权限。应在客服对象授权之下复用数据；只读资料、字段可见范围、资金/账户操作权限分别判断。建议普通客服可看本人客户的风险等级和客服可读说明，不恢复全量风险评分细节、案件正文或安全会话；这些字段仅具原专项权限者可阅。转绑撤权同时覆盖详情、消息、附件和重新加载，不只隐藏按钮。

核实的旧问题：会话累计金额只加最近 20 条，360 只加最近 30 条；某些子接口失败回填 0。风险缺失时既有前端默认中风险，也有后端按账户状态自行推算 20/76/88 分，可能误显低/中/高风险。正式恢复应取可信风险等级，缺失明确未知，停用这些伪造评级的兜底；补准确金额聚合和明确可用状态。展示 0、未知、无权限、读取失败四者不能混用。注册时间、最近登录和有效活动时间分别命名；近期流水不冒充累计。

头像建议：新建顾问/客服账号时上传并预览；建议新建客服或既有内部账号首次启用对客坐席时必填，普通内部运营账号不强制，此必填细节仍为建议。以真实管理员账号 ID 为顾问头像身份键，只有一份持久资源键和版本，各坐席及顾问接口引用，不能形成账号头像/坐席头像两套可写来源。已有坐席无头像先兼容姓名占位，由超管补齐，不因此停用或解绑。超管可替换头像，失败保留原图；客户头像读取其现有资料，不新增客服替客户改头像的权限。对外顾问资料、会话列表/标题/消息作者和客户端同步使用真实资源；历史作者身份不因转绑或改头像变成新顾问。上传校验、存储和授权复用现有设施，不能借头像上传扩大设备管理权限。

## 7. 设计与实施顺序

1. 确认 P01–P03，固定本稿逐项保留清单；输出正式业务 SPEC、字段/权限/状态契约和验收矩阵。
2. 按主人要求实际调用生图工具，生成包含全部必要信息的会话稿、群发选择/确认/结果稿、分配设置稿、头像创建/编辑稿；单独校正图片占位值和文字，之后才进入界面实现。
3. 后端先交付统一分配、顾问头像、资料聚合与授权契约；并行任务必须分清文件所有权。
4. 群发和 SKU 消息接现有专属发送链；后台接资料/模板/群发，正式 uniapp 客户端同步头像、链接及必要消息展示。
5. 各阶段按已有授权使用工作树和阶段会话，新会话使用 GPT-6.1 Sol high 或以上适合模型；主线最终跨仓验收。

验收至少包含：旧能力逐项存在且可操作、超层新段、同客并发分配、空候选、停用交接、改模式时未发任务、群发部分失败/超时/刷新、转绑撤权、不再维护排除、维护不清待回复、累计超过 30 笔且多币种、子接口失败、头像替换失败/成功后刷新、SKU 下架与链接失效、旧消息只读、真实回执、长列表分页、窄屏与键盘。

## 8. 本轮结论边界

这不是把旧页面整体换回来：旧版有效能力迁入新版专属模型，已确认退役项不复活；所有信息保留都需要真实数据、权限和可操作入口支撑。调查覆盖源码、Git 历史和两版页面实景，尚未实施上述新增能力，也没有新增功能通过验收的声明。
