# 客服统计与分级工作台：功能契约

状态：详细设计，待实施。适用产品基线为 33041 客服改版预览对应业务线；本文不证明该端口已经实现以下能力。2026-10-06 主人裁决优先于旧规格。

## 1. 目的、入口与边界

普通客服要知道今天先服务谁；主管要知道哪里积压、谁需要支援；总管理员要知道全平台服务覆盖和经营结果。数据必须能下钻到同口径列表，而不能靠卡片推测。

入口沿用 M1 工作台、M2 客户列表、M3 即时会话、客户详情、服务规则。三种角色共用事实数据与组件，但首页排序、主要内容和操作权限不同。M4 工单及原有合法快捷操作继续复用，不新建平行后台。Janus 开发、旧 KYC、临时转交和备用池不恢复。

## 2. 已确认的业务规则

1. 自动继承客服默认无限制；它是服务归属规则，不是邀请统计的统计层数。
2. 首充包含首次成功充值或首次购买设备，以最早合格事件为准，每个客户终身只计一次。主人明确系统赠送、试用等不算；实际付费试用转正式与免费领取分开处理。
3. 邀请数同时展示直属和全部下级，均不含本人。跨顾问下级只给获准的聚合数字，不因此开放下级个人资料。
4. 工作台期间首充按发生时客服归属统计；当前客户列表按当前绑定归属展示。两者不能互换。
5. 即时会话以旧原型三栏和原有效内容为基础补齐，再加入新资料；字段保留清单见 [LEGACY-COVERAGE](LEGACY-COVERAGE.md)。
6. 新增客服分组及每组资金、设备、活跃、服务等多角度看板；主人明确主管只看本人负责的组，总管理员看全部组。分组模型、归属历史、池路由、移交撤权及指标补充见 [GROUPS](GROUPS.md)。
7. 系统支持设置多名主管，总管理员可查看主管数量、各主管负责组与经营/服务统计；所有统计数据可下钻，且下钻保持原权限、范围、时间、币种和事实口径。

## 3. 首充（含购机）

以下为本次方案的细化建议：零实付不计首次付费转化、正额差价购机计入、付款后退款保留首次成功历史。这些是为避免重复和赠送混入而提出的规则，不冒称主人逐项明示；它们随整份设计评审，不另增付款方式或分析系统。

### 3.1 合格事件与状态

候选集合 = 成功实际入账的充值事件 ∪ 成功实际付费的设备购买事件。充值礼赠、人工加款、测试记录不是充值候选；订单已创建、待付款、支付失败、支付关闭、仅预授权不是购机候选。

购机按真实订单类型与对应付款事实适配，不能仅看设备来源或统一套用订单状态字符串。余额支付合格；折扣后仍有正数实际支付合格；全部由赠券抵扣、零支付不合格。新购、组合购、保留旧机另购新设备（CAPACITY_KEEP）及付费试用转正式属于购机；设备置换以实际支付的正额差价结算时成为候选，不要求等到发货/激活。单独保留算力、续费、锁仓、购买服务不属于本次设备购买定义，不得与“保留旧机另购”混淆。

不要把所有来源为 TRIAL 的设备排除：试用转正式可能仍保留此来源。不同支付链的入账状态可能不同，不强制每个订单都有同名 paymentNo、SUCCESS 或 ACTIVATED 状态。

按 `(成功时间, 固定来源优先序, 稳定事件ID)` 取最早事件；成功时间完全相同的充值与购机，以充值优先并保留两个源事件用于核查，不随查询顺序漂移。批量重放、重试回调、补数均按源事件ID幂等；一笔订单购多台或多SKU仍只有一个付款事件、一个首充客户。

先在客户全历史、全部支持币种中确定唯一首事件，再做日期/币种筛选；切换币种不能让同客再次首充。付款与转绑同刻发生时按服务端可证明的事务顺序/归属版本归因，证据缺失则归属未知，不猜测。

| 对象 | 必需字段 / 规则 |
|---|---|
| 合格付款事实 | 客户ID、来源类型、源业务ID、实际支付金额与币种、成功时间、源状态、退款信息、数据版本 |
| 首充事实 | 客户唯一键、首事件ID、来源充值/购机、首事件时间、首事件金额/币种、发生时顾问ID及归属状态 |
| 归属状态 | 已知顾问、当时未分配、历史未知；三类分开，不能用当前顾问回填历史未知 |
| 查询结果 | 数值、状态、统计范围、期间/时区、币种、截至时间；必要时标明数据覆盖起点 |

首充判定状态：待核实 → 未首充 / 已首充（充值）/ 已首充（购机）。源接口失败保持“暂不可用”，无权限显示“无权限”；这两种都不是“未首充”。历史不完整时不得把“未找到”当终身未首充，显示“历史待核实”。

真实付款成功以后退款，不抹掉曾经付费的事实，首充人数不自动倒减；退款单列，未退款净额另行统计。若原事件被证明是重复、测试或错误事实，由有权限的数据修正流程审计后重算，并保留修正原因与前后差异。

### 3.2 金额与归属

- 首充金额是每客首事件的实际金额，按充值来源/购机来源分别展示；不同币种不得相加。
- 充值累计只加实际成功充值，购机不加到充值里。购机累计按付款事实单列，退款另列；不可把“充值+购机”称为新增资金或净收入。
- 本月首充：首事件发生在本月，按事件当时绑定归属记账。转移客户不会重写客服历史业绩。普通客服对已转出客户仅保留汇总，不能继续获取逐客历史明细；下钻明确“含已转出客户N名，仅汇总可见”，不输出身份、逐笔金额或可反查链接。
- “当前名下已首充客户”是当前客户资产结构，即使首充发生在转移前也可显示；必须与“期间归属首充”分区标识。
- 当时未分配与历史归属未知单列。全平台期间已确认首充 = 各发生时顾问已确认首充 + 当时未分配 + 已确认首次但历史归属未知；被停用/离职的顾问仍占历史分组。连是否首次都不能确认的客户另列“历史待核实”，不加入已确认人数；覆盖不全时不得把已确认数标成完整总数。
- 期间充值也按充值发生时归属汇总；客服当前绑定客户的历史累计充值是另一列，不能拿当前归属重算期间成绩。组维度同理：事件保存当时组别，调组不搬过去业绩；当前成员和客户资产随现归属变动。主管授权组集合以当前负责关系为准，历史数据不能恢复已撤销的组权限。

### 3.3 最小判定样例

| 事件顺序 | 首充结果 | 充值累计 | 购机累计 |
|---|---|---:|---:|
| 充值100 → 余额购机80 | 充值首充，1人 | 100 | 80 |
| 无既往充值，用合法既有余额购机200 → 充值50 | 购机首充，1人 | 50 | 200 |
| 系统赠机 → 免费试用 → 试用转正式付120 | 购机首充，发生于付120成功时 | 0 | 120 |
| 全额券购机0 → 后续充值30 | 充值首充，发生于付30成功时 | 30 | 0 |
| 待付100 / 失败100 / 赠余额100 | 不构成合格事件 | 0 | 0 |
| 已充值100后退款100 | 保留充值首充；退款100单列 | 100 | 0 |

上述样例币种相同，仅用来解释规则；不得当作运营数据。本需求只识别现有合法付款事实，不恢复已退役的商城外部直付；余额的来源仍受原资金规则约束，赠机/赠余额本身不算付款事件。

## 4. 指标字典与操作价值

所有累计均取服务端全量事实，不能从当前分页、浏览器缓存、头像列表或最近20条流水求和。金额用服务端精确十进制，展示随币种精度；“未知”和真实0严格区分。

| 指标 | 定义 | 展示与用途 |
|---|---|---|
| 当前绑定客户 | 当前有明确绑定关系到所选客服的人数，按客户ID去重；停用顾问的存量绑定仍保留，单列待交接 | 客服资产规模；点开同范围客户 |
| 平台客户 / 归属覆盖 | 全平台客户去重；已绑定、待分配、归属异常三组互斥；停用仍有合法绑定属于已绑定，并附待交接标记，不能同时归池 | 总管理员覆盖图，三组合计与平台总数核对 |
| 客服账号数 | 有客服资格账号去重；启用/停用分组；在线/忙碌为动态状态，不能和启停相加 | 总管理员账号结构与停用交接 |
| 首充（含购机）人数 | 期间首次合格付款的客户去重；充值来源与购机来源互斥 | 服务转化数量；下钻带来源和日期 |
| 期间充值 / 购机 | 期间成功事件按发生时顾问归属；两类金额分列 | 衡量经营结果，避免重复资金 |
| 个人累计充值 | 该客户全部历史成功充值 | M2列表与M3同一个结果 |
| 直属邀请人数 | 当前邀请关系中直接下级去重，不含本人 | 拉新规模；有权限才展开个人 |
| 邀请团队人数 | 当前邀请关系全部可达后代去重，不含本人 | 标为“邀请团队”，不与客服名下混淆 |
| 邀请团队累计充值 | 上述后代集合每客成功充值之和，不含本人 | 跨顾问只展示获授权汇总；各行可能重叠，禁止按行相加当平台总额 |
| 客服名下累计充值 | 当前绑定客户各自个人累计充值之和 | 当前资产规模；不加邀请团队列，避免多次统计 |
| 活跃客户 / 最近活跃 | 沿用现有可配置活跃窗口与真实最近活跃时间；不以客服发消息刷新活跃 | 显示窗口和时间；不新增不透明“活跃分” |
| 待回复 | 沿用既有跨人工会话回复游标：任一人工会话存在未被指定回复游标覆盖的客户消息即算，按客户去重；已读不等于回复 | 等待起点取该客户最早未处理消息；另一会话被回复不能抵消旧待回复 |
| 首次待联系 / 待维护 | 沿用现有首次联系与维护规则；不再维护不进主动任务 | 有明确下一步“联系/维护”，客户主动咨询仍可处理 |
| 服务质量 | 本期使用已有待回复时长、待维护、首次待联系 | 与经营结果并列，不只按充值评判客服；不新增评分/排名系统 |
| 退款 / 沉默 | 退款独立计，沉默按现有配置窗口 | 已有详情与任务筛选继续保留，不把每项都堆首页 |

后续可选统计缺口：首响/解决时长分布、复购、明确注册批次的首充转化率。本期不新增事件采集、评分或分析窗口；这些要等真实事件完整且运营用途确定再立项。本期只给可靠人数与金额，不以“本月首充/当前名下人数”冒充转化率。平台总量包含未分配，客服统计不能代替平台总量。

邀请图异常（循环、孤儿、重复边）由服务端去重与检测返回异常状态；不能截断成假完整数字。无限继承无需前端无限递归；统计走服务端可扩展的关系查询或汇总并返回截至时间。

## 5. 角色与服务端权限

| 能力 | 普通客服 | 主管 | 总管理员 |
|---|---|---|---|
| 默认首页 | 我的工作台，以个人待办为主 | 我的分组管理，以负责组的分配/负载/积压为主 | 平台运营总览，以全平台/各组覆盖和经营为主 |
| 当前客户、会话、统计 | 本人绑定客户；期间业绩可含已转出但仅允许汇总 | 当前本人负责组的客户与组历史，可按组/组内客服筛选；无组则合法空态 | 全平台，含全部组、未分组、未路由/未分配及历史未知 |
| 会话发送 | 当前绑定且仍有接待权限 | 对他人会话默认审阅，只读；先正式转移到自身并有客服资格才可发送 | 同主管，管理权不是冒名回复权 |
| 分配 / 正式转移 | 不可 | 仅负责组的待分配队列及合法组内目标；跨主管组由总管处理 | 可跨组；明确客户/成员集合、目标、理由、影响与审计 |
| 跨顾问邀请聚合 | 按已批准策略可看聚合；个人明细不透出 | 管理范围内可展开，范围外仅汇总 | 全平台可展开，仍遵循字段级敏感权限 |
| 全平台客服数量/覆盖/规则 | 不展示 | 仅负责组客服负载；原获准只读规则摘要，不显示全局池数量 | 全量；规则编辑还须具有对应管理能力 |
| 分组管理与看板 | 可见自己所属组名称，不查看整组经营或成员隐私 | 创建/维护自己负责组、管理获授权成员；不能接管别组 | 全部分组、负责人交接、未分组客服及未路由池 |
| 账户/资金/重置密码等 | 有原模块动作权限才可执行 | 不因主管头衔自动获得资金写权限 | 统计全可见，具体高敏动作仍受原流程约束 |

服务端由认证身份解析角色、当前负责组集合与范围，前端 role/groupId 参数只是请求条件。卡片、曲线、表格、搜索、导出、URL直达、360资料、图片附件和数字下钻都用同一权限范围。筛选groupId/agentId不能越权，直接篡改请求拒绝且不返回越权计数。“全部”对主管仅表示全部负责组。组移交或客服跨主管调组与客户转绑一样必须即时撤销旧主管访问。

组内客户的已获准邀请树聚合属于客户画像，继续按全后代规则提供；不据此返回当前角色获准范围外的成员身份或按范围外组拆分数据。主管负责范围内与总管理员客服域权限内的明细按上表展开。组看板的客户、资金、设备及活跃总数只使用本组直接服务客户的自身事实，绝不叠加邀请团队列。组未绑定队列与全平台未路由池分开，主管不能读取后者的客户或数量。

归属转移/权限撤销即时让旧客服停止发送，关闭详情与附件访问并清除对应缓存、订阅和未发送草稿的可见性；写操作在提交时二次检查权限，不能只检查弹窗打开时。保留合法服务历史与审计，不向已撤权客服泄露。

## 6. Tab、筛选、排序与一致性

保留现有全部/待回复/首次待联系/待维护/活跃/沉默/不再维护等真实入口，待分配按角色与负责组开放；新增“未首充”“已首充”作为可组合筛选，不用不互斥的状态冒充互斥总数。具体当前Tab清单以对应业务注册为准，不能因新版屏幕空间删除入口。

“按tab类型排序”落实为：每个Tab有自己的默认排序，并可点表头升降序。待回复→等待最久；首次待联系→分配时间最早；待维护→到期最早；沉默→最近活跃最早；全部/活跃→最近活跃最新；已首充→首事件最新；未首充→注册最早；不再维护→状态更新时间最新；待分配→进入池最早。以上默认字段缺失时未知置末，服务端用客户ID作稳定次序。

可排序字段：注册/分配/最近活跃/首充时间、直接邀请数、邀请团队人数、个人累计充值、邀请团队累计充值、维护到期、等待时长（仅有该字段的Tab）。多币种金额必须先选币种；无权限/未知数不参与数值比较且始终置末。

服务端在授权全集先筛选再排序再分页。连续翻页使用同一查询快照；若现有接口不支持快照，至少带查询数据版本并检测变化，变更时提示回第一页刷新，不无提示拼接新旧页。仅显示“截至时间”不能代替此保证。范围、币种、日期、排序或Tab变化回到第一页；浏览器记住本账号各Tab排序偏好，禁止带入另一账号；返回详情保留同一筛选/页码与滚动位置。筛选条件和表头明确当前排序。统计卡下钻携带相同范围、期间、币种、来源及时间口径；失败重试不偷偷回默认范围。

所有可展示的统计数字、分布分段和趋势点都进入对应明细，不能只弹口径解释冒充下钻。0也可打开同筛选空列表；未知/异常数字进入有权的待核实对象及原因。比例可查看分子/分母清单。明细再进入原对象详情或业务流水，返回保留范围与位置；没有对应权限的部分明确“仅汇总可见”，不伪造与汇总等量的个人列表。总管理员可用全量权限完成总数与明细核对。具体主管→组→客服→客户/事件的下钻映射见 GROUPS。

日期显示统一业务时区（沿用后台配置），请求使用起始含、结束不含。默认期间为本月，可选今日/昨日/近7天/近30天/本月/自定义；配置未加载不自行猜时区。当前快照与期间业绩分区展示，不让日期选择器误导“当前绑定客户”会随期间变化。

## 7. 无限继承参数、状态及迁移

| 参数 | 目标默认 / 含义 |
|---|---|
| 自动继承模式 | UNLIMITED：不限继承代数；LIMITED：最多N代，沿用现有合法非负整数范围，0表示不继承下一代；UNCONFIGURED只用于识别存量待升级配置 |
| 有限深度 | 根客户为0；直接邀请为1；限制N时N+1不再自动继承，按无顾问分配策略处理 |
| 无顾问分配 | 默认SUPERVISOR：进待分配池；保留现有AUTO_RANDOM等已明确配置，不强改 |
| 手工转移 | 只作用于操作中明确列出的客户，不默认整条邀请链一起转移 |

无限制仅移除“超过代数”这个失败条件；上级无有效顾问、停用顾问、邀请关系异常等仍按现有无顾问规则处理，不能无限查找无效上级或绕过账号资格。具体继承锚点复用现有服务端规则；不要把邀请树无限层统计与服务绑定深度混用。

迁移策略：新建配置默认UNLIMITED；存量明确LIMITED/UNLIMITED原样保留；明确存在的UNCONFIGURED记录通过有版本、可审计的迁移改为UNLIMITED，仅影响迁移后的新注册分配。缺字段、数据库读取失败、配置服务报错不能冒充UNCONFIGURED后自动兜底为无限。

本变更不追溯重排已绑定客户，也不自动捞取历史待分配池。处理旧池需独立筛选、预览目标集合并走原分配动作。普通客服不可修改。规则编辑显示旧值→新值、起效范围“新注册”、历史不变说明，理由与审计沿用现有高敏配置规则，提交中禁重复，失败保留输入并允许重试。版本冲突先刷新差异，不覆盖别人的配置。

## 8. 接口与实施依赖（设计，不代表已存在）

复用现有 Support API、客户详情、工作台、列表、分配规则的路由与鉴权，不再开一套平行CRM API。实施时扩展现有请求/响应模型，最后确定字段名；以下是最低语义要求。

1. 工作台返回有效范围、当前资产快照、期间事件业绩、首充来源拆分、未分配/未知、更新时间；由同源查询保证总分核对。
2. 客户列表补全邀请数、充值汇总、首充摘要与支持的排序白名单，分页返回total和数据快照时间；禁止客户端遍历全树/分页拼总额。
3. 客户详情与M3复用统计结果，包括成功/空/未知/无权限/失败状态；分区加载错误不吞掉其他已加载内容。
4. 付款事实适配复用订单、账本、充值权威模块；先确认历史覆盖与事件发生时顾问历史，缺少则先建设补数/归属历史，不能拿UI示例上线。
5. 自动继承使用现有配置接口及注册分配服务，增加新默认、受控存量迁移与回归用例。
6. 首响/解决时长、注册批次转化率等属于后续可选项；本期没有为它们补建采集或分析系统的依赖。

实施顺序：分组与归属历史/授权迁移 → 锁定付款、设备及活动事实 → API聚合/权限/排序 → 三角色/分组工作台与M2 → 旧M3补齐及新字段 → 默认迁移 → 跨角色端到端验收。每步进入下一步前都有可运行反例，具体见 [ACCEPTANCE](ACCEPTANCE.md) 和 GROUPS 的分组验收。
