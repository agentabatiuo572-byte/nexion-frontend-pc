# 客服重构：主人要求与已确认决定

日期：2026-09-29。此文件是本任务的需求输入，功能契约由同目录 SPEC 正文承载，视觉稿与交互说明单独存放。

## 原始目标

1. 重构后台客服业务与 UI。客服账号登录后有自己的工作台，展示绑定客户、活跃客户、沉睡客户、待维护客户、会话消息与可直接执行的待办。
2. 沉睡天数、待维护天数可由超管在客服板块配置。
3. 每位客户绑定一个专属顾问，双方进行独立 1v1 沟通；一个顾问可以服务多位客户，但不同客户之间相互隔离。
4. 邀请链 A→B→C 可继承同一顾问；自动继承最大层数可配置，超出者进入待绑定池，由客服主管分配。
5. 在设计前核对现状、推敲矛盾，不把未明确的规则当已确认需求。

## 已逐项确认

### R01 沟通范围

主人选择：先做站内文字、图片等私聊，暂不含实时语音、视频。

### R02 人工分配与继承段

主人选择：人工分配后开启新的继承段。起点记为 0 层；最大 2 层时，A0→B1→C2 归 G1，D 进入待绑定池。D 人工分给 G2 后为新的 0 层，其未来邀请可再次向下继承。

### R03 严格专属

主人选择：消息留给原顾问；紧急情况由主管正式转绑后，新顾问才能回复。无临时代班，不得因离线、忙碌、并发会话已满而暗中更换顾问。

### R04 转绑范围

主人选择：默认只转指定客户，已有后代保持原归属；需要一起转时主管另行选择并确认范围。

### R05 维护执行、成功与停止

主人原话："算执行了一次维护，但直到用户账户重新活跃才算维护成功，客服也可以选择将该用户标记为不再维护。"

必须分别建模维护执行事实、重新活跃结果、是否继续主动维护。成功发送人工联系可以记录一次执行；客户回复不直接替代账户有效活跃事件；失败发送、自动推送、点击完成、改备注不能伪造执行或成功。不得将不再维护计为成功。

不再维护的默认边界：仅停止主动维护任务，不解绑、不删除客户、不屏蔽客户主动求助；仅本人客户可操作，需理由和可追溯记录，并提供恢复维护。规格必须明确停止后再活跃、恢复维护、重复联系、转绑后的归因与计数规则，不得隐含矛盾。

## 已提出方案的实施边界

- 邀请关系、当前服务归属、维护状态分别保存；转绑不得修改邀请或既有财务业务关系。
- 待绑定客户最多零个有效顾问；已绑定客户恰好一个有效归属，必须由服务端与数据库保证，而非前端过滤。
- 未绑定客户仍可留言。无邀请人、邀请人未绑定、继承超限等分别记录入池原因，不跳过未绑定邀请人向上寻找顾问。
- 注册时无法继承则进入待绑定池；上级之后补绑不自动吸走历史池中客户，主管可显式选中分配。
- 人工单客与批量分配使用同一规则：每个选中客户新开 0 层起点，未选中客户不动。重试同一操作不得重复重置。
- 修改最大层级只影响之后的新注册判定，既有归属和待绑定记录不自动重排。修改沉睡或维护阈值可重算现有标签，不伪造历史行为。
- 个人工作台六个核心指标：绑定客户、活跃客户、沉睡客户、待维护、待顾问回复、首次待联系。活动统计窗口与当前状态分开解释，待办按客户去重；已读不等于已回复。
- 活跃来源必须为客户真实、服务端认可的前台活动；排除 token 心跳、自动结算、设备后台任务和管理员操作。缺数据明确 unknown，不伪造时间。
- 新顾问的首次联系按本次归属计算。历史消息保留作者，新顾问接续必要历史，旧顾问转绑后停止读写及附件访问；主管可审阅，不冒用顾问身份发送。
- 绑定人数与会话并发分别展示；本期不额外强加未要求的绑定人数上限。
- 超管可配置规则；主管可分配、转绑、审阅与处理停用顾问交接；普通客服只服务本人客户。旧 M1/M3/M5、普通客服入口、转接、主动发送与图片接口不得旁路专属规则。
- 规则初始值先查现有权威配置。不存在时明确未配置及启用前置，不得把设计样例中的 30 天、7 天、2 层当作已批准的线上值。
- 保留工单与知识库的已有功能，工单内部协作不得旁路专属对客发信权限。
- 客户端仅同步必要的顾问归属、等待分配状态、图片消息、失败恢复与访问契约；不扩展到网站或无关页面。
- 存量迁移先预检重复/缺失/异常绑定，保留旧关系和历史，不从任意旧会话接待人推断长期顾问。不得擅自对生产数据库执行迁移或发布。
